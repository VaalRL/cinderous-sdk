# 0078. 耐久度發布加 `standbyWhenDisconnected`：主要中繼只是沒連線時可以不改用備援

- 狀態：**已接受（Accepted，2026-10-13）**——CinderSync 自動化實機驗證時找到（使用者 2026-10-13「三個 bug 都修」，這是驗證修正時發現的第四個）；實作於 v0.57.0
- 日期：2026-10-13
- 對應：ADR 0041（耐久度、備援補發）、0045（G12d 名單待送）、0054（只讀中繼）、0056（名單分享備援清單）；CinderSync ADR 0017、0018、0031

## Context
CinderSync 是排程連線：兩輪之間刻意不連中繼。實機（2026-10-13）在設了備援的那台記錄每一次發布，名單發布（kind 1060）全部是：

```
錨點 1: not-connected   →   錨點 2（備援）: accepted   →   算送出（pending 清掉）
```

`#publishDurable` 在主要中繼**一座都沒開**時，耐久收下數是 0，就延遲連上備援補發。這對一直連線的應用是對的（主要中繼掛了就用備援）。但對排程連線的應用來說，兩輪之間的每一次名單變動（改名、宣告備援、新增或撤銷裝置）都只落在備援上，沒設同一座備援的裝置**永遠收不到**。

名單分享備援清單（ADR 0056，CinderSync ADR 0031）本來就是要讓還沒設備援的裝置知道該加，這個宣告自己也走名單發布，形成死結。

## 決策
- `PublishDurability` 加 `standbyWhenDisconnected?: boolean`，預設 `true`，與之前相同。
- 設 `false` 時：主要中繼**只是沒連線**就**不改用備援**，照實回報 `not-connected`、不滿足。名單同步據此記成待送（G12d），連上主要中繼時重送。「只是沒連線」的定義是：沒有一座開著，也沒有一座被健康狀態擋下。
- 主要中繼開著但拒收、已滿、被健康狀態標記時，照舊改用備援。

## 試過、沒有採用
- **一律不在沒連線時用備援**：一直連線的應用在主要中繼全掛時就失去備援的意義；改成選項、預設維持原行為。
- **應用自己在兩輪之間不呼叫發布**：名單同步在名單一變就送（`onChange`），應用要攔就得包一層連線池；在耐久度選項上表達最直接。
- **讓沒設備援的裝置也去讀備援**：備援是各裝置自己設定的，還沒設的裝置不知道有這座。

## Consequences
- ＋ 排程連線的應用：兩輪之間的名單變動等下一輪送到主要中繼，每台都收得到；備援只在主要中繼滿了或拒收時用。
- ＋ 預設不變，其他應用不受影響。
- － 設了 `false` 的應用：名單變動要等下一次連上才送出（排程連線本來就是這樣）。
- 驗證：`tests/relay-pool-durability.test.ts`〈standbyWhenDisconnected〉（沒連線不連備援、預設照舊、開著但拒收照舊用備援）；CinderSync `tests/e2e/schedule-e2e.test.ts`〈兩輪之間的名單變動不改送備援〉。
