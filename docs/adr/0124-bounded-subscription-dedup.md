# 0124. 常駐訂閱的去重表有上限

- 狀態：**已接受（Accepted，2026-10-29）**——使用者 2026-10-29：「先修 SDK 再遷移」（Cinderous 即時通訊把連線層改接 `RelayPool` 之前）
- 日期：2026-10-29
- 對應：SDK ADR 0001（連接池以 id 去重）、0035（補訂閱的游標與回溯窗）；Cinderous ADR-0398（引擎連線層改接 `RelayPool`）

## Context

`RelayPool.subscribe` 以事件 id 去重：每個訂閱一個 `Set`，收過的 id 全部放進去，**從來不刪**。

遊戲一局就關掉，看不出影響。聊天 App 不一樣：桌面版常常好幾天不關，常駐訂閱一直收到聯絡人的心跳（在線時 30 秒一則、閒置時 5 分鐘一則）。50 位聯絡人在線，每天多記 1 萬多個 id，大約 1～2 MB，而且只會一直變大。惡意中繼也能一直送簽章有效的新事件，把記憶體灌滿。

去重本身不能拿掉，有兩種重複要擋：
1. **多座同時送同一則**：一次載入歷史時，別座可能晚幾分鐘才送到。
2. **補訂閱重播**：重連後的 REQ 帶 `since`（ADR 0035），可能被回溯的 filter（禮物包、收件匣）還要往前退讓兩天，這段時間內的事件會再送一次。

## Decision

1. 去重表改成 `Map<id, { createdAt, seenAt }>`，插入序就是收到的順序。
2. **每收 1024 則新事件整理一次**（`SEEN_PRUNE_EVERY`）。兩個條件都成立的 id 才會被忘掉：
   - 事件時間早於補訂閱的 `since`：每個 filter 各算 `resumeSince`，取最早的那個。補訂閱不會再重播這些事件。
   - 收到已經超過 `SEEN_GRACE_MS`（10 分鐘）：別座的同一則不會再晚到。
3. **上限** `maxSeenPerSubscription`（新選項，預設 50,000）：整理完還超過，就先忘最早收到的。上限比 1024 小時，整理週期也跟著縮小。
4. 補訂閱的 REQ、游標、`onEose` 都不變。

## Consequences

- 正面：常駐訂閱的記憶體有界。只有心跳這類非回溯的事件時，去重表大約只留最近 10 分鐘的量。
- 負面 / 殘餘：
  - 中繼如果不照 `since` 過濾（違反 NIP-01）、重連後重播整段歷史，已經忘掉的舊事件會再送一次給 `onEvent`。應用端本來就該容忍重複，因為多數中繼的 `since` 是秒級邊界。
  - 超過上限時，FIFO 可能忘掉還在回溯窗內的禮物包，造成極少數重複。這是記憶體上限優先的取捨。
  - 有回溯窗的訂閱要記住兩天份的 id。收件匣的量本來就小，可以接受。
- 驗證：`tests/relay-pool-seen.test.ts` 有 5 個測試，涵蓋：
  - 時間早於補訂閱範圍的會被忘掉；
  - 寬限內不忘；
  - 回溯窗內不忘；
  - 超過上限先忘最早收到的。
  
  四種破壞（拿掉補訂閱範圍的條件、拿掉寬限、拿掉上限、忽略回溯窗）各有一個測試會失敗。
