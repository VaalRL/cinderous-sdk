# 0074. 過時的摘要不觸發重送：摘要帶「已處理到各寄件人的寄件序號」與狀態識別碼

- 狀態：**已接受（Accepted，2026-10-12）**——使用者 2026-10-12：CinderSync 待辦「調查同一版本重複送出」→ 調查結果 → 「修正」；實作於 v0.56.0
- 日期：2026-10-12
- 對應：ADR **0025 §5**（摘要、索取）、**0045**（`digestPolicy`）、**0068**（寄件序號 `rs`、簽收單）、0028 §6（名單晚到時 `resync()`）

## Context
量測（`npm run measure:duplicate-sends`，同一個版本送給同一台幾次、依送出前發生的事分類）：

| 情境 | 重送比例（延遲 0／0–2 秒） | 主因 |
|---|---|---|
| 三台都在線、輪流編輯 | 0％／0％ | — |
| 一台離線、其他台編輯後它回來 | 37.5％／39.6％ | 過時的摘要 |
| 新裝置加入（200 篇） | 50％／54.8％ | 過時的摘要 |
| 重新啟動 | 50％／36.6％ | 過時的摘要 |
| 同時編輯同一篇 | 0.7％／23％ | 亂序到達的索取 |

**過時的摘要**：`NostrVaultTransport` 一連上就回報上線、之後才補拉中繼上積著的訊息；協調器在自己的佇列清空後就送摘要，**這時還沒處理完積著的訊息**。
對方看到摘要沒有那些版本，就把其實已經在中繼上、正要送到的版本再送一次。剛啟動的那台的摘要晚到（寄件人已經送出新版本之後才處理到）也一樣。
CinderSync 每次啟動（`resync()`）、每天的定期對帳、有修改的那一輪都會送摘要。重送不會遺失資料，但佔中繼空間、送出端額度與流量。

## 決策
1. **摘要帶 `seen`**：產生摘要時，已處理到各寄件人的最大寄件序號（`[deviceId, rs]`，ADR 0068 的 `rs`）。收件端持久化在 meta（`rh`）；簽收單送出後 `rp` 會清掉，`rh` 留著。
2. **摘要帶 `sid`**：這份同步狀態的識別碼（第一次啟動時產生、存在 meta）。寄件人記住每台最近的 `sid`；換了＝那台的狀態重建過（例如清掉了儲存、同一個裝置 id），`seen` 不能拿來比對，照舊重送。
3. **寄件端**：經中繼送出版本時，記下「送給哪一台（送出當下明確知道的收件人：指定的 `to`，或傳輸層的 `recipients()`）、哪個版本、序號、時間」（只在記憶體，最多 20 萬筆，超過丟最舊的）。
   處理摘要時，對方沒有的版本頭如果是**在 `seen` 之後才經中繼送給它、而且還在中繼的保存期內**，就不重送（還在路上）。其他照舊（缺的照樣補送）。
4. **真的遺失時怎麼補**：
   - 對方之後處理到比它新的訊息，下一份摘要的 `seen` 就超過了 → 補送；
   - 之後都沒有新訊息：過了中繼的保存期（送出端的 `retentionSeconds`）→ 補送；
   - 對方缺父版本時照舊來索取（`want` 不受影響）。
5. **`resync({ lost })`**：預設 `lost: true`——這台可能真的漏收了（名單晚到、訊息被傳輸層擋掉、中繼說有訊息在送到前被刪掉，ADR 0028 §6、0042）：摘要**不帶 `seen`**，對方照舊重送全部缺的。
   只是對帳（例如每次啟動送一份）時呼叫 `resync({ lost: false })`。自動的摘要（連上時、`'on-change'`、定期）都帶 `seen`。
6. **相容**：舊版收到新摘要略過兩個欄位、照舊重送；新版收到舊版的摘要（沒有 `seen`）照舊重送。線上格式版本不變。

## 試過、沒有採用
- **等補拉完才送摘要**：傳輸層沒有「補拉完了」的訊號；就算有，也解決不了「剛啟動的那台的摘要晚到」——那是寄件人那一端的時序。
- **用中繼帳（ADR 0068）判斷送過什麼**：帳裡的廣播沒有記收件人，新裝置加入之前的廣播會被當成「送過給它」→ 新裝置初次同步會卡住。
- **對方沒有 `seen` 裡沒有自己就不比對**：新裝置加入、剛啟動的情境（摘要裡還沒有任何寄件人）就得不到改善；名單晚到被擋掉的情境改由 `resync()` 預設不帶 `seen` 處理。

## Consequences
- ＋ 量測：過時的摘要造成的重送全部消失。重新上線 37.5％→0％（延遲 0–2 秒：39.6％→15.3％）、新裝置加入 50％→0％（54.8％→17.4％）、重新啟動 50％→0％（36.6％→0％）。
  剩下的是亂序到達時的索取（版本比父版本先到，回頭要了一次）與少數在路上的，屬正常。
- ＋ 線上格式向下相容，不必所有裝置一起升級。
- － 真的在中繼上遺失、對方之後也沒有新訊息時，要等過了保存期（預設 7 天）或對方呼叫 `resync()` 才補送；之前是下一份摘要就補。
  緩解：缺父版本時對方照舊索取；名單、中繼刪除通知等「可能漏收」的情況應用照舊呼叫 `resync()`（預設不比對）。
- － 寄件端多一份記憶體裡的對照表（每筆約 100 位元組，上限 20 萬筆）；重開後清空（重開後的第一份摘要照舊可能重送）。
- 應用：CinderSync 啟動時的 `resync()` 改成 `resync({ lost: false })`；新裝置加入、中繼刪除通知照舊用 `resync()`。
- 🔴 實作時發現：重新開啟的裝置原本**從中繼收不到**關掉期間的訊息（傳輸層在協調器註冊監聽前就收到、丟掉），一直靠這份摘要讓別台重送才補齊——同一版一起修（ADR **0075**），否則這裡的改動會讓那些情境補不齊。
- 驗證：`tests/sync/vault/stale-digest.test.ts`（格式、重開不變的 `sid`、重新上線與剛啟動不重送、遺失後依序號或保存期補送、`resync()` 預設照舊重送、狀態重建照舊重送、舊版照舊重送；變異測試：拿掉判斷、拿掉保存期、拿掉 `sid` 比對各有測試失敗）、
  `tests/pairing/coordinator-integration.test.ts`（名單晚到後 `resync()` 補齊）、全部單元與性質測試（另跑加大種子）。
