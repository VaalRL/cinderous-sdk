# 0107. 新加入的收件人不算加入前的廣播用量

- 狀態：**已接受（Accepted，2026-10-22）**——使用者 2026-10-22 同意處理 ADR 0106〈另案〉
- 日期：2026-10-22
- 對應：SDK ADR 0029（塊數預算）、0068（按收件人記帳）、0106（同一輪實機）

## Context

ADR 0068 讓中繼帳按收件人記，但廣播的訊息（沒有 `to`）記帳時不帶收件人，`used(device)` 把它算在**每一台**頭上，連之後才加入的裝置也算。

2026-10-22 motorola（MotoTest6）加入 VaultA 時，桌機的帳上還有加入前約 2,400 塊的廣播，大多是之前測試留下的。手機一加入，用量就是 2430／1080 塊：

- 送給它的批次一開始就被預算擋住，只能走直連；
- 實際上這些廣播從來沒有寄給它，它的收件匣是空的。

## Decision

1. `RelayLedger` 記下每台**第一次成為收件人**的小時（`join(devices)`，持久化在帳的 `j`）。
2. 沒有 `to` 的廣播帳，只有在那個小時以後送的才算它的。同一個小時、在加入之前送的照算（寧可多算）。
   - 指定 `to` 的照舊只算 `to` 裡的那幾台。
   - 簽收劃帳、過期劃帳、`wait`、`usage` 都依同一條規則。
3. 協調器每次取收件人（`#recipients()`）時呼叫 `join`。有新記的就盡快存下：晚存的話，重開後會當作更晚加入，變成少算。
4. **舊版的帳**（沒有 `j`）與全新的帳：第一次 `join` 時，名單上的每一台一律從 0 算——舊的廣播照樣算它們的。之後才出現的裝置，才從出現時算起。
5. 已經記過的裝置不改：被撤銷又加回來的，照舊算它以前的廣播（寧可多算）。

## Consequences

- ＋ 新加入的裝置一開始的中繼預算是空的，初次同步可以經中繼照常送（受批次限速），不必只靠直連。
- ＋ 只改送出端的帳，線上格式與收件端都不變。舊版 SDK 讀到帶 `j` 的帳會略過這個欄位，退回原本的算法（多算）。
- － 升級後第一次啟動時，傳輸層如果還不知道某台成員（名單還沒載入完），那台會被當作稍後才加入，加入前的舊廣播就少算。CinderSync 在協調器啟動前就載入名單，實務上不會發生。
- － 帳上多一個小表（每台一個數字）。
- 測試：
  - `tests/sync/vault/relay-ledger.test.ts`：第一次 `join` 從 0 算、之後出現的只算出現後的、同一小時照算、`wait`、持久化與舊版的帳；
  - `tests/sync/vault/relay-receipts.test.ts`：b 不簽收、帳滿，c 之後加入時用量是 0、經中繼收齊。
  - 變異測試：拿掉判斷後 4 項失敗。
