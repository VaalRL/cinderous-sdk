# 0068. 送出端的中繼預算改成按收件人記帳，用加密簽收單扣帳

- 狀態：**已接受（Accepted，2026-10-11）**。使用者 2026-10-11 要求「與我討論送出端的節流預算議題」，比較 A（不改）、B（宣告確認就縮短記帳期）、C（中繼回報收件人用量）、D（收件人加密簽收）後裁示：「採用 D 方案，預算跟確認功能分開出，寫進 ADR」；〈使用者裁示〉三題同日：「都照建議」。
- 日期：2026-10-11；2026-10-12 實作（v0.54.0，見〈實作紀錄〉）
- 對應：
  - ADR **0029**（塊數預算 `relayLimits`、`RELAY_QUOTA_SAFETY` 0.75）、**0058**（`VaultSendOptions.to`／`omitContentFor`）、**0028**（摘要補送）、**0026**（批次模式、P2P）。
  - ADR **0067**（收件確認後提早過期；本 ADR 是它 §5 的第二階段，**分開出版**）、**0066**（中繼推得出群組與上線狀態）、**0064**（中繼不可信任）。

## Context

### 現在的預算（ADR 0029，`coordinator.ts` 的 `#sendCounted`／`#relayQuotaWait`）

- 每一則經中繼送出的訊息都記帳：以小時為單位記塊數（一塊 48 KB），**記帳期＝保存期（7 天）**。
- 只有一本帳：同一則訊息會送給每一台裝置，所以「已送塊數」同時當作每位收件人的用量。
- 上限＝`chunksPerRecipient × 0.75`。CinderSync 的中繼（`maxFileMb` 17）約 654 塊，**約 31 MB／7 天**。
- 即時修改不會被擋但會記帳；批次模式（待送版本 ≥ 10）且走中繼時，超出預算就延後。

### 問題

1. **送出端看不到收件人領了沒有**，只能假設每一塊都在中繼上放滿 7 天。實際上收件人每小時都來領，信箱幾乎是空的。
2. 新裝置加入、P2P 連不上時，經中繼的補送一週只能約 31 MB，幾百 MB 的照片要好幾個月。
3. 一本帳：一台裝置很久沒上線，送給所有人的批次都被拖慢。
4. ADR 0067 讓中繼上的包處理完就提早過期，但送出端預算看不到這件事，好處到不了送出端。

### 為什麼選 D

| | 做法 | 為什麼不選／選 |
|---|---|---|
| A | 不改 | 問題 2、3 留著 |
| B | 中繼宣告了確認，就把記帳期縮短 | 送出端其實不知道收件人來領了沒有；收件人離線幾天，包會堆到超過配額，中繼淘汰最舊的而掉資料 |
| C | 中繼在 `OK` 回報收件人目前用量 | 任何能寫入的人都能查到某台裝置有沒有來收，公開中繼會把上線狀態洩漏給陌生人（比 ADR 0066 更糟）；而且要中繼支援 |
| **D** | **收件人以加密的同步訊息回簽收單，送出端按收件人記帳** | 中繼看不到、不新增中繼資料；任何中繼都能用（不需要 ADR 0067 的中繼擴充）；一台離線只拖慢送給它的份 |

## Decision

### 1. 按收件人記帳

- 帳本從「一本」改成「每位收件人一本」：每次經中繼送出，對**實際收到的每一台**（`to`／名單）各記一筆：`(序號, 塊數, 送出時間)`。
- 預算照舊是 `chunksPerRecipient × 0.75`，但各收件人分開算。
- 一筆帳在兩種情況下劃掉：
  1. **收到那位收件人的簽收單**涵蓋了它（§2）；
  2. **超過保存期**（現在的行為，當作沒有簽收時的上限）。
- 舊版裝置不會回簽收單 ⇒ 送給它的帳只會因為過期而劃掉，等於照舊，不會出錯。

### 2. 簽收單（新的同步訊息）

- 寄件端在每則經中繼的訊息標頭加一個**每台寄件裝置自己的遞增序號**（暫名 `rs`）。舊版收端驗證時會丟掉不認得的欄位，不受影響。
- 收件端在一則訊息的所有訊框都收齊、協調器**已經保存**結果之後（與 ADR 0067 §3 同一個時間點），記下「這位寄件人的哪些序號處理完了」。
- 收件端以新的訊息類型（暫名 `receipt`）回給**那一位寄件人**（`to: [寄件人]`）：內容是處理完的序號區間。
  - 走同一條加密的 kind 1060，中繼只看得到「又一顆包」。
  - 頻率：每輪同步結束時、或累積夠多時送一次；沒有新處理的就不送。
- 舊版收端遇到不認得的 `type` 會丟掉（`validateVaultMessage` 回 null），不會出錯。
- 寄件人不在信任名單、解不開、訊框沒收齊的訊息**不簽收**（與 ADR 0067 §3 相同）。

### 3. 某位收件人的帳滿了

- 只有送給**那位**收件人的份暫停：批次送出時用 `to` 把它排除，其他裝置照常送。
- 被排除的版本記進既有的待推送清單（`#pushes`，按裝置記），等它的帳空出來（收到簽收單或過期）再送；它上線時也可以走 P2P 或摘要（ADR 0028）補齊。

### 4. 和 ADR 0067 的關係

- 兩者**分開出版**，互不依賴：
  - ADR 0067（中繼提早過期）省的是中繼空間與重複下載，要升級中繼。
  - 本 ADR 省的是送出端的節流，只改客戶端，任何中繼都能用。
- 兩者一起用時，中繼上的實際佔用與送出端的帳大致一致。

### 5. 影響範圍

- 只改 SDK 的同步協調器（`@cinderous/client/sync/vault`），目前只有 CinderSync 用它，升級 SDK 即可。
- Cinder Coffice（只用排除路徑工具）、Cinder 即時通訊、四款遊戲：不用改。
- 中繼與錨點：不用改、不用重新部署。

## 使用者裁示（2026-10-11：「都照建議」）

| # | 題目 | 結果 |
|---|---|---|
| 1 | 收件人一直沒回簽收單（離線、舊版）時 | §3：只暫停送給它的份，其他照常；它的帳過期或回簽收單後再送 |
| 2 | 簽收單多久送一次 | 每輪同步結束送一次，或處理滿 500 則先送；沒有新處理就不送 |
| 3 | `status.relayQuota` 怎麼呈現 | 改成每位收件人一列（`used`／`budget`），CinderSync 的狀態畫面只顯示最滿的那位與它的裝置名 |

## 實作計畫（TDD）

1. 編解碼：`rs` 欄位與 `receipt` 訊息的驗證（區間格式、上限）；舊版收端丟掉不認得的類型。
2. 協調器：按收件人記帳、簽收扣帳、過期扣帳、帳滿只排除那一位。
3. 收件端：保存後才記序號、批次送簽收單、不簽收未信任與未收齊的訊息。
4. 整合測試（harness）：一台離線五天只拖慢送給它的份；新裝置加入走中繼的補送速度；混用舊版裝置時行為不變。
5. 把 2026-10-11 的測量腳本加上送出端節流的模型重跑，記進本 ADR。

## 補充裁示（2026-10-12）：簽收單順便更新「對方已收到」

使用者 2026-10-12 在 CinderSync 的待決清單裁示「收到修改的裝置在那一輪就回報收到了：要」，並選定「等本 ADR 的簽收單」，不採「每輪多送整份摘要」。
所以簽收單除了扣帳，也當作「對方已經有這些版本」的證據：寄件端記帳時順便記下每則訊息帶的版本（`[fileId, nodeId]`），
收到簽收單就把那些版本記成它已知的版本頭（與直連的送達確認相同，SDK ADR 0053 §G17）。`peerStatus(device).missing` 不必等它的摘要就會更新。

## 實作紀錄（2026-10-12，v0.54.0）

- **編解碼**（`codec.ts`）：每一種訊息可帶 `rs`（正整數，不合法整則丟掉）；新的 `receipt`：`{ from, for, ranges }`，區間遞增、不重疊、不相鄰、
  `lo ≥ 1`、最多 1000 段，本身不能帶 `rs`。舊版的 `validateVaultMessage` 重建訊息時不帶不認得的欄位、丟掉不認得的類型。
- **帳**（新模組 `relay-ledger.ts`，純資料結構）：每筆 `(rs, 塊數, 小時, to?, 版本?)`；每台的簽收區間；`used(device)`、`wait(device, frames, budget)`、
  `usage(devices)`（快取）、`prune`（過期的、每一台都簽收了的）、`compact`（超過 20,000 筆時最舊的併成沒有序號的廣播帳，只會多算）。
  持久化在協調器的 meta（`rb`，寫狀態時才轉 JSON）；舊版的 `relayUse` 轉成沒有序號的廣播帳（只會過期）。
- **收件人**：傳輸層新的選配方法 `recipients()`（`NostrVaultTransport` 給了 `deviceOf` 才有）。不知道收件人時照舊一本帳。
- **寄件**（`#sendCounted`）：簽收單以外每則都帶 `meta.rs` 遞增的序號（重開時跳過 1000，萬一上次沒存下也不重複）；記帳時 `to` 只在傳輸層照收件人送時才記。
- **簽收單不記帳**：它很小（一塊），收件人處理完照樣以 ADR 0067 的收件確認讓中繼提早清掉；若記進帳只會過期，每輪一份、七天下來會佔掉預算的一大塊。
- **批次模式**（`#buildNext` → `#quotaPlan`）：要送的對象裡帳滿的那幾台先排除（`to` 只送其他台），版本留在佇列、記成 `owed`；之後只送給還欠的那幾台
  （帳空出來、或直連送到為止）。全部都滿、或傳輸層不能照收件人送，就等（最早空出來的時間；簽收單來了會再推一次）。
  又有新的廣播需要時 `owed` 清掉；又有一台要時加進 `owed`。
- **收件**：處理完、和結果一起保存之後記下 `(寄件人, rs)`（`meta.rp`，跨重開）；20 秒內沒有新的就送（期間再處理的併進同一份），滿 500 則先送；
  只送給那位寄件人（`to`）。送不出去的放回去，下次連上再送；中繼都滿了或不收（`blocked`）時不送，恢復時送（不風暴）。
  `flushReceipts()` 讓排程同步的應用在一輪結束、斷線之前立刻送。`receipts: false`＝像舊版一樣不簽收。
- **寄件端收到簽收單**：`for` 不是自己就不理；劃掉 `from` 那一台的帳（只有它自己的帳，冒名劃不到別台）；簽收的訊息帶的版本記成它已知的版本頭。
- **`status.relayQuota`**：多 `devices`（每位收件人一列，最滿的在前），`used` 是最滿的那一位。
- **測試**：`relay-ledger.test.ts`（帳的每一條規則、持久化、上限）、`codec.test.ts`（`rs` 與 `receipt` 的驗證）、`relay-receipts.test.ts`
  （序號遞增、處理完才簽收、只送給寄件人、簽收劃帳、「對方已收到」不必等摘要、離線收到的上線後簽收、冒名與別人的簽收單、`flushReceipts`、
  c 離線時只停送給 c 的份而 b 經中繼收完超過一份預算、舊版不簽收、重開後帳與序號都在）；`relay-limits.test.ts` 原本的 FIFO 中繼情境改成「收件端不簽收」
  （行為不變），另加「收件端簽收：一天內送完（原本要超過 7 天）、還沒簽收的不超過預算」。
  **變異測試**：把 `recipients()` 改成永遠不知道（退回一本帳），`relay-receipts` 有 4 個測試失敗。
- **既有測試的調整**（行為依本 ADR 改變）：「收到修改的裝置什麼都不送」→ 只回一份簽收單（`peer-status`、`scheduled-sync`）；訊息數或種類的斷言排除 `receipt`
  （`checkpoint`、`history-sync`、`excludes`）；輕量成員自己寫的內容，完整成員簽收了就算確認收到、自動清掉（`sparse`，原本要等它的摘要）；
  同一個刪除版本因為摘要先到被索取而再送一次，改看刪除版本數（`sparse`；簽收單讓假網路的亂數抽取順序變了）。
- **已知（與本 ADR 無關）**：`property-p2p` 加大種子（起點 200、30 個）在種子 211 失敗，改動前的程式同樣失敗；預設種子數都通過。
- **2026-10-12 補（ADR 0073）**：帳原本放在協調器的 meta 裡，meta 每做完一件工作就整份轉 JSON，帳有幾千筆時大量同步是平方級（5,000 檔的初次同步是 1,000 檔的 19 倍）；改存在自己的鍵 `rb`、累積 500 筆變動才寫、停止時一定寫，舊的 `meta.rb` 啟動時搬過去。
- 第 5 項（量測）：見下方〈量測〉。

## 量測（2026-10-12，`npm run measure:relay-budget`，ADR 0073）

P2P 打不通（全部經中繼）、中繼每位收件人 1,440 塊／7 天、預算 0.75、每小時 120 則（CinderSync）、400 個 200 KB 的附件（約 78 MB，超過一份 7 天的預算）：

| 情境 | 舊（一本帳、不簽收；＝v0.53） | 新（每台一本帳＋簽收單） |
|---|---|---|
| A. 新裝置加入，收齊要多久 | 7.1 天 | **4 小時** |
| B. 筆電整段時間離線，手機收齊要多久 | 7.1 天 | **3 小時**（修掉隊頭阻塞之後；修之前也是 7.1 天） |

新版的時間是每小時 120 則的限速決定的（不再是 7 天的預算）。

## Consequences

- 好處：經中繼的批次同步不再被保守的 7 天假設卡住；一台離線不拖累別台；中繼不多知道任何事；不需要中繼支援。
- 代價：多一種同步訊息與每位收件人一本帳（狀態儲存變大，按名單人數成長）；簽收單本身也是中繼上的包（很小）。
- 不變：中繼的每收件人配額與淘汰；ADR 0066 的中繼資料外洩；舊版裝置的行為。
