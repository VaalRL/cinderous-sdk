# 0072. 自動檢查點可以由應用決定時機（`autoCheckpoint: 'app'`、`checkpoint({ minIntervalMs })`）

- 狀態：**已接受（Accepted，2026-10-12）**——使用者 2026-10-12 裁示（CinderSync ADR 0057：自動檢查點跟著同步頻率，「到期制」）；實作於 v0.55.0
- 日期：2026-10-12
- 對應：ADR **0063**（版本歷史、檢查點；補充 1：自動檢查點在同步告一段落時建立、最多每小時一個）；CinderSync ADR 0057

## Context
自動檢查點由協調器在「同步告一段落」時建立，最多每小時一個。CinderSync 的使用者覺得它和同步的時間對不上，決定改成「跟著同步頻率：同步完成之後、每個頻率最多一個」。
協調器不知道應用的同步頻率、也不知道哪一次是「同步完成」（排程同步的一輪是應用的概念），所以時機要交給應用。

另外，原本的節流是從上次**嘗試**算起：剛好在 Vault 沒變動時試過一次（沒建出來），接下來一整個小時就算有變動也不會建。

## 決策
1. 新選項 `autoCheckpoint?: 'idle' | 'app'`：
   - `'idle'`（預設，行為不變）：協調器在同步告一段落時建立，最多每小時一個。
   - `'app'`：協調器自己不建；應用在它認定的時間點呼叫 `checkpoint({ auto: true, minIntervalMs })`。
2. `checkpoint({ auto: true, minIntervalMs })`：離**上一個建立的**自動檢查點不滿 `minIntervalMs`（預設一小時）就回 `null`；和最新的檢查點相同（沒有變動）也回 `null`，不佔掉這一段。
3. `'idle'` 模式的節流改成：沒建出來的那一次嘗試 5 分鐘後就能再試；真正的間隔由「離上一個建立的」決定（`checkpoint` 裡先比時間，不滿就直接回，不比對整個 Vault）。
4. 還原之前的檢查點、命名檢查點不受影響。

## Alternatives Considered
- **協調器自己接一個 `intervalMs` 選項、照時間建**：協調器不知道「一輪同步完成」，照時間建一樣會和同步錯開。否決。
- **只改預設的節流、不給應用控制**：解決不了「跟著同步頻率」。否決。

## Consequences
- ＋ 應用可以讓檢查點和它的同步週期對齊；預設行為不變。
- ＋ 沒有變動的嘗試不再吃掉一整個小時。
- － `'app'` 模式下，應用不呼叫就沒有自動檢查點（文件寫明）。
- 驗證：`tests/sync/vault/checkpoint.test.ts`〈autoCheckpoint: 'app'…〉（協調器不自己建；從上一個自動檢查點算起、沒滿不建、沒變動不建也不佔掉；命名照常）與〈預設（'idle'）：沒有變動的那一次嘗試不再佔掉一整個小時〉。
