# 0056. 名單帶中繼清單（含備援），裝置之間自動共享

- 狀態：**已接受（Accepted，2026-10-05）**——使用者裁示「甲」（選項 C＋保守規則），實作於 v0.45.0
- 日期：2026-10-04（提議）；2026-10-05（裁示、實作）
- 對應：CinderSync ARCHITECTURE §5 **G11 第 1 部分**（外掛 ADR 0017：每台手動設同一組備援，以能力宣告的 `standby` 指紋偵測不一致）。
  第 2 部分（只訂閱、不寫入的中繼）已由 ADR 0054 解決。相關：本 repo ADR 0028（名單、合併、撤銷）、0035 §G9（自簽能力宣告）、0041（備援）、
  0052（中繼搬家通知：只替換、不新增、新網址測得通才換）。

## Context

外掛希望名單（`VaultMembership`／`NostrRosterSync`）帶**簽章的中繼清單（含備援）**，配對時一起交付、之後自動共享，不必每台手動設同一組備援。

這**改變信任模型**：今天每台的中繼清單是本機設定，名單只決定「誰是成員」。把中繼清單放進名單，等於讓**任何一位成員都能改其他成員要連哪些中繼**：

- 被盜或惡意的成員可以把大家導到它控制的中繼（看到誰在何時同步、丟掉或延遲訊息、做流量分析；內容仍是端到端加密，讀不到）；
- 把備援換成不存在的網址，等於讓「主中繼滿了時的補發」失效；
- 與 ADR 0052 的搬家通知不同：搬家通知「只替換清單裡已有的舊網址、新網址測得通才換」，是收方自己決定；名單合併是自動的。

所以 SDK 不自行決定，列出選項與建議。

## 選項

| 選項 | 誰能改 | 合併規則 | 風險 |
|---|---|---|---|
| **A. 名單欄位、任何成員都能改、最後寫入者贏** | 任何成員 | LWW（簽章時間） | 最高：一台被盜就能改全部 |
| **B. 名單欄位、只有建立者（或指定的管理裝置）能改** | 管理裝置 | 只採用管理裝置簽的 | 名單目前沒有角色；要加「管理者」概念與轉移流程 |
| **C. 每台自簽的「建議清單」（能力宣告的延伸），收方決定** | 各自 | 不合併；收方看到「別台建議 X」，經使用者同意或依規則採用 | 最低；要多一步確認（或規則：只自動採用**備援**、只**新增**不移除、新網址 NIP-11 測得通才加） |
| D. 不做 | — | — | 維持手動＋指紋提示（外掛現況） |

## 建議（提議時）

**C 加上保守的自動規則**：

1. 每台在自簽的能力宣告裡帶**完整的備援清單**（今天只帶指紋），不新增名單欄位、不改合併規則；
2. 收方的 SDK 函式 `planStandbyAdoption(own, declared)` 只建議：**只新增備援、不移除、不碰主清單**、新網址以 `probeRelayEndpoint`（ADR 0052）測得通才算；
   預設**要使用者確認**（外掛顯示「B 用了備援 X，要加入嗎？」），應用可以選擇自動採用；
3. 配對時交付的中繼清單（ADR 0028）可以順便帶上備援（只在配對當下、由使用者確認的那台交出，與今天的主清單相同）。

理由：攻擊者最多讓別台「多連一座只讀／補發用的中繼」（多一點流量分析的面），拿不走主中繼、也不能讓補發失效（只新增不移除）；不必在名單引入角色。

## 待使用者裁示的問題（提議時）

1. 接受「任何成員都能影響別台的中繼設定」嗎？若不接受，選 C（建議）或 D；若接受，選 A 或 B。
2. C 的採用要**一律確認**，還是允許外掛自動採用（只新增備援、測得通）？
3. 移除備援要不要也能共享（風險：讓補發失效）？建議不要。
4. 配對時是否一併交付備援清單？

## 使用者裁示（2026-10-05）：甲

「甲」＝上面的建議版本：每台在自己簽的宣告裡帶備援清單；收方只「新增備援」、不刪除；新網址要測得通才算；**預設要使用者確認**才加入；
移除備援不共享；配對時一併交付備援清單。各題定案：

| # | 問題 | 定案 |
|---|---|---|
| 1 | 接受「任何成員都能影響別台的中繼設定」嗎？ | **不接受自動影響**：選 C。別台的宣告只會變成「建議」，要這台的使用者確認才進設定；不採 A／B，名單不引入角色、不改合併規則 |
| 2 | 一律確認，還是允許自動採用？ | **預設要使用者確認**。SDK **不提供**自動採用的 API（`StandbySuggestions` 只列建議、測試、記住忽略；加入由應用做）；CinderSync 一律確認。ADR 對「應用可以選擇自動採用」沒有定義條件，依最保守的做法不做——要自動採用另開 ADR |
| 3 | 移除備援要不要共享？ | **不共享**。收方只會被建議**新增**；別台拿掉某座，這台照舊保留，也不會出現「建議移除」 |
| 4 | 配對時是否一併交付？ | **是，作為建議**：歡迎訊息帶邀請方的備援清單（`PairingResult.standby`），新裝置同樣要使用者確認才加入（與主清單不同：主清單照 ADR 0028 直接交付） |

提議沒寫清楚、依最保守做法定案的細節：

- **「能力宣告裡」放不下網址**：`caps` 的值只能是 ≤ 24 字的字串／數字／布林、正規化 JSON ≤ 160 字；舊版（≤ v0.44）解析時遇到不合規的 `caps`
  會**整份名單不收**。所以備援清單放在名單上與 `caps` 並列的新欄位 `standby`（同樣是裝置自己簽、領域分隔的簽章 `standby`，同一台取 `at` 較晚的），
  是能力宣告的延伸而不是 `caps` 裡的一個鍵；舊版略過未知欄位、照常合併（轉送時丟掉這一欄，新版以聯集保留，不會來回震盪）。
- **網址規則**：只分享公開的 `wss://`——不帶帳密與片段、不是本機或私有／保留網段（127/8、10/8、172.16/12、192.168/16、100.64/10、169.254/16、0/8、多播、
  `::1`、`::` 開頭（含 IPv4 對應）、fc00::/7、fe80::/10）、不是區網網域（`localhost`、`.local`、`.lan`、`.home.arpa`、`.internal` 等）或單一標籤主機；
  ≤ 200 字；每台最多 4 座（前 4 座分享得出去的）。不合規的留在那台自己的設定，只是不分享。
- **測得通**：由應用給 `probe`（建議 `probeRelayEndpoint`，讀 NIP-11；也可以用 WebSocket 試連）。建議帶測試狀態 `pending`／`reachable`／`unreachable`，
  只有 `reachable` 的應該讓使用者採用；測不通的隔 1 小時（`refresh()`）才重測。
- **只收有效成員的宣告**：`declaredStandbys()` 只列目前有效的其他成員；被撤銷的裝置的宣告在合併時丟掉；配對交來的建議以 `isMember` 再過濾一次。
- **不合規或簽章不對的宣告**：只丟那一筆，名單其他部分照收（較新的版本若放寬規則，不能讓舊版整份不收）。
- **忽略**：被忽略的網址由應用存在本機（不同步），建構 `StandbySuggestions` 時傳回；之後誰再宣告都不建議。
- **歡迎訊息的大小**：名單裡的備援宣告只帶邀請方自己的一筆（其他成員的之後經名單同步補上），歡迎訊息仍在 65,535 字以內（測試釘住）。

## 實作（v0.45.0）

全部在 `./pairing`（零執行期相依，不拉進連線池或同步零件）：

- `VaultRosterData.standby?: RosterStandby[]`（`{ pubkey, urls, at, sig }`）；`membership.declareStandby(urls)`（只宣告分享得出去的、正規化、去重、最多 4 座；
  空陣列＝「沒有備援」也會宣告；內容沒變回 false、不重簽；有變發 `change`，`reason: 'caps'`——不新增 reason，免得窮舉 `switch` 的使用方型別變動）；
  `membership.standbyOf(pubkey)`、`membership.declaredStandbys()`（其他有效成員，`{ pubkey, deviceId, label, urls, at }`）。
- `normalizeStandbyUrl`／`isShareableStandbyUrl`／`shareableStandbyUrls`；常數 `ROSTER_STANDBY_MAX_URLS`（4）、`ROSTER_STANDBY_MAX_URL_LENGTH`（200）。
- `planStandbyAdoption({ own, declared, offers?, ignored?, isMember? })`：純邏輯，回「建議新增」的 `{ url, sources }`（來源 `{ pubkey, deviceId, label, via: 'roster' | 'pairing' }`），
  自己已經有的（主清單＋備援，比對不分主機大小寫與結尾斜線）、被忽略的、不合規的不列。
- `StandbySuggestions({ probe, ignored?, retryMs?, now? })`：`update({ own, declared, isMember? })`、`offer(source, urls)`（配對交來的）、`list()`（帶 `probe` 狀態與 `checkedAt`）、
  `ignore(url)`／`ignored()`、`onChange(listener)`、`refresh()`。新網址自動測試，每個網址同時只測一次。
- 配對：`PairingSessionOptions.standby`（預設＝這台在名單上宣告的）；歡迎訊息多一個 `standby` 欄位（舊版新裝置略過）；`PairingResult.standby`
  （新裝置：邀請方交來的建議；成員：自己交出去的；舊版成員＝空陣列）。

應用的接法（CinderSync）：啟動與備援清單改變時 `declareStandby(standbyRelayUrls)`；名單一變就 `suggestions.update({ own: [...relayUrls, ...standbyRelayUrls], declared: membership.declaredStandbys(), isMember })`；
配對完成時 `suggestions.offer(peer, result.standby)`；設定頁列出 `list()`，「加入」走既有的備援清單流程（驗證、去重、與主清單互斥），「忽略」呼叫 `ignore` 並存 `ignored()`。

## 安全性

- 攻擊者（被盜或惡意的成員）最多能讓別台的使用者**看到一則建議**；使用者按了「加入」，也只是多連一座只讀／補發用的中繼（多一點流量分析的面，內容仍端到端加密）。
  拿不走主中繼、不能讓補發失效（不共享移除）、不能替別台宣告（簽章綁公鑰）、不能把大家導到本機或區網位址（網址規則）。
- 網址規則只看網址本身：公開網域解析到私有位址（DNS rebinding）擋不了；但採用前要使用者確認，而且備援只在主中繼滿了或不收時才寫。
- 宣告的網址是秘密時（私人路徑），只在名單成員之間以 NIP-59 加密傳遞，與配對交付的主清單相同；應用顯示時應遮蔽（CinderSync 的 `maskRelayUrl`）。

reason；`declaredStandbys` 只列有效的其他成員、撤銷後丟掉；後宣告的蓋過先前的；🔴 竄改與冒名的那一筆丟掉；沒有 `standby` 的舊名單照收、不震盪；持久化；
名單同步送得到；32 台塞滿仍在中繼單顆上限內（1060、1059 都試）；`planStandbyAdoption` 的排除與來源合併；`StandbySuggestions` 的測試狀態、只測一次、忽略、

## Consequences

- ＋ 名單多一個選用欄位、合併規則不變；舊版裝置不受影響（解析時略過 `standby`，轉送時丟掉、新版以聯集保留）。
- ＋ 外掛可以從「提示不一致」改成「一鍵加入」（使用者確認）。
- － 仍不是「設一次、全部跟上」：每台都要按一次「加入」；移除備援要每台各自做。
- － 名單變大：32 台都塞滿 4 座 200 字的備援，名單約多 30 KB；名單事件仍在中繼單顆上限 262,144 bytes 內（測試釘住）。
- － 分享的網址以本機／私有網段的字面規則過濾，擋不了 DNS rebinding（見安全性）。
