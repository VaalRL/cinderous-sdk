# 0133. NIP-86 管理 API 的補強：綁對外網址、先擋人再收內容、存檔不再是死路

- 狀態：**已接受（Accepted，2026-11-11）**
- 日期：2026-11-11
- 對應：SDK ADR 0132（本文補它）；Cinderous ADR-0261、0047

## Context

v0.88.0（ADR 0132）發版當天做了一次獨立審查。沒有找到能讓外人繞過授權的洞，但找到幾項與 ADR 0132 寫的不變式不符、或會讓站方把自己鎖死的行為，全部以測試重現過：

1. **簽章綁的主機是對方說的**。伺服器拿 `X-Forwarded-Host`／`Host` 標頭組出網址去比對 `u`，而這兩個標頭都是送請求的人寫的。同一把運維金鑰管兩座站時，看得到甲站請求的人（例如替甲站終結 TLS 的託管方）可以在 60 秒內把同一個動作重送到乙站。ADR 0132 只把「同一座站 60 秒內重送」列為殘餘風險。
2. **存過的名冊沒有出口**。名冊存進資料庫之後，環境變數 `ALLOWED_PUBKEYS` 被悄悄忽略；再把 `ROSTER_ADMIN_PUBKEY` 拿掉，就沒有任何管道能改成員，只能手動改資料庫。
3. **名冊的 `updatedAt` 沒有範圍檢查**。誤用毫秒的名冊會被接受，之後所有以秒為單位的正常名冊都被當成「舊的」。
4. **成員的 pubkey 沒有驗格式**。npub、大寫 hex 或亂字會被放進白名單，而白名單以小寫 hex 比對——那個人永遠寫不進，整份名冊都這樣就等於鎖站，繞過了「沒有在世成員就拒絕」。
5. **讀回存檔時沒有驗結構**。`allowed: "abc"` 會被逐字拆成三個成員；空的 `allowedKinds` 讓整站拒收；少了 `updatedAt` 讓舊名冊重新被接受。
6. **沒授權的請求也替他收內容**。任何帶對 `Content-Type` 的 `POST` 都會被緩衝到 1 MiB 才驗授權，超過上限後也沒有切斷連線。
7. **先套用、後存檔**。存檔拋錯時記憶體已經換了名單；而那個例外出現在 `end` 事件的回呼裡，會讓整個程序結束，重開後載回舊名冊——被移除的人又寫得進。

## Decision

1. **新環境變數 `NIP86_PUBLIC_URL`**（本站對外的 `http(s)://` 網址）。設了就**只認簽給它的請求**（有無結尾斜線視為相同，協定要一樣），不看任何標頭；寫錯就拒絕啟動。沒設時照舊以 `Host` 標頭比對，啟動時警告。
   - **不再信任 `X-Forwarded-Host`**。反向代理後面的站要設 `NIP86_PUBLIC_URL`。
2. **存過的名冊記下是哪一把名冊金鑰簽的**（`roster.admin`）。重開時 `ROSTER_ADMIN_PUBKEY` 沒設、或與它不同，那份名冊就不生效，成員回到 `ALLOWED_PUBKEYS`，並警告。
   - 名冊金鑰沒變時，名冊仍然蓋過 `ALLOWED_PUBKEYS`（ADR 0132 §8 不變），但兩者不同時啟動會警告；`ALLOWED_KINDS` 同理。
   - v0.88.0 存的名冊沒有 `admin`，視為與目前的名冊金鑰相符。
3. **`cinder_applyroster` 多兩項檢查**（在中繼這一側，不改 `verifyOrgRoster`——那是客戶端也在用的協定函式）：
   - `updatedAt` 必須是非負整數，且不超過現在一天以上（客戶端為了遞增會 +1，留餘裕）。
   - 每個在世成員的 pubkey 必須是 64 個小寫 hex，否則整份拒絕。
4. **讀回存檔一律經 `parseNip86State`**：任何一格結構不對就整份不用、照環境變數開，並警告。
5. **先擋人、再收內容**：新的 `httpAuthSigner`（只驗簽章與時間窗）與 `nip86Precheck`（簽署者是運維金鑰）。沒過就回 401 並切斷連線，一個位元組都不緩衝；`Content-Length` 超過上限直接 413；超過上限或被拒之後切斷連線。完整授權（綁網址、方法、內容）仍在收完內容後由 `verifyHttpAuth` 做。
6. **先存檔、存成功才生效**。存不進去就回錯誤、什麼都不套用；請求處理另包一層，例外回 500，不讓程序結束。

## 理由

- 伺服器不知道自己對外叫什麼，這件事只能由站方告訴它。預設不強制是因為單機直連、單一金鑰單一站的情境不受影響，而且強制會讓既有的啟動方式全部失效；改為啟動時明講。
- 「存檔蓋過環境變數」是為了不讓重開把名冊丟掉，不是為了讓站方失去控制權。把名冊綁在名冊金鑰上，站方拿掉那把金鑰就是明確的「不再用名冊」。
- 第 3 項放在中繼而不是 `verifyOrgRoster`：客戶端對名冊的接受條件是另一回事，收緊它會影響既有安裝。

## Alternatives Considered

- **`NIP86_PUBLIC_URL` 必填**：最乾淨，但測試與本機試用（埠號由系統分配）都得先知道網址。改為沒設就警告。
- **防重放表**（記下 60 秒內用過的事件 id）：能擋同站重送，但方法都是冪等或後蓋前，ADR 0132 已接受這項殘餘風險；跨站重送用第 1 項解。
- **名冊移除某人時切斷他現有的連線**：見殘餘風險。

## Consequences

- 行為改變（都只影響開了 NIP-86 的站，而 v0.88.0 才發布一天）：
  - 反向代理後面、靠 `X-Forwarded-Host` 才對得上網址的站，要設 `NIP86_PUBLIC_URL` 才能繼續用管理 API。
  - 誤用毫秒的名冊、成員 pubkey 格式不對的名冊現在會被拒絕。
  - 拿掉或換掉 `ROSTER_ADMIN_PUBKEY` 之後，存過的名冊不再生效。
- 沒開 NIP-86 的站不受影響。Worker 不受影響（它沒有這個 API）。
- 殘餘風險：
  - 沒設 `NIP86_PUBLIC_URL` 時，跨站重送仍可能（啟動時警告）。
  - 同一座站 60 秒內可重送同一個請求（ADR 0132，未變）。
  - **名冊移除某人後，他已連著的連線不會被切斷**：寫入立刻被擋，但他已開的訂閱在斷線前仍收得到投遞給他的事件。要切得靠宿主找出該 pubkey 的連線，本版未做。→ **已做：[ADR 0136](0136-roster-removal-closes-connections.md)**（被移除者已認證的連線以 4003 關閉、訂閱立刻停）。
  - 能直接改資料庫檔的人仍能換掉名冊（那已經是主機層的權限）。
