# 0030. 多人星狀會話：`./star` 子路徑、Host 解密再轉送的成對雙棘輪、邀請／踢出、Host 序號、每成員背壓、後量子開銷的應用層緩解

- Status: Accepted
- Date: 2026-09-29
- 相關：
  - ADR 0021〈後續〉#6（Cinder Coffice G4）、#10（PQ header 成本）
  - ADR 0009（`PeerNode`、中繼軌 kind 20079）、0010（`secureChannel`、雙棘輪）、0014（引擎協商：扇出不用雙棘輪）、0015／0026（`FileTransfer`／`StreamTransfer`）、0028（配對 URI 的風格）
  - Cinder Coffice PRD §2.3（主機星狀拓撲＋成對雙重棘輪）、ARCHITECTURE §3.2、§5 G4

## Context

Cinder Coffice 要 3 人以上同時編輯同一份筆記（Yjs 更新、游標、邊欄聊天、蟲洞投影）。SDK 只有成對的 `connectPeer`＋`secureChannel`；外掛要自己管 N 條通道、轉送、成員進出（G4）。外掛 PRD 已拍板拓撲：**Host 對每位 Guest 各持一條成對的雙棘輪通道；A 的更新由 Host 解密後再經 Host–B 通道加密轉送；Host 看得到所有內容，是信任前提。**

限制：

- 不改雙棘輪的線路格式（ADR 0010；ADR 0021〈後續〉#10 的 2,314 B header 也不動）。〔v0.28 起後量子線路格式已由 [ADR 0033](0033-pq-ratchet-header-cost.md) 改版，星狀會話不需任何改動，見 §6 的更新表。〕
- 平台無關、零 Node（Obsidian 行動版）。
- 中繼軌（kind 20079）每框都是一個中繼事件；SDK 中繼每把公鑰每分鐘 120 則（NIP-11 `cinder_max_events_per_minute`），Host 的轉送全部算在 Host 的公鑰上。
- 慢成員（手機在地下室）不能拖垮其他人。

## Decision

### §1 拓撲與信任模型：Host 看得到一切，名稱與文件都寫明

- 每位成員只連 Host，一條成對的 `secureChannel`；成員之間沒有直接的通道。成員送 `SEND`，Host **解密**、蓋上 Host 序號與寄件人、再以其他每位成員的通道**重新加密**成 `DELIVER`。
- **Host 能讀、能改、能捏造**經過它的任何內容，也能對不同成員送不同東西（分岔）。成員能確認的只有「這是 Host 說的」；`from` 是「Host 宣稱的寄件人」。只讓信任的人當 Host。
- API 名稱刻意不用 group／e2ee 字樣：`StarHost`、`StarMember`、`StarMessage.from` 的文件註解、子路徑 `index.ts` 開頭、README 都寫「這不是端到端群組加密」。
- 成員對其他成員**沒有**任何端到端保證；成員對 Host 的保證就是雙棘輪通道的保證（前向保密、外洩後自癒、後量子步進）。中繼只看得到密文（整合測試驗證就算拆開 NIP-59 也找不到明文）。
- 為什麼不做真正的群組加密（例如 MLS）：見 §9。

### §2 邀請：沿用配對 URI 風格，秘密只在加密通道裡送

```
cinderous-star:1.<base64url(核心 53 bytes)>.<中繼>[,<中繼>,<中繼>]
核心：[旗標 1（保留，必須 0）][Host 身分公鑰 32][邀請秘密 16][到期時間 u32 秒]
```

- **為什麼不用 NIP-59 信令直接「邀請某人」**：加入者本來就要先知道 Host 是誰、去哪座中繼找它，一定有一段帶外資訊（QR、私訊、複製連結）。所以沿用 ADR 0028 的字串風格，一段帶齊。中繼網址的壓縮與還原與配對共用（`compactRelayUrl`／新匯出的 `expandRelayToken`）。
- 加入流程：成員 `connectPeer(Host)` → `secureChannel` 握手（身分已由 DTLS 指紋經 NIP-59 或每框 NIP-59 認證）→ 在加密通道裡送 `JOIN{秘密, 名稱}`。**秘密從不以明文上網路**。
- Host 只存秘密的 SHA-256；邀請字串只在 `createInvite` 回傳一次，`invites()` 不含字串（記錄或 UI 外洩不了可用的秘密）。成員端送出 JOIN 後把自己那份秘密清掉，也不把邀請留在會話裡。每張邀請：到期（預設 10 分鐘，上限 24 小時）、可用次數（預設 1；上限＝成員上限）、可撤銷（`revokeInvite(id)`）、可綁定公鑰（`forPubkey`：別人拿到字串也進不來）。到期以 Host 的時鐘為準；成員端只做提早失敗。
- 順序：**先驗邀請（不扣次數）** → 會話已結束／被封鎖／成員已滿 → **扣次數** → 問 App（`approveJoin`，預設 2 分鐘沒回答＝拒絕）。兩個人同時拿一次性邀請，只有一個能進；App 拒絕時次數不退；成員已滿不耗邀請。
- 拒絕原因（`invalid-invite`／`expired`／`revoked`／`used`／`full`／`banned`／`denied`／`closed`）：沒有有效邀請的人只會拿到邀請相關的四種，看不到人數滿了沒、自己有沒有被封鎖；持有有效邀請的人才拿到其餘原因。綁定公鑰不符回 `invalid-invite`，不透露「這張邀請存在但不是給你的」。
- 邀請裡的中繼只收 `wss://`（本機測試可 `ws://localhost`／`127.0.0.1`），不收帶帳號（`@`）的網址。SDK **不會**自己連到邀請裡的中繼：`StarMember.join` 用 App 給的 `PeerNode`，App 要讓它的連線池涵蓋 `parseStarInvite(uri).relays`。
- 邀請簿只在 Host 記憶體；Host 重開＝所有邀請失效（會話本身也結束了）。
- `host.listen(node)` 會替每條連進來的 PeerChannel 做雙棘輪握手。同一個 `PeerNode` 還有別的用途（例如 Vault 同步的 `peerNodeLink`）時**一定要給 `accept`**，否則別人的通道會被搶去握手、逾時後被關掉；或者 App 自己握手後交給 `host.attach(secure)`。

### §3 線路格式（跑在雙棘輪裡面）

```
封包：[0xC5][版本 1][旗標 bit0=有序號][lseq u32][ack u32] 紀錄*
紀錄：[類型 u8][長度 u32][內容]
```

| 類型 | 方向 | 內容 |
|---|---|---|
| JOIN 1 | 成員→Host | 秘密 16 ＋ 名稱（≤ 64 B UTF-8，未經認證） |
| WELCOME 2 | Host→成員 | JSON：會話 id、Host、你的公鑰、`next`（你會收到的第一個序號）、名單、酬載上限 |
| REJECT 3 | Host→成員 | JSON：原因 |
| LEAVE 4 | 成員→Host | 空 |
| END 5 | Host→成員 | JSON：原因（`kicked`、`host-closed`、`overflow`、`rate-limit`、`replaced`、`protocol`） |
| SEND 6 | 成員→Host | 旗標（volatile／echo／單播）、topic、收件人（最多 64）、酬載——**沒有寄件人欄位** |
| DELIVER 7 | Host→成員 | Host 序號 u64、寄件人 32、旗標、topic、酬載 |
| ROSTER 8 | Host→成員 | Host 序號、joined／left、公鑰、原因、名稱 |

- 標記 0xC5 與 `FileTransfer`（0xCF）、`StreamTransfer`（0xCB）不同：同一條成對通道可以同時跑星狀會話與串流（`channelOf(pubkey)`／`member.channel`），互相略過對方的封包。
- 一個封包可以裝多筆紀錄：這就是 §6 的批次。
- 解析器對任何輸入都不拋例外（固定種子 3,000 筆隨機位元組的模糊測試）；格式錯誤＝協定錯誤，Host 端請該成員離開（`protocol`），成員端視為 Host 失聯（`host-lost(protocol)`）。

### §4 順序保證：Host 序號＝全序、與因果一致；不保證跨 Host

- Host 對每一則轉送的訊息與名單事件配一個**嚴格遞增**的序號（同一個會話內；可能跳號——單播與別人的 echo 不會送到你）。
- **全序**：同一個序號在每個人那裡是同一則（同寄件人、同內容）；每個人收到的序號嚴格遞增、無重複。
- **因果**：鏈路是 FIFO（P2P 軌 DataChannel 本身有序；中繼軌由 §5 的 lseq 重排），所以成員送出訊息時已經看過的每一則，序號都比它小——Host 序號與「經 Host 的 happens-before」一致。
- **完整**：成員在線期間（從 WELCOME 的 `next` 起，到離開為止），每一則廣播（別人送的）都會收到；中途失聯（溢出、逾時、失步）就結束，不會「少幾則但還在線」。唯一的例外：某位成員因灌量被請離開（`left(rate-limit)`，§5）時，它還沒送出的訊息從所有佇列撤掉，其他人可能只收到它的一部分——收到 `left(rate-limit)` 的 App 應該跟 Host 重新同步（Yjs：交換 state vector）。
- Yjs：更新本身可交換，照收到的順序套即可；Host 序號讓「快照＋之後的更新」這種模式有明確的切點——Host 在 `joined` 事件裡單播主文件狀態，之後的更新序號都比快照大（整合測試 `crdt.test.ts`）。
- 不保證：跨 Host 會話的順序（新會話從 1 起算）、Host 自己不誠實時的一致性（見 §1）。

### §5 背壓、節流、可靠性

- **每成員佇列**（預設 8 MiB／4,096 筆，可調）：一次只有一個封包在途，佇列裡的東西在下一包一起送（慢的鏈路自然合成更大的批次）。滿了先丟佇列裡最舊的 `volatile`（游標、在線狀態）；本筆也是 volatile 就默默丟；還是放不下，就**請這位成員離開**（`END overflow`），它重新加入再用快照同步。不丟非 volatile 的：丟一則 Yjs 更新會讓那個人永遠不收斂，寧可讓它重來。
- **成員端**：佇列滿了 `send` 丟 `StarMemberError('backpressure')`（volatile 則默默丟）；`bufferedAmount` 讓 App 自己節流。
- **灌量的人負責，不是慢的人**：一個人灌爆會連帶把別人的佇列灌滿。兩道防線：
  1. 每成員的進站 token bucket（預設 200 則／秒、突發 2,000 則、1 MiB／秒、突發 2 MiB——突發不超過佇列上限的 1/4），超過就 `rate-limit`。
  2. 佇列記下每筆的寄件人。某位收件人的佇列滿了，先看是誰塞的：**單一成員佔了佇列上限的一半以上**，就請那位寄件人離開（`rate-limit`），並把它還沒送出的從所有佇列撤掉，收件人留下；沒有這樣的寄件人（大家都正常送、是收件人自己慢）才請收件人離開（`overflow`）。Host 自己送的不算在任何成員頭上。
- **成員上限**預設 16、最多 64（Host 對每位成員各加密一次，上行與 CPU 隨人數線性增加）；單則酬載預設 1 MiB、最多 16 MiB。
- **還沒加入的連線**（任何人都能連上 Host 並完成雙棘輪握手，不需要邀請）：等待名額（含握手中）最多 32，滿了就踢掉最舊一條還沒送 JOIN 的（換金鑰佔名額擋不住真的要加入的人）；連上後 10 秒內沒送 JOIN 就關；加入前單包上限 1 KB、亂序暫存最多 4 包；不算進中繼事件預算的分母。每包最多 4,096 筆紀錄、除了 LEAVE 不能有空紀錄；亂序暫存存原始位元組、輪到才解碼（不為暫存的東西建物件）。
- **中繼軌節流**：每個封包（含心跳與確認）是一個中繼事件（中繼軌的批次上限 44,000 B＝一框）。每條中繼鏈路的最小間隔＝60,000 ms × 走中繼的鏈路數 ÷ 每分鐘預算（預設 100，低於 SDK 中繼的 120；`starRelayEventsPerMinute(nip11)` 取 NIP-11 宣告值 × 0.8、多座取最小）。例：預算 96、Host 有 8 位走中繼的成員 → 每位每 5 秒一包；期間的更新全部合在那一包裡。同一個值也應該給 Host 的 `PeerNode` 當 `relayFramesPerMinute`（它是整個身分的硬上限）。心跳也守這個間隔（心跳間隔＝max(設定值, 節流間隔)，逾時至少三個心跳）；所以走中繼的成員越多，Host 發現「成員不見了」越慢（預算 96、64 人全走中繼時每人 40 秒一包、逾時 2 分鐘）。建議 App 依預算限制走中繼的人數。
- **可靠性**：每個有序號的封包帶 lseq，對方的 ack 搭在每個封包的 header；確認了還沒送的號碼＝協定錯誤。P2P 軌（可靠有序）不留底、不重送，跳號＝協定錯誤。中繼軌（kind 20079 會亂序、會掉）：收端依 lseq 重排（最多 256 包／16 MiB，缺號超過 30 秒＝失步），缺號時回一個單獨的確認讓送端快速重送，送端 4 秒沒被確認就重送（最多 6 次，之後＝失步），未確認最多 128 包（到了就先不送新資料，背壓回到佇列）。重複的封包依 lseq 丟掉（雙棘輪本身也擋重放）。
- **心跳**：P2P 5 秒／逾時 20 秒，中繼 15 秒／逾時 60 秒；沒東西送才送空封包（帶 ack）。

### §6 後量子 header 成本：不改線路格式，應用層批次攤掉

雙棘輪後量子模式每則訊息固定帶 2,314 B header（ADR 0021〈後續〉#10）。本 ADR **不改線路格式**（「只在 DH 步進時附 KEM 欄位」仍是 #10 的評估項目），改在應用層緩解：

- **批次**：批次視窗內（P2P 16 ms、中繼 250 ms，可調）進佇列的所有紀錄合成一個封包＝一則棘輪訊息，header 只付一次。背壓時批次自動變大。
- **Host 端節流**：中繼軌依 §5 的預算拉開間隔，期間的更新全部合併。
- **App 端**：游標用 `volatile`、自己限 10 Hz；Yjs 可以在送出前先 `mergeUpdates`。

實測（`tests/star/integration.test.ts`，真的 `secureChannel`；位元組數是 PeerChannel 上的一則訊息，不含 P2P 的 17 B 分框 header）：

| 情境 | 後量子 | 古典 |
|---|---|---|
| 成員送一則 20 B 更新（成員→Host） | 2,395 B | 122 B |
| Host 轉送一則 20 B 更新（Host→**每位**成員） | 2,434 B | 161 B |
| 同一批次視窗內 50 則 20 B 更新（成員→Host，1 則訊息） | 3,767 B（每則 ≈ 75 B） | 1,494 B（每則 ≈ 30 B） |
| 經中繼：一則 20 B 更新的 kind 20079 事件（NIP-59 兩層＋base64） | 8,702 B | 2,214 B |
| 經中繼：50 則合併 | 14,162 B（每則 ≈ 283 B） | 5,970 B |

星狀下 Host 的上行＝每則 × 成員數：8 位成員時一則不合併的按鍵是 8 × 2,434 ≈ 19.5 KB；合併後主要成本變成酬載本身。

**v0.28 更新（[ADR 0033](0033-pq-ratchet-header-cost.md)，後量子線路格式 v2）**：同一組量測（`tests/star/integration.test.ts`）：

| 情境 | 後量子 v0.27 | 後量子 v0.28 | 古典 |
|---|---|---|---|
| 成員送一則 20 B 更新（成員→Host） | 2,395 B | **131 B** | 122 B |
| Host 轉送一則 20 B 更新（Host→**每位**成員） | 2,434 B | **170 B** | 161 B |
| 同一批次視窗內 50 則 20 B 更新（1 則訊息） | 3,767 B | **1,503 B** | 1,494 B |
| 經中繼：一則 20 B 更新的 kind 20079 事件 | 8,702 B | **2,214 B** | 2,214 B |
| 經中繼：50 則合併 | 14,162 B | **5,970 B** | 5,970 B |

8 位成員時一則不合併的按鍵，Host 上行 8 × 170 ≈ 1.4 KB。每方每 50 則仍會有一則多帶 1.1–1.2 KB 的 ML-KEM 密文或公鑰（輪次），攤提後約每則 +45 B。批次仍然有用（省的是每則的 AEAD 與分框開銷），但已不再是後量子模式的必要緩解。

### §7 踢出、離開、Host 斷線

- `kick(pubkey)`：丟掉還沒送給它的，只送 `END kicked`，送完（中繼軌等到被確認，或 2 秒）就關它的通道；Host 從此不處理它送的任何東西（成員表先移除，鏈路再關）。預設加進封鎖名單（這個會話內這把公鑰不能再用別的邀請回來；`unban` 解除），**並撤銷它用來加入的那張邀請**（多次邀請不能讓它換一把新金鑰再回來；`revokeInvite: false` 可關）。封鎖只認公鑰：拿到別張有效邀請的新金鑰擋不住。**成對通道之下，踢一個人不影響其他人的通道，不必重新協商任何金鑰**——它本來就沒有別人的金鑰。但它**已經收到的內容無法收回**。
- `leave()`：送 `LEAVE`、送完就關；其他人收到 `left(left)`。
- 同一把公鑰再加入：舊連線 `END replaced`，其他人看到 `left(replaced)` 再 `joined`。
- Host 結束（`close()`）：每位成員 `END host-closed`、所有邀請作廢。
- **Host 斷線**：成員收到 `host-lost`（`closed`＝通道關閉；`timeout`＝心跳逾時，中繼軌沒有關閉通知只能靠它；`desync`；`protocol`）。**不自動選新 Host**：新 Host 會看到所有內容（§1），不能由程式自動替使用者決定信任誰；成員之間也沒有通道可以協調選舉，要做就得先建 N×N 的通道並對「誰是新 Host」取得共識，不是「容易且安全」。App 可以讓使用者自己發新邀請、重新開會話（Yjs 的狀態在每個人手上，重新加入後交換 state vector 即可）。

### §8 測試（TDD）

`tests/star/`：線路與邀請（編解碼、格式錯誤、模糊測試、邀請簿語意）；會話（3／5／8 位成員的加入與轉送、名單、離開、單播、echo、**寄件人不可冒充**〔成員自己塞 DELIVER 會被請離開；SEND 沒有寄件人欄位〕、通道對方不是 Host 就拒絕、踢出後不能收發、封鎖與解除、Host 關閉、P2P 斷線、中繼軌心跳逾時、邀請一次性／過期／撤銷／綁定公鑰／亂猜、核准被拒、成員已滿不耗邀請、遲遲不 JOIN、加入逾時、**慢成員被請離開而其他人照常**、volatile 先丟、成員端 backpressure、灌爆的人被 rate-limit、酬載上限、同一身分取代）；順序（中繼軌 20% 掉包＋10% 重複＋亂序下恰好一次且依序、中繼軌節流、NIP-11 預算）；**隨機化性質測試**（3 個固定種子、每個 250 步隨機加入／離開／踢出／斷線／廣播／單播／echo，P2P 與掉包的中繼軌混合：每個人收到的序列嚴格遞增無重複、同序號同內容、單播只到指定的人、一直在線的人沒有遺漏）；**Yjs 風格收斂**（最小 LWW CRDT，5 位成員＋Host、中途加入用單播快照補齊）；真的 `PeerNode`＋`secureChannel`（P2P、中繼退路且線路上找不到明文、混合模式、Host 節點關閉）；後量子開銷量測；安全審查修正（§11，每項一個測試）；子路徑守門。共 77 個測試。

### §9 與真正群組加密（MLS 等）的關係：未來選項，不做

- 本 ADR 解的是「3–8 人即時共編、Host 可信」；它的安全性與「把文件交給 Host 保管」一樣。
- 要讓 Host 看不到內容，需要群組金鑰協商（MLS／TreeKEM，或 Sender Keys）：成員之間的訊息對 Host 不透明，Host 只做排序與轉送。代價：新的密碼學協定（外部審計前不宜上線）、成員進出時的金鑰更新、與雙棘輪不同的前向保密語意、需要成員之間可驗證的身分承諾。
- 屆時可以沿用本 ADR 的外層（邀請、名單、Host 序號、背壓、中繼節流）：`SEND`／`DELIVER` 的酬載換成群組密文即可，Host 仍然提供全序。列為未來選項，**本版不做**。

### §10 子路徑與打包

- `@cinderous/client/star`（`package.json` exports）；零 Node 內建模組、不拉進連線池執行期、部署、中繼、同步、傳檔（`tests/star/subpath.test.ts` 以 esbuild 實際打包守著）。
- 主入口與 `./sync`、`./sync/vault`、`./transfer`、`./protocol`、`./pairing` 都不帶星狀會話；主入口打包大小不變（156,329 B，與 v0.25 相同）。`./star` 本身約 114 KB（minify；大部分是雙棘輪與 ML-KEM，與 `secureChannel` 共用）。

### §11 安全審查（2026-09-29，內部、唯讀審查者）

審查範圍：`src/star/*`、`src/pairing/uri.ts` 的 `expandRelayToken`。發現與處理：

| # | 嚴重度 | 發現 | 處理 |
|---|---|---|---|
| H1 | High | 預設突發（16 MiB）大於佇列上限（8 MiB），溢出時被請離開的是收件人：一位 P2P 成員在速率內就能讓所有走中繼的成員被判 `overflow` | 突發改 2 MiB、每秒 1 MiB；佇列記寄件人，佔一半以上者被請離開（`rate-limit`）並撤掉它的佇列項目，收件人留下；§5。測試：預設值下灌 9 × 1 MiB、速率內灌滿 64 KB 佇列、真的慢的人仍 `overflow` |
| H2 | High | 未加入的連線（不需邀請）用完整參數：單包 1 MB、重排 16 MiB × 32 名額，加上一包幾十萬筆空紀錄的物件放大 | 加入前單包 1 KB、重排 4 包，加入後才放寬；P2P 跳號＝協定錯誤；每包 ≤ 4,096 筆、除 LEAVE 外不收空紀錄；重排存原始位元組。測試 |
| M1 | Medium | 等待名額可被換金鑰佔滿；未加入的中繼連線稀釋正式成員的事件預算 | 名額滿了踢最舊的閒置連線；預算分母只算已加入的成員；加入時限 15 → 10 秒。測試 |
| M2 | Medium | 心跳不受節流：中繼成員一多，光心跳就超出中繼每分鐘上限 | 心跳間隔＝max(設定, 節流間隔)、逾時至少三個心跳；文件建議限制走中繼的人數。測試 |
| M3 | Medium | 邀請字串（含秘密）留在邀請簿，`invites()` 會回傳；成員端會話期間一直留著邀請 | 邀請簿不存字串、`invites()` 不含；成員端只用自己的副本、送出後清零、不留在選項裡。測試 |
| M4 | Medium | 踢出只封鎖公鑰：多次邀請的持有者換金鑰就能回來 | 踢出（封鎖時）預設撤銷它用的邀請；文件寫明封鎖只認公鑰。測試 |
| L1 | Low | 沒有邀請的人也拿得到 `full`／`banned`／`closed` | 先驗邀請（不扣次數），無效一律回邀請相關原因。測試 |
| L2 | Low | `SecureChannel` 沒有 `closed`，鏈路的「通道已關」檢查從不成立 | `listen`／`join` 在握手完成後先看底層 `PeerChannel.closed`，已關就不交給鏈路；鏈路也接受選用的 `closed`（不改 `SecureChannel`，主入口打包大小不變） |
| L3 | Low | ack 大於已送出的號碼也被接受（只影響那位成員自己） | 視為協定錯誤。測試 |
| L4 | Low | `listen()` 沒給 `accept` 會接管節點上所有連進來的通道 | 文件警告：共用節點時一定要給 `accept`（或把通道自己交給 `attach`） |
| L5 | Low | 中繼軌上 END／REJECT 不等確認就關，掉了對方要 60 秒才知道 | 關閉中的中繼鏈路等未確認清空（或寬限 2 秒）再關 |
| L6 | Low | 成員端沒人聽時暫存滿 1,000 則就默默丟 | 上限 10,000 則，滿了以 `ended(overflow)` 明確結束 |
| L7 | Low | 名稱過濾漏了 U+061C、U+2028/2029、U+FEFF、U+2060–2064、U+180E | 補齊；文件：名稱未經認證，UI 一律附公鑰指紋 |
| Info | — | `StarMessage.from` 的註解寫「成員無法冒充」，但成員端拿到的是 Host 宣稱的寄件人 | 註解改寫（只在 Host 可信時成立）；另：邀請中繼只收 `wss://`、不收 `@`；lseq 用完明確 `desync`；`approveJoin` 加時限（預設 2 分鐘）；成員端檢查 WELCOME 的 `you` 是自己、依 Host 宣告的上限收緊 |

審查者確認沒有問題的：寄件人不可冒充（SEND 無寄件人欄位、加入後送其他類型一律協定錯誤）、成員只認邀請裡的 Host、邀請扣次數在 `await` 之前（無競態）、被踢／已離開／被取代的連線送來的一律不處理、解析器邊界、Host 序號不重用不倒退、計時器與監聽在關閉時釋放。

## Consequences

- ＋ 外掛只要 `listen`／`createInvite`／`join`／`send`／`onMessage`，其餘（成員進出、順序、背壓、中繼節流、重送）由 SDK 處理；Yjs 的合併仍在外掛。
- ＋ 雙棘輪線路格式不變；舊的成對用法不受影響。
- ＋ 後量子 header 的成本在批次下從每則 2.4 KB 降到每則約 75 B。
- － Host 看得到所有內容（刻意的取捨，§1）。
- － Host 是單點：Host 斷線整個會話結束，不自動換手（§7）。
- － 中繼軌下，人一多每人的更新頻率就低（預算平均分配；8 人約每 5 秒一包）。
- － 邀請、封鎖名單與序號只在 Host 記憶體，Host 重開就是新會話。
- － 任何人都能連上 Host 並完成握手（邀請秘密在加密通道裡才送）；未加入的連線有嚴格上限，但仍會吃掉少量 Host 的中繼事件配額。未來可在信令裡帶 `HMAC(秘密, 加入者公鑰)`，Host 驗過才握手。
