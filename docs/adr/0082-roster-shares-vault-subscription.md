# 0082. 名單同步共用 Vault 傳輸層的 1060 訂閱：中繼不再把同一批檔案塊回兩次

- 狀態：**已接受（Accepted，2026-10-14）**——CinderSync 實機（手機）找到；使用者 2026-10-14「好 依序處理」
- 日期：2026-10-14
- 對應：ADR 0028 §5（名單同步）、0029（分頁補拉）、0035（補訂閱往前退讓兩天）、0043（名單外層 kind）、0052（中繼搬家通知）、0081；CinderSync ADR 0072

## Context
名單同步的外層預設是 kind 1060（與檔案塊相同，ADR 0043），所以 `NostrRosterSync` 與 Vault 傳輸層各開一個**條件完全相同**的常駐訂閱 `{kinds:[1060], #p:[我]}`。
2026-10-14 手機（CinderSync）連上錨點時的訊息紀錄：兩個常駐訂閱與補拉的第一頁各回 **138 則**（中繼每次 REQ 的 16 MB 上限）——同一批檔案塊下載三次，
名單同步還把 138 顆檔案塊各解一次，只為了找出其中幾則名單（實機 12 則、共 132 KiB）。

「常駐訂閱只收即時、歷史全靠補拉」做不到：NIP-59 的外層時間被往前推最多兩天，中繼對即時轉發也套用 `since`，所以常駐訂閱必須往回兩天（ADR 0035）；
而錨點把 `limit: 0` 當成不限，沒有「只要即時」的寫法。這部分（補拉第一頁與常駐訂閱重疊）在 ADR 0081 讓收件匣變小之後量很小，另案再評估。

## Decision
- **傳輸層 `onOtherEvent?: (event) => void`**：解得開、但內層不是同步訊框（kind 4360）的外層事件交給應用，每顆只交一次（與訊框共用去重）。
  寄件人不論在不在信任名單上都交（剛配對的新裝置寄來的名單），由接手的一方驗證；解不開的不交。常駐訂閱與補拉來的都會交。
- **`NostrRosterSync` 的 `subscribe?: boolean`**（預設 true）：`false` 時不開自己的訂閱，事件由應用以 `ingestEvents` 餵進來；宣告、收送名單變動、待送標記照舊。
- 應用（外層同為 1060 時）：`createNostrVaultTransport({ …, onOtherEvent: (e) => roster.ingestEvents([e]) })` ＋ `new NostrRosterSync({ …, subscribe: false })`。
- 外層 1059 的名單（ADR 0043）不適用：傳輸層只訂 1060，名單同步照舊自己訂閱。

## Alternatives Considered
- **連線池合併條件相同的訂閱**：通用，但兩個訂閱的游標、重訂與關閉時機各自不同，合併後的語意要另外設計；而且名單同步仍要把檔案塊各解一次。
- **名單改用 1059**：要所有裝置同時換（兩端外層相同才互通），而且不收 1060 的情境才需要。

## Consequences
- ＋ 每次連上少一份常駐訂閱的回應（實機約 16 MB、138 則），也少解 138 次。
- ＋ 名單也從補拉拿得到（以前只有常駐訂閱那一頁，被截斷的較舊名單要等下一次宣告）。
- － 應用要接兩個地方；沒接的應用行為不變（兩個選項都預設關）。
- 名單事件仍不送收件確認（量小；名單是最新狀態，之後另案）。
