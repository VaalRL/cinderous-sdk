# 0103. 保底用量照實扣、單一值的查詢順著索引分頁

- 狀態：**已接受（Accepted，2026-10-20）**——使用者 2026-10-20 選定「刪幾列扣幾列」與「中繼改查法」
- 日期：2026-10-20
- 對應：Cinderous ADR-0390（同一件事在錨點的中繼，程式與測試逐字相同）；SDK ADR 0102（同一次量測的前半）、0042（保底份額）、0084（外掛啟動從頭補拉收件匣）

## Context

ADR 0102 修完後，用同一套 `wrangler dev` 量測，還剩兩處讀取：
1. **保底用量快取被作廢後要重建**：每收件人上限刪了某人的列，會逐人重算，每次約 1,400 列。整批淘汰、舊版天花板淘汰之後，會整個以 `GROUP BY` 重建，每次約 4,200 列。
2. **外掛每次啟動從頭補拉收件匣**：`#p`、`kinds` 以 `json_each` 的 `IN` 下推，SQLite 不能順著分桶索引讀，每一頁都要把剩下的列全部排序。收件匣塞滿（約 1,430 塊）時，一次約 3.4 萬列。

## Decision

與 Cinderous ADR-0390 逐字相同：
1. `describeRows` 多帶大小、是否借用、作者。新增 `forgetUsage`：刪掉的列照實從借用總量與每個人的正常列用量扣掉。
   - 用在每收件人上限、舊版天花板淘汰、整批淘汰。
   - `refreshOwner` 刪掉。
2. `pushIn` 只有一個值時寫成 `column = ?`。多個值照舊用 `json_each`。

## Alternatives Considered

- **只重算那一個人**：改動最小，但每次仍讀約 1,400 列。
- **外掛限制從頭讀的頻率**：收不齊的塊要晚一天才確認，使用者沒有選。

## Consequences

- ＋ 塞滿後每寫一顆：平均讀 42 → 25–30 列，最多一次讀 1,541 → 約 830 列。一次啟動補拉 33,828 → 約 18,200 列。行為不變。
- － 補拉每一頁「先查大小」仍讀到筆數上限 1,024 列，原因是大小欄不在索引上。這次不動。
- 驗證：`tests/relay/evict-reads.test.ts`（與 Cinderous 逐字相同）：
  - 快取與實算逐人一致；
  - 補拉形狀的查詢計畫沒有整個重排。
  - `tests/relay/sql-message-store.test.ts` 三則「下推到 SQL」的斷言改成接受 `IN` 或 `=`。
