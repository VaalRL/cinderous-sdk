# 0073. 技術債：停止追蹤副本的大小寫索引、G10 只收斂內容來源版本、中繼帳獨立保存、規模測試比倍數

- 狀態：**已接受（Accepted，2026-10-12）**——使用者 2026-10-12：「先處理 SDK 另案的技術債」；實作於 v0.55.1
- 日期：2026-10-12
- 對應：ADR **0047**／**0071**（停止追蹤、搬進排除範圍）、**0035 §G10**（相撞的兩個檔案內容相同就收斂）、**0068**（中繼帳）、0025 §效能（規模測試）

## Context
四件累積下來的另案：
1. ADR 0071〈另案〉：隨機性質測試加大種子時，只差大小寫的兩個路徑（`Note.md`／`note.md`）在重新納入時，停止追蹤的那一筆被當成使用者刪除（`property-excludes` 種子 28）。
2. `property-p2p` 種子 211 遺失資料（改動前就有）。
3. ADR 0068 實作計畫第 5 項：量測送出端預算的效益。
4. 5,000 個檔案的規模測試在機器忙時超時。

## 決策與原因

### 1. 停止追蹤副本的索引：一個比對 key 可以有好幾筆
- 原因：`#byDet` 以 `pathKey`（不分大小寫）為 key、只放一筆。大小寫有別的檔案系統上 `Note.md` 與 `note.md` 是兩個檔案，各自停止追蹤時其中一筆被蓋掉：
  磁碟上的 `Note.md` 之後被當成新檔交給另一筆紀錄，原本那筆還以為檔案是它的；撞名處理把它改名成副本後，原本那筆看到「檔案不見了」→ 當成使用者刪除。
- 決策：`#byDet` 改成 key → 一組 fileId。查詢以**路徑完全相同**的那一筆優先；沒有的話，只差大小寫的只有一筆才算（大小寫不分的檔案系統上就是同一個檔案）。
- 試過但不採用：只差大小寫時再比對磁碟上的大小與修改時間判斷是不是同一個檔案——改變了 P2P 情境的時序，`property-excludes`（P2P）種子 25 開始失敗；單純的「一組＋完全相同優先」就夠，種子 25–144 都通過。

### 2. G10（相撞的兩個檔案內容相同就收斂）只收斂「內容來源」的版本
- 原因（種子 211）：同一台裝置在同一秒對兩個不同的檔案產生衝突副本，名稱相同（`Note (衝突-LATE-…).md`）。其中一個（A）保存著另一邊的內容；另一個檔案（B）的某個版本頭
  只是把一份**已經被搬進 A** 的內容改名過來，內容剛好和 A 一樣 → G10 把 A 刪掉（「內容還在 B」）。B 之後合併它的兩個版本頭，結果正確地換成另一份內容，A 的內容就沒有任何地方有了。
- 決策：留下的那個版本**只是沿用父版本的內容**（改名、搬家：有父版本的雜湊與它相同）時不收斂，照舊產生衝突副本（多一份、不丟資料）。只看版本資料，每台判斷一樣。
  兩邊各自新建的同內容檔案（G10 原本的情境：新裝置帶著既有的檔案加入）、真的改成這份內容的版本、輸的是空檔，照常收斂。
- 試過但不採用：「兩邊都只有一個版本頭才收斂」——版本頭數量取決於訊息到達的順序，各台判斷不同，種子 211 照樣失敗。

### 3. 送出端預算的量測（ADR 0068 第 5 項），以及量出來的隊頭阻塞
- 新的量測 `tests/bench/relay-budget.measure.ts`（`npm run measure:relay-budget`；`FILES`、`SIZE_KB`）：P2P 打不通、中繼每位收件人 1,440 塊／7 天、每小時 120 則，比較舊（一本帳、不簽收）與新（每台一本帳＋簽收單）：
  A. 新裝置加入收齊要多久；B. 一台整段時間離線時其他台收齊要多久。結果記在 ADR 0068〈量測〉。
- 第一次量出來 B 的新版**也要 7.1 天**：ADR 0068 的「一台離線不拖累別台」沒做到。原因是**隊頭阻塞**——批次挑下一則時，佇列前面那些「只欠離線那台、它的帳滿了」的版本讓整輪停下來等，
  後面送給其他收件人的都輪不到。單元測試只看「最後收齊」、沒看要多久，所以沒抓到。
- 決策：帳滿而送不出去的那一則**先跳過**、看後面的；整輪都送不出去才等（最早空出來的時間）。每小時則數的限速照舊停整輪。
  同一次挑選裡每台的用量與等待時間只算一次（佇列很長、又有一台帳滿時，逐則重算是平方級）。
- 單元測試補上時間：`relay-receipts`〈c 離線…〉要求 b 在一天內收齊（修之前要 7 天以上）。

### 4. 中繼帳存在自己的鍵、用量遞增快取；規模測試改比「寫入的位元組數」
- 原因：規模測試改成比倍數之後抓到 v0.54 起的平方級退化——同一台機器上 5,000 檔初次同步 v0.53 約 4–9 秒、v0.54／v0.55 約 120 秒：
  1. 中繼帳的快照放在 meta 裡，meta 每做完一件工作就整份轉 JSON 寫一次（5,000 檔寫進狀態儲存 4.6 GB，v0.53 是 46 MB）；
  2. `status()` 每次都要每位收件人的用量，快取每記一筆帳就失效，整本重算。
- 決策：
  - 中繼帳改存在自己的鍵 `rb`，累積 500 筆變動才寫一次、停止時一定寫；v0.54–v0.55 放在 `meta.rb` 的帳啟動時搬過去。當掉時最多少記這一小段（只會讓送出端多送一點）。
  - 用量快取改成遞增：記帳時直接加到快取上；簽收、清理、合併、換小時（可能有過期）時才整本重算。
  - 結果：5,000 檔初次同步回到 v0.53 的水準（同一台機器 8.1 秒 vs 8.9 秒），寫進狀態儲存 60 MB。
- 規模測試：牆鐘時間受平行跑的其他測試影響太大（同一段程式 8 到 37 秒），改成比**同步時寫進狀態儲存的位元組數**（每次都一樣、不看機器）：
  5,000 檔不超過 1,000 檔的 12 倍——v0.53 是 7.6 倍、目前 8.1 倍、v0.54 的退化 24.5 倍（會失敗）。掃描照舊比時間（很快、雜訊小）；牆鐘時間只留 300 秒的防呆。

## Consequences
- ＋ 兩個會遺失或誤刪資料的情境修掉；加大種子的性質測試（`property-excludes` 25–144、`property-p2p` 200–229、其他 9 種性質測試各 20–60 個新種子）都通過。
- ＋ 規模測試不再因為機器忙而失敗，同時真的擋得住平方級退化（這次就抓到兩個）。
- ＋ ADR 0068 的「一台離線不拖累別台」真的做到（量測 B：7.1 天 → 3 小時）。
- － G10 少收斂一些「改名來的同內容」情境，會多一份衝突副本（使用者可以刪掉）。
- － 中繼帳的節流保存：當掉時最多少記 500 筆。
- 驗證：`property-excludes`（種子 28 不再誤刪）、`property-p2p`（種子 211 不再遺失）、`tests/sync/vault/scale.test.ts`（寫入位元組的倍數）、`relay-receipts.test.ts`〈c 離線…一天內收齊〉與〈v0.54–v0.55 把帳放在 meta.rb：重開時搬到自己的鍵〉、全部單元與性質測試（2,860 個）。
