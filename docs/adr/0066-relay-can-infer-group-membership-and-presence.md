# 0066. 已知限制：中繼推得出同步群組有哪些裝置、誰還沒上線過

- 狀態：**已接受（Accepted，2026-10-11）**，記錄為已知限制，不改程式。使用者 2026-10-11 問：「relay 是否可以知道同樣同步群組中還有誰沒有上過線」；看過分析後裁示：「寫 ADR 記錄成已知限制」。
- 日期：2026-10-11
- 對應：
  - ADR **0064**（中繼站主不可信任）、**0065**（對外說法：加密藏內容、不藏中繼資料）。
  - ADR **0025** §5（協調器的 Nostr 網路層：kind 1060 禮物包、每台裝置各包一份）、**0042**（每收件人配額與丟棄計數）。
  - 中繼的「訂閱必須具名」（`relay-core.ts` 的 `scoped()`，Cinderous ADR-0123）。

## Context

中繼程式**沒有**記錄或統計群組成員與上線狀態，但它手上的資料足以推算出來。站主改程式、直接讀 Durable Object 的 SQLite，或使用公開中繼時對方站主，都做得到：

1. **誰上線過。** 讀自己的收件匣（`#p:[我]`）之前必須以裝置的真實 pubkey 做 NIP-42 AUTH；中繼在記憶體記著哪個 pubkey 正在讀收件匣（`inboxSubs`，丟棄計數用）。從沒連上的裝置，中繼從沒見過它的 AUTH。
2. **同一個群組有哪些裝置。** 協調器把同一則訊息「每台裝置、每個訊框各包一份」（`nostr-transport.ts`），外層帶收件人的 `#p`。外層簽章是一次性金鑰，但送出的連線已經以寄件裝置的真實 pubkey AUTH（白名單檢查就靠這個，`relay-core.ts` 的 `authedAs`）。同一刻、同一條連線送出幾份大小相同、寫給 X、Y、Z 的包 ⇒ {寄件裝置, X, Y, Z} 是同一群。
3. **誰一直沒來收、最後一次什麼時候收。** 寫給某台的包存到保存期限（預設 7 天），每收件人有自己的配額計數（`MAX_PER_RECIPIENT`）與丟棄計數。包一直累積、收件人一直沒 AUTH ⇒ 那台是成員但沒上線過（或很久沒上線）。
4. **白名單本身就是名單。** 私人中繼開了白名單，站主不必推算。

中繼看不到的：內容、檔名、裝置名稱、群組名冊、金鑰（都在加密層內）。

## Decision

1. **記錄為已知限制，不改程式。** 這屬於 ADR 0064／0065 已經寫明的「中繼看得到中繼資料（誰、何時、寫給誰、多大）」。
2. 理由：
   - CinderSync 的主要用法是中繼部署在使用者**自己的** Cloudflare 帳號，站主就是使用者本人，實際風險低。
   - 能降低外洩的做法（見下）都要改協定或配對流程，代價不小，等有需求再個別開 ADR。
3. **對外說明**：README 的〈中繼看得到、看不到什麼〉已涵蓋（收件人 pubkey、連線時間）；用公開中繼或別人架的中繼時，群組成員與上線時間對站主是可推知的。

## 可能的緩解（未研究可行性，留待日後）

| 做法 | 藏住什麼 | 代價 |
|---|---|---|
| 送出用另一條**不 AUTH** 的連線或一次性身分 | 寄件人與收件人的關聯 | 私人中繼的白名單靠 AUTH，要另外設計准入 |
| 收件匣用**輪替的假名 pubkey** | 收件人是誰、跨期間追蹤 | 配對時交換派生規則；協調器、中繼配額都受影響 |
| 群組**共用收件匣**、只發一份 | 群組人數、誰沒來收 | 要群組金鑰；前向保密與移除裝置要重新設計 |
| 掩護流量、隨機延遲 | 時間上的關聯 | 吃免費額度 |

## Consequences

- 好處：已知的中繼資料外洩有明確紀錄，推廣與文件不會誤稱「中繼不知道群組成員」。
- 代價：用公開或他人架的中繼時，群組大小與各裝置的上線時間對站主是可推知的。
- 相關研究：已送達後讓中繼上的資料提早過期（使用者 2026-10-11 要求研究），**不會**消除本 ADR 的推算——中繼本來就從 AUTH 知道誰上線。
