# 0136. 名冊移除成員後，切斷他已連著的連線

- 狀態：**已接受（Accepted，2026-11-18）**——Cinderous 使用者 2026-11-18 要求把 SDK〈還沒做〉的功能做完
- 日期：2026-11-18
- 對應：SDK ADR 0013（白名單外的人以 4003 斷線）、0040（拒收詞元表）、0132、0133（本 ADR 補它〈殘餘風險〉的一條）、0134、0135

## Context

自架 Node 站在執行期換成員有兩條路：NIP-86 的 `cinder_applyroster`（ADR 0132）與名冊金鑰把名冊發到站上的自動套用（ADR 0134、0135）。兩條最後都呼叫 `RelayCore.setAllowedAuthors`。

ADR 0133 寫明的殘餘風險：**名冊移除某人後，他已連著的連線不會被切斷**。寫入立刻被擋（下一則 `EVENT` 就 `blocked: not-allowed`），但他已開的訂閱在斷線前仍收得到投遞給他的事件——被移出組織的人，只要不關 App，就繼續收得到組織內發給他的訊息與心跳。

## Decision

1. **`RelayCore.setAllowedAuthors(list)` 改為回傳 `Outbound[]`**（原本回 `void`）。新名單生效的同時，找出**已完成 NIP-42 認證、但認證身分不在新名單上**的每一條連線：
   - 送一則 `NOTICE`：`restricted: not-allowed: 已被移出這座站的白名單`（新常數 `REJECT.removedFromWhitelist`；詞元沿用 `not-allowed`，客戶端分類與 AUTH 時被擋相同）。
   - 以 **4003 `restricted`** 關閉——與 AUTH 時擋白名單外的人同一個關閉碼（ADR 0013），`classifyRelayClose` 已分成 `restricted`，客戶端不用改。
   - **立刻**在核心裡拆掉這條連線的訂閱與認證狀態（`disconnect`），所以從換名單到 socket 真的關掉之間到達的事件也不會再投遞給他。
2. **還沒認證的連線不動**：要求 AUTH 的站上它們什麼都讀不到；之後 AUTH 時照新名單判斷（被移除的人重連會在 AUTH 時以 4003 擋下）。
3. **開放站換成封閉站也一樣**：已認證、不在新名單上的人一起切，與「AUTH 時不在名單就斷線」的規則一致。
4. **Node 主機**：`Nip86Admin` 的 `apply.allowed` 把回傳值交給 `dispatch` 送出並關閉連線。兩條入口（`cinder_applyroster`、名冊自動套用）都走這裡。

## 理由

- 只擋寫入、不擋讀取，等於被移出的人仍是半個成員；企業情境（Cinderous ADR-0047）移除人通常正是為了讓他看不到後續內容。
- 判斷用**認證身分**而不是事件作者：讀取權限只跟 AUTH 綁定，未認證的連線本來就讀不到。
- 沿用既有關閉碼與詞元，舊客戶端的處理（不自動重連 `restricted`）照樣成立，不用協定改版。
- 改回傳值而不是讓核心自己關連線：`RelayCore` 不碰 socket，所有關閉都由宿主依 `Outbound.close` 執行（ADR-0366 §容量的既有模式）。

## Alternatives Considered

- **只拆訂閱、不關連線**：他還能開新訂閱——雖然 `scoped` 會擋大部分，但已認證的連線仍是一個名單外的人佔著的位置，與 AUTH 時直接斷線的規則不一致。
- **宿主自己掃 socket**：每個宿主都要重寫一次，而認證狀態只有核心知道。
- **等連線自然斷**：手機 App 常駐時可能好幾天都不斷，就是 ADR 0133 記下的問題本身。

## Consequences

- ＋ 名冊移除生效時，被移除的人的連線立刻斷、訂閱立刻停。
- ＋ 兩條執行期換名單的入口都涵蓋；Worker 不受影響。
- － `setAllowedAuthors` 的回傳型別從 `void` 變成 `Outbound[]`：直接呼叫它的宿主若忽略回傳值，就只有舊行為（只擋寫入）。型別相容，但要把回傳值送出去才有新行為。
- － 同一把被移除的金鑰若也是共同管理者或運維金鑰，照樣被切（成員資格以名冊為準）；名冊金鑰本身永遠在名單上（ADR 0134 的 `withRosterAdmin`），不會被切。
- **Worker（Cloudflare）**：沒有執行期換名單（它沒有 NIP-86，`ALLOWED_PUBKEYS` 改了要重新部署，部署本身就會斷掉所有連線），所以不適用。
- 驗證：`tests/relay/roster-kick.test.ts`——核心單元測試（被移除者收到 NOTICE 並 4003、訂閱立刻停、同一人的每條連線都切、留下的人與未認證的連線不動、開放站變封閉站、重連在 AUTH 時被擋）與 Node 主機整合測試（名冊金鑰發新名冊 → 被移除者的 socket 以 4003 關閉，另一位成員不受影響）。
