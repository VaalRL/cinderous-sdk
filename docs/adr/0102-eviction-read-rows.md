# 0102. 檔案車道塞滿後的讀取列數：淘汰時只讀要刪的那幾列

- 狀態：**已接受（Accepted，2026-10-20）**——使用者 2026-10-20「好 依序修復」
- 日期：2026-10-20
- 對應：Cinderous ADR-0389（同一件事在錨點正在跑的中繼，程式與測試逐字相同）；SDK ADR 0085（整批淘汰）、0042（保底與溢位帶）、0097（額度用完時說明原因）、0098（拿掉 `idx_offline_kind`）

## Context

2026-10-19 錨點 1 用完的是 Durable Object 的**讀取**額度。免費方案每日 500 萬列，當天讀了 693.7 萬列，全在 `app:cindersync`。那一小時正在做 CinderSync 實機測試：寫入 2.36 萬列、讀取 568 萬列。

用 `wrangler dev` 跑錨點的 `SqlMessageStore`，設定與錨點檔案車道相同，加總 SQL 游標回報的 `rowsRead`：
- 天花板以下，每寫一顆讀 0 列；
- 塞滿以後，平均讀 172 列、最多一次讀 10,438 列。

來源是四條「本來只該讀幾列、實際掃過整個索引」的查詢：
1. 淘汰前查批次：`INDEXED BY idx_offline_batch` 加上 rowid 條件，SQLite 只能掃整個部分索引，每次約 4,400 列。
2. 淘汰後清掉每收件人列數快取，下次寫入重數 `COUNT(*)`，每次約 1,400 列。
3. 列出借用列時，規劃器為了省排序改走整個到期索引，每次約 4,300 列。
4. 每小時清理查到期借用列的批次，與第 1 點同一個寫法，每次約 4,200 列。

## Decision

與 Cinderous ADR-0389 逐字相同：
1. `describeRows(rowids)`：以 rowid 只查要刪的那幾列的收件人、批次與桶別，取代 `batchesOf`。回收借用列時，先決定刪哪幾列再查。
2. `forgetRows`：刪掉的列照實從各桶的列數快取扣掉，不再整個清掉。`dropBatchMates` 扣掉同批列數；`enforceCap` 整批刪完從快取取回列數，不再 `COUNT(*)`。
3. 列出借用列時指定 `INDEXED BY idx_offline_borrowed`。
4. 每小時清理改成：先從借用列的部分索引找出到期的那幾列，再以 rowid 查批次。

## Alternatives Considered

- **調低天花板或關掉保底與溢位帶**：會減少收件匣能放的量，等於用體驗換額度。
- **升級付費方案**：是費用決策，使用者另外處理。

## Consequences

- ＋ 塞滿後每寫一顆：平均讀 172 → 42 列，最多一次讀 10,438 → 1,541 列。每小時清理 4,233 → 54 列。行為不變。
- － 剩下的主要是保底用量快取在整批淘汰後重建。另外，外掛每次啟動從頭補拉收件匣，塞滿時一次約 3.4 萬列。這兩項這次都沒動。
