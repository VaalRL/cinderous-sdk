# 0096. 小檔合併照「這次實際的去向」分組：拆過收件人、有欠款的也合

- 狀態：**已接受（Accepted，2026-10-19）**——實機驗證 ADR 0095 時發現
- 日期：2026-10-19
- 對應：ADR 0095（`bundle`）、0091（只限速積壓的收件人）、0068（欠款 `owed`）；CinderSync ADR 0095

## Context

v0.68.0 上了三台實機（兩台桌機加一支手機，都宣告看得懂 bundle），測「手機一次新增 8 篇小筆記」。結果：
- 手機照舊送出 8 則 `node`，**一則都沒合**。
- 手機給 B 的修改有積壓，所以新修改被拆了收件人：先即時送給 A，B 記成欠著（ADR 0091）。
- ADR 0095 的實作排除了「拆過收件人」與「有欠款」的項目，等於排除了最需要合併的情況。
- 而且分組看的是佇列欄位（`to`／`owed`／`got`／`full`）是否完全一樣。不同時間排進來的項目這些欄位多半不同，即使這次實際送給同一組人也不合；積壓補送因此照舊一篇一則。手機重新載入後的第一輪，就把每小時 120 則的額度用完了。

## Decision

1. 把「這一項這次要送給誰」抽成 `#route(entry, bulk, heavy)`，回傳限速與配額之前的四件事：`to`、`owed`、是否限速、是否拆過。送出流程與合併共用同一段。
2. 合併的分組鍵改成這次實際的去向：`[to, owed, 是否限速]`。佇列欄位不同、算出來的去向一樣的，照樣合。
3. 拆過收件人、有欠款的項目也可以合。整包送給 `to`，包裡每一項都記同一份 `owed`，送出後逐項 `#onSent(seq, owed)`，跟單獨送一樣。配額帳滿時排除的收件人（`plan.blocked`）也一樣套用到整包。
4. 其餘不變：一則不超過一個訊框、收件人全部看得懂才合、不碰輕量成員、限速一包算一則。

## Alternatives Considered

- **維持 ADR 0095 的排除條件**：積壓時完全不合，實機上就是沒有效果。
- **只放寬「拆過收件人」，分組仍看佇列欄位**：積壓補送照樣幾乎合不起來。

## Consequences

- ＋ 有一台積壓時，給其他裝置的新修改照樣合成一則即時送；給積壓那台的補送，每個限速名額都裝滿一包。
- ＋ 多算一次每一項的去向，佇列很長時多一點計算，跟送出的成本比起來可以忽略。
- 驗證：`tests/sync/vault/bundle.test.ts`〈有一台積壓時也合〉（c 積壓、每小時只補 1 則：給 b 的 5 篇新修改合成一則，給 c 的積壓用不到 15 則補完）；全套 3,019 項。
