# 0047. 使用者自訂的同步排除範圍：gitignore 風格的兩層規則、排除不等於刪除、執行中更新（v0.37.0）

- 狀態：**已接受（Accepted）**——2026-10-01，使用者核准方向（兩層、gitignore 語法、排除不等於刪除、各裝置可不同）；實作於 v0.37.0
- 日期：2026-10-01
- 補註（2026-10-05，[ADR 0058](0058-sparse-vault-members.md) §4）：§4 第 5 列「排除期間被使用者刪掉的，重新納入時當作一次本機刪除」對**用排除做滾動視窗、自己刪掉視窗外本機副本**的應用是風險（應用的清理會被當成使用者刪除）。v0.46 起應用改呼叫 `coordinator.evict(path)`：停止追蹤的本機副本清掉、不產生版本，重新納入時重新抓。本列的定義不變（使用者自己刪的仍是刪除）。
- 相關：本 repo ADR **0025**（協調器、不變式、`ignore`、改名語意、墓碑）、0026（P2P 批次與大檔直送）、0028（摘要對帳）、
  0035 §G10（同內容的路徑相撞直接收斂）、0045（排程同步、`whenSent`、`digestPolicy`）、0046（衝突 callout）；
  CinderSync ADR 0008（固定排除：`vault.configDir`、`.trash`、`.git`、`node_modules`、備份資料夾、點開頭路徑，不分大小寫）

## Context

使用者要求 CinderSync 與 Cinder Coffice 都讓使用者自己設定「哪些檔案不同步」，而且要有預設值。現況：

- 協調器只有 `ignore?: (path) => boolean`（ADR 0025）。它在掃描、通知、改名、`#reingest` 時略過被忽略的路徑；`#materialize` 對
  目標路徑被忽略的版本直接回 `ok`。**沒有「規則改變」的概念**：已經追蹤的檔案之後變成被忽略時，紀錄照舊掛在磁碟上，
  掃描的「不見的檔案」判斷也特別略過它（所以不會被當成刪除），但它的狀態會一直停在舊的基底版本上，遠端改名到被忽略的路徑時
  本機那一份也不會動——這些行為對「固定、永遠不變的排除」是夠的，對「使用者隨時會改的清單」不夠。
- CinderSync 在外掛層用 `sync-paths.ts` 自己實作固定排除（協調器的 `ignore`、轉接器的防呆、監聽器共用），Coffice 還沒有。
  兩個外掛各寫一份 glob 比對會分岔（大小寫、路徑分隔、資料夾語意），設定頁的驗證訊息也會不一致。

使用者核准的方向：**兩層**（固定＋使用者）、**gitignore 風格**、**排除不等於刪除**、**執行中可更新**、**各裝置規則可以不同**、
平台無關零 Node、放在 `./sync/vault` 讓兩個外掛共用（SSOT）。

## 決策

### 1. API（`@cinderous/client/sync/vault`）

| 名稱 | 用途 |
|---|---|
| `compilePathFilter(patterns, { caseInsensitive?, invalid? })` | 編譯規則清單（陣列，或文字框的整段文字）→ `{ isExcluded(path), explain(path), patterns, caseInsensitive }` |
| `compileSyncExcludes({ fixed, user, caseInsensitive?, invalid? })` | 兩層：`fixed.isExcluded(p) \|\| user.isExcluded(p)`；`explain` 多回 `layer: 'fixed' \| 'user'` |
| `validatePattern(pattern)` | 設定頁即時驗證：`{ ok, kind: 'rule' \| 'negation' \| 'comment' \| 'blank', error?: { code, message }, warning? }` |
| `DEFAULT_USER_EXCLUDES` | 使用者清單的預設值（凍結陣列） |
| `literalPathPattern(path, { dirOnly? })` | 確切路徑 → 從根目錄算起、特殊字元跳脫的規則（固定排除 `vault.configDir` 用） |
| `combinePathFilters(...)`、`asPathFilter(fn)` | 濾網與函式的 OR 組合 |
| `VaultSyncOptions.excludes` | 協調器的排除範圍（`PathFilter` 或函式）；省略＝與 v0.36 相同 |
| `coordinator.setExcludes(filter \| null)` | 執行中更新（語意見 §4）；Promise 在重新掃描與套用完成後 resolve |
| `coordinator.isExcluded(path)` | `ignore` ∪ `excludes` ∪ 協調器暫存名稱；監聽器先用它過濾 |
| `coordinator.detached()` | 因排除而停止追蹤、本機仍保留的檔案：`{ fileId, path, reason: 'excluded' \| 'moved-out' }` |

`compilePathFilter` 預設遇到不合法的規則丟 `RangeError`（訊息帶那一行與原因）；`compileSyncExcludes` 的**使用者清單**預設 `invalid: 'skip'`
（存下的設定在新版變成不合法時，同步仍然要起得來），**固定排除**一律丟錯（那是應用的程式錯誤）。

`path-filter.ts` 單獨打包 < 8 KB、不依賴任何模組（設定頁可以只引用它）；主入口 `.` 位元組不變（179,045 B／gzip 63,448 B），
`./sync/vault` 167,705 → 177,355 B（gzip 60,692 → 64,151 B）。

### 2. 語法（gitignore 的子集）

- 一行一條；空行、`#` 開頭的行略過；**前後空白一律去掉**（git 保留開頭空白、結尾可用 `\ ` 跳脫——設定頁的文字框裡多打的空白幾乎都是誤打，與 git 不同之處）。
- `*` 不跨 `/`；`?` 一個字元（不含 `/`）；`[abc]`、`[a-z]`、`[!a]`／`[^a]`（集合永遠不比對 `/`）；`\` 跳脫下一個特殊字元（`* ? [ ] ! # \ 空白`）。
- `**`：`**/x`＝任何深度；`x/**`＝x 底下的全部（不含 x 本身）；`a/**/b`＝中間零到多層；其他位置等同 `*`（同 git）。
- 結尾 `/`：只比對資料夾；資料夾被排除時底下全部排除。
- 開頭或中間有 `/`：從 Vault 根目錄算起（開頭的 `/` 只是錨點）；否則比對任何一層的名稱。
- **`!` 反向：支援**。理由：「排除所有 PDF，但留下 `重要.pdf`」是常見需求，而且 gitignore 使用者預期它存在。語意同 git：最後一條符合的規則決定；
  **上層資料夾被排除時，底下的檔案不能再用 `!` 納入**（`archive/` ＋ `!archive/keep.md` 仍排除 keep.md；要寫 `/archive/**` ＋ `!/archive/keep.md`）。
  `explain()` 回報是哪一條規則、經由哪一層資料夾（`via`），設定頁可以直接告訴使用者。反向只在同一層內有效：**使用者的 `!` 不能把固定排除重新納入**。
- 比對前路徑與規則都做 **NFC** 正規化；**預設不分大小寫**（與協調器預設的 `pathKey`＝NFC＋小寫一致；Windows、macOS 的檔案系統大小寫不分，多排除一點是安全的一側）。
  `caseInsensitive: false` 可關閉，但與預設 `pathKey` 混用時，只差大小寫的兩個路徑可能一個被排除、一個沒有（已知限制）。
  小寫化讓字元範圍顛倒的規則（`[Z-a]`）改用原規則加 `i` 旗標，不會變成不合法。
- 不合法（`validatePattern` 的錯誤碼，訊息是繁體中文、給人看的）：`backslash`（`folder\sub`：路徑請用 `/`）、`absolute`（`C:/…`）、
  `dot-segment`（`.`、`..`）、`empty-segment`（`a//b`）、`unclosed-bracket`、`invalid-class`（`[z-a]`）、`empty`（只有 `!` 或 `/`）、
  `control-char`、`too-long`（> 512 字元）。合法但會排除整個 Vault 的（`*`、`**`、`**/*`）給 `warning: matches-everything`。
- 實作：每條規則編成一個 `u` 旗標的正規表示式，對路徑的每一層前綴（資料夾）與檔案本身求「最後一條符合的規則」。沒有反向規則時走快速路徑（任何一層符合即排除）。

### 3. 預設清單 `DEFAULT_USER_EXCLUDES`

只放**各平台自動產生、從來不是使用者內容**的檔案：

| 規則 | 來源 |
|---|---|
| `.DS_Store` | macOS Finder |
| `._*` | macOS 在非 HFS 磁碟（隨身碟、網路磁碟）上的 AppleDouble 資源分支 |
| `Thumbs.db`、`ehthumbs.db` | Windows 縮圖快取 |
| `desktop.ini` | Windows 資料夾設定 |
| `~$*` | Microsoft Office 開啟中的鎖定檔（`~$報告.docx`；**Coffice 最需要**） |
| `.~lock.*#` | LibreOffice 開啟中的鎖定檔 |
| `*.tmp` | 各種程式的暫存檔 |
| `*.swp`、`*.swo` | Vim 交換檔 |
| `*.crdownload` | Chrome 下載中 |

刻意**不放**：`*~`（有人的檔名真的以 `~` 結尾）、`*.bak`、`*.part`（使用者可能自己留著）、`node_modules`、`.git`（屬於應用的固定排除）。
CinderSync 的固定排除已經涵蓋所有點開頭路徑（`.*`），`.DS_Store` 等在那裡是重複的、無害；Coffice 不一定有點開頭的固定排除，所以預設清單照樣列。

### 4. 協調器：排除不等於刪除

核心概念是**停止追蹤（detach）**：檔案紀錄的 `disk` 清掉，記下當時的磁碟狀態 `det = { path, hash, size, mtime, base, why }`
（持久化；`why`：`x`＝路徑被本機排除，`m`＝別台把檔案搬進了本機排除的範圍、本機在原路徑留著一份）。**停止追蹤不產生任何版本**。

| 情況 | 行為 |
|---|---|
| 已追蹤的檔案變成被排除（`setExcludes`、啟動時規則不同） | 停止追蹤（`why: x`）。本機檔案不動；不產生刪除版本；其他裝置照常保留它們的副本，之後不再收到這台的修改 |
| 排除期間本機修改／刪除被排除的檔案 | 不收進來、不送出（`notifyLocalChange`、掃描都略過被排除的路徑） |
| 收到其他裝置對被排除路徑的版本（修改、新建、刪除） | **併入版本圖、不寫入**：對帳時這台知道那些版本（不會反覆索取，也不會被補送），只是不碰磁碟。本機那一份（若有）絕不被刪或覆寫 |
| 本機沒有追蹤、所有版本頭都在本機排除的範圍、而且分岔了 | **這台不合併**（不必等內容、不會出現 `pending`）；納入它的裝置算出的合併版本（確定性 id）到了就收斂成一個版本頭 |
| 其他裝置把檔案**搬進**本機排除的範圍 | 本機原路徑那一份停止追蹤、**留著不刪**（`why: m`，`detached()` 的 `moved-out`）；之後的掃描不會把它當新檔送回去（不會「搬走又冒出來」）。本機改了它 → 變成一個新檔；檔案在別處被刪了 → 它就是普通的本機檔案（新檔）；別台把檔案搬回同步範圍 → 恢復追蹤、跟著搬過去（不會多一份） |
| 從排除移除（`setExcludes` 或下次啟動的規則） | 重新掃描。停止追蹤的那一份**重新納入**：以 `det.base` 為父版本，本機期間的修改成為一個本機版本、與別台期間的修改照常三方合併（兩邊都沒改＝什麼都不送；只有別台改＝寫入別台的內容；只有本機改＝照常送出；兩邊改不同行＝合併；同一行＝衝突副本／callout）。**排除期間被使用者刪掉的**當作一次本機刪除（父版本 `det.base`；別台期間改過就保留修改——與「期間的修改在重新納入時送出」對稱）。沒有追蹤紀錄的本機檔案當作新檔（別台同路徑同內容 → G10 收斂成一個；內容不同 → 衝突副本）。這台還沒寫入的遠端檔案寫進來 |
| 本機把檔案搬進自己排除的範圍 | 與 v0.36 的 `ignore` 相同：離開同步範圍＝其他裝置刪除（一刪一改時保留修改）。這是使用者對**檔案**的動作，不是改規則；`.trash` 這類固定排除需要這個語意 |

其他細節：

- **啟動**：讀回狀態後、開閘之前就把被排除的已追蹤檔案停止追蹤（排在啟動前的遠端刪除不會碰到它們）；`scanOnStart` 之後排出「本機沒有追蹤、
  有版本頭在同步範圍內」的檔案重新套用，並清掉被排除檔案的 `pending`。`meta.ex` 記下「用過排除」，之後即使不帶規則啟動也會補寫當時略過的檔案。
- **內容保存**：被排除的版本頭**不在這台保存內容**（不佔 IndexedDB——行動裝置排除大資料夾的主要目的）；文字檔的合併祖先照舊保留，
  `det.base` 列入必留。重新納入時缺的內容照常向別台索取（中繼內容以 `want`、大檔由對方收到摘要後直送；`setExcludes` 重新納入了東西時會在
  `digestPolicy` 不是 `manual` 時送一份摘要）。停止追蹤的本機副本**仍可提供已經發布過的版本內容**（讀那一份、雜湊相符才算），
  所以「每一台都排除了」也不會讓內容憑空消失。
- **大檔（P2P）**：本機排除的大檔，收到串流的內容段時回 `skip`（送方當作送達、清掉直送佇列），不收資料；停止追蹤的檔案不再當作直送來源。
- **`pending` 的處理**：停止追蹤、或所有版本頭都在排除範圍時，那個檔案的 `pending` 清掉——「本機排除」不是「遺失」，`whenSent`、狀態列都不會卡住。

### 5. 證明

沿用 ADR 0025 的框架：版本圖的併入與規則無關，規則只影響「寫不寫磁碟」與「合不合併」。

**(P1) 改變排除規則不會讓任何裝置刪除檔案。** 一台裝置產生刪除版本只有三條路：(a) 本機刪除被收進來（`#ingestPath` 發現追蹤中的路徑不見、
`#scanAll` 的「不見的檔案」、改名到被略過的路徑、`#reingest` 發現不見）——它們都只看 `disk` 不為空的紀錄；(b) 合併／G10 收斂（確定性，
與規則無關）；(c) 重新納入時，`why: x` 的那一份在磁碟上不見了（使用者在排除期間刪的）。停止追蹤把 `disk` 設成空、**不產生任何版本**，
之後 (a) 的每一條路都碰不到它；(c) 只在使用者自己刪了檔案時發生，而且以 `det.base` 為父版本——別台期間的修改一定是並行的，
「一刪一改保留修改」讓修改留下。所以「加入／移除排除」本身不會產生任何刪除；其他裝置只會因為使用者真的刪了檔案而刪除。

**(P2) 排除範圍內的本機檔案永遠不被同步刪除或覆寫。** `#materialize` 在目標路徑被排除時，於任何 `apply` 之前回傳；刪除分支在本機那一份的路徑被排除時改成停止追蹤；
帶 `det` 的紀錄只在「`det.path` 與目標路徑**都**在同步範圍內」時才恢復追蹤，之後的改名／寫入一律帶前置條件（內容就是 `det.hash`，否則先收成本機版本再合併——ADR 0025 不變式 1）。

**(P3) 各裝置規則不同也收斂、不會無限來回。** 每一台都併入每一個版本（驗證與版本圖不變），所以摘要裡的版本頭集合與規則無關。
被排除的檔案這台不索取內容、不合併，因此永遠不會等任何東西；別台也從不等這台的回應（協調器沒有「確認」，P2P 的 `skip` 算送達）。
跳過的合併由納入它的裝置算出——合併 id 是確定性的，到了就是這台既有版本頭的後代，版本頭收斂成一個，摘要比對 `covered` 成立、不再補送。
每個版本在每台裝置只併入一次，沒有任何訊息會因為「對方排除」而被重送，所以不會無限來回。留著的 `moved-out` 副本在沒改過時不會被送回去，
所以「搬進別台排除的資料夾」也不會來回複製。

**(P4) 不遺失資料。** 被排除的內容仍在某一台的磁碟上：寫入它的裝置（排除後停止追蹤也照樣留著）、或納入它的裝置。同步對排除範圍只做「不寫」，
從不刪、不覆寫（P2）。性質測試以「每一次寫入的內容，除非使用者自己刪掉，都還在**某一台**的磁碟上（排除範圍裡的也算）」驗證。

### 6. 向下相容

- 沒有 `excludes`、沒呼叫 `setExcludes`、狀態裡沒有 `det`／`meta.ex`：所有新分支都不會進入（`#excl === null`、`#byDet` 空），行為與 v0.36 位元組相同；
  既有 vault 測試（含三組性質測試，同樣的種子）的斷言一條都沒改，照過。
- `ignore` 保留 v0.36 的語意不變（已追蹤的檔案之後被忽略時不停止追蹤）。CinderSync 現有的固定排除做法照樣可以運作；
  要改用新語意就把它換成 `excludes: compileSyncExcludes({ fixed: [...] , user })`（§8）。
- 線上格式不變。舊版裝置收到新版裝置的版本照常處理；新版的排除只影響自己（不寫、不合併、不送本機排除範圍的修改）。
- `FileRecord.det`、`Meta.ex` 是新增的選配欄位，舊版讀到會略過（舊版不會產生它們；降版後 `det` 紀錄只是沒有磁碟的紀錄，掃描會把那些本機檔案當作新檔——不刪）。

### 7. 已知限制

1. **只比對衝突副本名稱的規則**（例如 `*衝突*`）：衝突時輸的一方主檔被改寫成贏的內容、它自己的內容存成衝突副本，而副本在這台被排除就不寫——
   那份內容只在納入副本路徑的裝置上。目錄、副檔名、名稱開頭的規則不受影響（副本名稱保留目錄、名稱開頭與副檔名）。設定頁應提醒。
2. **本機把檔案搬進自己排除的資料夾＝其他裝置刪除**（§4 最後一列）。**使用者 2026-10-01 確認維持此行為（選項 A）**：移進排除的資料夾通常就是不想讓它出現在其他裝置；檔案仍留在本機，且有寫入前備份。各台規則不同時，納入那個資料夾的裝置也拿不到它（它只在搬移的那台上）。
   要「這台不下載、別台照常同步」請在**這台**排除、別台搬移。
3. 停止追蹤的檔案被使用者**改名**（排除期間）：重新納入時是「刪除＋新檔」，不是改名。
4. 別台把檔案從本機排除的資料夾搬到同步範圍：這台寫一份新的，原本被排除的那一份留在原處（成為普通的本機檔案）。
5. 大檔（P2P）：停止追蹤的檔案不再當作直送來源；別台對這台送摘要時仍會試著直送本機排除的大檔，在標頭就被 `skip`（每次摘要多一次標頭往返）。
6. `caseInsensitive: false` 與預設 `pathKey`（不分大小寫）混用：只差大小寫的兩個路徑可能一個被排除、一個沒有。

### 8. 給外掛的整合指引

**固定排除怎麼傳入**（CinderSync，等價於 `sync-paths.ts` 的現有規則）：

```ts
import { compileSyncExcludes, DEFAULT_USER_EXCLUDES, literalPathPattern, validatePattern } from '@cinderous/client/sync/vault';

const FIXED = [literalPathPattern(app.vault.configDir), '/.trash', '/.git', '/node_modules', '.*'];
const excludes = () => compileSyncExcludes({ fixed: FIXED, user: settings.syncExcludes ?? DEFAULT_USER_EXCLUDES });
const sync = new VaultSyncCoordinator({ adapter, store, transport, deviceId, excludes: excludes() });
```

`literalPathPattern(configDir)`（不加 `dirOnly`）同時排除同名檔案，與現有的 `path === root || startsWith(root + '/')` 相同；`.*` 涵蓋所有點開頭路徑
（含 `.trash/cindersync-backup`）。Coffice 至少放自己的設定資料夾；Office 鎖定檔 `~$*` 在預設使用者清單裡。

**設定頁**：

- 一個多行文字框（一行一條），旁邊唯讀列出固定排除；第一次開啟時把 `DEFAULT_USER_EXCLUDES` 複製進設定（使用者可刪），另給「恢復預設」。
- 每行即時 `validatePattern(line)`：`error.message` 直接顯示在那一行；`warning`（例如 `*`）用黃色提示「會排除整個 Vault」。
- **即時預覽被排除的檔案數**（防抖 300 ms）：
  ```ts
  const draft = compileSyncExcludes({ fixed: FIXED, user: textarea.value });   // 不合法的行自動略過
  const paths = (await adapter.list()).map((f) => f.path);                     // 含點開頭與附件
  const hit = paths.filter((p) => draft.isExcluded(p));
  preview.setText(`${hit.length} 個檔案不會同步`);
  for (const p of hit.slice(0, 50)) row(p, draft.explain(p));                  // 「被 *.tmp 排除（使用者）」
  ```
  另外列出「目前同步中、套用後會停止追蹤」的數量：`sync.index().filter((e) => draft.isExcluded(e.path)).length`，並說明「不會刪除任何檔案，其他裝置照常保留」。
- 按下儲存：`await sync.setExcludes(excludes())`；之後可用 `sync.detached()` 顯示停止追蹤的檔案，`moved-out` 的另外說明
  「其他裝置把它搬進了你排除的資料夾，這台留著一份不再同步的副本」。

**監聽器與轉接器**：事件先以 `sync.isExcluded(path)` 過濾（取代各自的 `createExclusionFilter`）；協調器不會對被排除的路徑寫入，
轉接器的防呆可以保留只看固定排除的那一份。
