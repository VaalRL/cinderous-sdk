# 0071. 把檔案搬進自己排除的範圍：停止追蹤，不是刪除

- 狀態：**已接受（Accepted，2026-10-12）**——使用者 2026-10-12 裁示（CinderSync TODO〈把檔案移進這台排除的資料夾，其他裝置會當成刪除。要不要改？〉：「要」）；實作於 v0.53.0
- 日期：2026-10-12
- 對應：ADR **0047**（排除不等於刪除、停止追蹤 `detach`、重新納入）；CinderSync ADR 0020 §4、0055

## Context
ADR 0047 讓「規則改變使檔案變成被排除」只停止追蹤、不刪除；但**使用者把追蹤中的檔案搬進自己排除的範圍**（改名事件的新路徑被 `excludes` 排除）仍走 `#ingestRename` 的舊路：新路徑被略過、舊路徑不見了 → 本機刪除版本 → 其他裝置刪掉它。CinderSync 一直在設定頁警告「其他裝置會當成刪除」。

## 決策
1. **搬進排除範圍＝停止追蹤**：`#ingestRename(from, to)`，`from` 追蹤中且不在排除範圍、`to` 被 `excludes`（不是 `ignore`）排除、新路徑上真的有檔案 → 不產生版本，記成停止追蹤，**位置記在新路徑**，新的原因 `why: 'v'`（`detached()` 照舊回 `reason: 'excluded'`）。其他裝置照常保留。
2. **還在排除範圍時，別台的修改不寫回原路徑**（`#converge` 開頭）：否則這台會在原路徑多出一份。
3. **重新納入＝改名**：
   - 移除排除規則（`setExcludes`）後掃描到它（`#adopt`）：以停止追蹤時的版本為父，送出「改名到這裡＋現在的內容」——即使內容沒變也要送（否則會被改回原路徑）；與別台期間的修改照常三方合併（路徑取這台的改名、內容合併）。
   - 使用者把它從排除範圍搬回同步範圍（改名事件，`#moveDetached`）：同上。
   - 在排除範圍裡搬動：只更新記著的位置。
   - 排除期間使用者把它刪了：重新納入時當作一次本機刪除（同 ADR 0047 的 `x`）。
4. **`ignore` 不變**：搬進 `ignore`（暫存名稱等）照舊是離開同步範圍＝刪除。
5. **應用的責任**：**移到垃圾桶不是搬進排除範圍**。應用把垃圾桶（例如 Obsidian 的 `.trash`）放進 `excludes` 時，移到垃圾桶要通知**刪除**、不是改名（CinderSync 的監聽器只把「使用者清單」的排除當成改名，固定排除照舊是刪除）。
6. 只看得到**即時的改名事件**；應用關著時搬的（之後只靠掃描）看起來是「舊路徑不見＋排除範圍多一個檔案」，照舊是刪除。

## Alternatives Considered
- **應用層把改名拆成「停止追蹤」＋什麼都不送**：應用拿不到協調器的內部狀態，重新納入時無法以原本的檔案身分合併。否決。
- **別台的修改照樣寫到原路徑**：這台會同時有排除區那一份與原路徑一份，重新納入時撞名、產生衝突副本。否決。
- **掃描時以雜湊比對推回「搬家」**：同內容的檔案可能不只一個，猜錯就把別的檔案當成搬家。否決（記在 Consequences）。

## Consequences
- ＋ 使用者把檔案收進「私人」資料夾不會讓其他裝置刪掉它；搬回來就恢復同步並合併期間的修改。
- － 應用關著時搬的照舊是刪除（只有掃描看得到）。
- － 狀態多一種停止追蹤的原因（`v`，只在這台的狀態裡，不上線）。
- **另案（已知、與本 ADR 無關；2026-10-12 由 ADR 0073 修正）**：隨機性質測試加大種子數時（`VAULT_EXCLUDES_PROPERTY_SEEDS=60`、起點 25），**改動前**的程式在種子 82 就已失敗（某個二進位檔各台內容不同）；改動後的軌跡不同，P2P 版在種子 28 失敗——追蹤到的是既有的「只差大小寫的兩個路徑（`Note.md`／`note.md`）在重新納入時撞名：撞名處理先把其中一個改名成衝突副本，停止追蹤的那一筆再看到『檔案不見了』而當成使用者刪除」（ADR 0047 的 `x` 分支，不經過 `v`）。預設種子數（24＋8）都通過。待另案修正。
- 驗證：`tests/sync/vault/excludes.test.ts`〈這台把檔案搬進自己排除的範圍：停止追蹤，不是刪除…〉（別台保留、掃描不刪、別台修改不寫回原路徑、移除排除後當作改名並與別台修改合併）與〈本機把檔案搬進 ignore 的範圍＝離開同步範圍〉；`property-excludes`（`sharedView` 不比停止追蹤的檔案在別台的路徑）。
