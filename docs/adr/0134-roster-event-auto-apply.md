# 0134. 名冊金鑰簽的名冊發到自架站就直接套用，不必經手運維金鑰

- 狀態：**已接受（Accepted，2026-11-12）**——Cinderous 使用者 2026-11-12 在「管理端按鈕＋貼運維金鑰」與本方案之間選了本方案
- 日期：2026-11-12
- 對應：SDK ADR 0132、0133；Cinderous ADR-0261 §4、ADR-0047、ADR-0414

## Context

ADR 0132 讓自架 Node 中繼能在執行期改成員：運維金鑰呼叫 NIP-86 的 `cinder_applyroster`，送入名冊金鑰簽的名冊。ADR 0132 的後續寫著「企業管理端可加『推送名冊到自架站』的按鈕」。

動工前發現這個按鈕做不好：

- NIP-86 的請求要用**運維金鑰**簽 NIP-98。
- Cinderous ADR-0261 §4 規定運維金鑰**不能**是名冊金鑰：名冊金鑰是組織的成員權威，運維金鑰是這台機器的憑證，可能交給託管方。
- 管理端的 App 持有的是名冊金鑰（管理者的身分）。要按按鈕推送，就得讓它也拿到運維金鑰，兩把金鑰又回到同一個人、同一台裝置上。

而管理者發布名冊時，名冊事件**本來就會發到組織的中繼**（客戶端靠它取得名冊）。

## Decision

1. **自架 Node 中繼收到名冊金鑰簽的名冊事件（kind 10038）時，直接套用**。
   - 檢查與 `cinder_applyroster` 完全相同：驗簽（`verifyOrgRoster`）、`updatedAt` 比上次新、是秒、不超前一天、成員 pubkey 是 64 個小寫 hex、至少一個在世成員。
   - 先存檔、存成功才生效（ADR 0133）。存過的名冊照樣記下 `admin`，名冊金鑰換掉或拿掉後不再生效（ADR 0133）。
   - 事件照一般流程存檔與扇出（客戶端也要收到）。舊的或重送的名冊安靜地不套用；其他不套用的原因記一行警告。
   - 實作：`Nip86Admin.applyRosterEvent`；宿主在 `RelayCore` 的 `intercept` 裡呼叫，回 `undefined` 讓事件照常處理。
2. **只需要 `ROSTER_ADMIN_PUBKEY`**。沒設 `NIP86_ADMIN_PUBKEYS` 時：
   - `Nip86Admin` 仍然建立（運維金鑰清單可以是空的，前提是有名冊金鑰），但**不開 HTTP 端點**，NIP-11 也不宣告 86。
   - 存檔只沿用名冊；存過的事件類型、站名、說明照環境變數（那些只能經管理 API 改，管理 API 沒開就不該生效）。
3. **名冊金鑰永遠寫得進這座站**：設了 `ROSTER_ADMIN_PUBKEY`，它就被加進生效中的白名單（環境變數的與名冊的都是）。
   - 否則管理者沒把自己列進名冊時，它簽的下一份名冊會被白名單擋在門外，自動套用只能用一次。
   - 名冊金鑰本來就能把自己加進名冊，所以這不多給任何權力。
4. `ALLOWED_KINDS` 設了清單的站，清單要包含 10038，名冊事件才進得來。

## 理由

- 成員的權威是名冊的**簽章**（Cinderous ADR-0047），不是「誰把它送來」。中繼本來就驗簽、擋舊名冊；運維金鑰對成員資格不多提供任何保障，只是另一條送達管道。
- 這樣管理者照常按「發布名冊」，自架站就跟著換成員，不必有按鈕、不必經手運維金鑰，ADR-0261 §4 的金鑰分離也保得住。
- 拿名冊金鑰的人本來就能簽一份所有客戶端都採用的名冊；讓中繼也跟著採用，沒有擴大它的能力。

## Alternatives Considered

- **管理端按鈕，每次貼運維金鑰簽 NIP-98（不存檔）**：只改 Cinderous，但管理者的裝置要經手兩把金鑰，ADR-0261 §4 的分離形同虛設。否決。
- **管理端按鈕，App 另外產生並保存一把運維金鑰**：一樣是兩把金鑰在同一台裝置，還多一份要保管的秘密。否決。
- **只放行名冊金鑰的 kind 10038（不加進整個白名單）**：權限更窄，但要改 `RelayCore` 的白名單檢查。名冊金鑰本來就能把自己列進名冊，窄化換不到實際保障。不採用。
- **不做，維持站方自己用 NIP-86 工具送**：可行，但對自架的小組織等於沒有執行期改成員。

## Consequences

- 行為改變（只影響設了 `ROSTER_ADMIN_PUBKEY` 的 Node 站）：
  - 名冊金鑰發到站上的新名冊會改成員。過去要運維金鑰呼叫 `cinder_applyroster` 才會。
  - 名冊金鑰一定寫得進這座站，即使不在 `ALLOWED_PUBKEYS` 或名冊裡。
  - 只設 `ROSTER_ADMIN_PUBKEY`、沒設 `NIP86_ADMIN_PUBKEYS` 也會讀寫 `cinder_admin_state`（只有名冊）。
- 沒設 `ROSTER_ADMIN_PUBKEY` 的站不受影響。Worker 不受影響（它沒有這條路）。
- 殘餘風險：
  - 名冊金鑰外洩＝對方能改這座站的成員。這在本文之前就成立：外洩的名冊金鑰能簽出所有客戶端都採用的名冊。處理方式不變：換名冊金鑰（Cinderous ADR-0052）並更新 `ROSTER_ADMIN_PUBKEY`。
  - 名冊移除某人後，他已連著的連線不會被切斷（ADR 0133，未變）。
