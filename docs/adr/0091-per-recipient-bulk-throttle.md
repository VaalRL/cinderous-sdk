# 0091. 批次限速按收件人：只限速要給積壓那幾台的，其他裝置的新修改照常即時送

- 狀態：**已接受（Accepted，2026-10-15）**——使用者 2026-10-15「修」
- 日期：2026-10-15
- 對應：ADR 0026（P2P 批次、中繼限速補送）、0029／0068（按收件人的塊數帳、`owed`）、0058（輕量成員、只帶版本資訊的合併訊息）；CinderSync ADR 0085

## Context
批次模式原本是**全域**的：佇列裡待送的版本 ≥ `bulkThreshold`（10）就進批次模式，所有經中繼的送出都按 `relayBulkPerHour`（20／小時）排隊，不分收件人。
2026-10-15 實測：手機重新配對後離線，桌機 B 補送給它的 14 筆積在佇列（只欠手機）；B 這時改的一小段字要給 A 和手機，排在後面，
25 分鐘還沒送到 A。排程同步的兩台桌機很少同時在線，直連也幫不上——一台長期離線、剛加入的裝置，會拖住其他裝置之間的同步，最長一小時以上。

另外，驗證時隨機性質測試抓到一個原本就有、時序改變才露出來的問題：大檔走直送（`#pushes`）時版本資訊也先交出去了，卻沒有把版本標成「已交出」
（`rec.unsent`）。中繼那一則還排在佇列裡時本機緊接著修改或刪除，就會被當成「沒送出、直接取代」，造成分岔：對方留著已刪除的大檔，或大家都卡在等一份不存在的內容。

## Decision
1. **積壓的收件人**（`#backlogged()`）：佇列裡還欠它（`owed ?? to ?? 所有裝置`，扣掉已經經直連收到的 `got`）的版本達到 `bulkThreshold` 的裝置。
   批次模式＝佇列 ≥ 門檻**而且**至少有一台積壓（中繼不收檔案塊等 `blocked` 狀態照舊整批）。
2. 批次模式下每一項：還沒收到的收件人裡**有不積壓的**，就照常即時送給它們（不計入每小時限速、不走塊數預算——與非批次模式相同）；
   積壓的那幾台記成 `owed`（ADR 0068 的機制），之後照限速補送或經直連送達。收件人全部都積壓的才照舊限速；
   限速等待時不再整個停下，先看後面有沒有要給不積壓裝置的。
3. 需要傳輸層能照收件人送（`targeted`）；不行的照舊整批限速。被拆過收件人的這一項不和其他項合成一則 `nodes`（ADR 0058）。
4. 大檔直送交出版本資訊時，同樣標成「已交出」（與中繼送出、批次送出一致）。

## Alternatives Considered
- **門檻改大或限速放寬**：只是延後問題，也違背 ADR 0026 保護收件人中繼配額的用意。
- **新修改插隊（優先送最新的）**：仍是全域限速，額度被插隊的吃掉，積壓的那台更慢；也沒有區分收件人。

## Consequences
- ＋ 一台離線很久、剛加入或重新配對的裝置積壓時，其他裝置之間的修改照常幾秒內經中繼送到；給積壓那台的照舊限速、等直連。
- ＋ 大檔直送後馬上刪除或修改，不再分岔。
- － 一則版本可能分兩次經中繼送（先給不積壓的，再補給積壓的），多一點中繼流量；只發生在批次模式。
- 驗證：`tests/sync/vault/p2p.test.ts`〈只有一台積壓〉（三台、打不通直連：c 積壓時 a、b 互傳的新修改一分鐘內到，給 c 的照舊要好幾小時補完；修正前一分鐘內沒到）、
  〈大檔經直送交出了版本、中繼還沒送出就在本機刪掉〉（修正前 b 留著已刪除的大檔）；隨機性質測試另跑 80 個種子；全套 209 檔 2,993 項通過。
