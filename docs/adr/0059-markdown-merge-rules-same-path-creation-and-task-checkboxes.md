# 0059. Markdown 合併規則：同路徑各自新建的文字檔以空檔為祖先合併、任務勾選框衝突自動合併；由版本資料決定、名單宣告開關

- 狀態：**已接受（Accepted）**——使用者 2026-10-05 裁示 5、7（見 ADR 0058〈使用者需求與裁示〉）；實作於 v0.46.0
- 日期：2026-10-05
- 相關：本 repo ADR **0025**（確定性合併、路徑相撞、涵蓋規則）、0035 §G9／§G10（能力宣告、同內容的路徑相撞直接收斂）、**0046**（callout；模式由版本 id 的標記決定）、
  0048（空檔不產生副本、改名回音）、0058（輕量成員；同一批裁示）

## Context

輕量成員的手機 App（ADR 0058）主要寫 daily note。手機離線時打開今天的筆記、桌機也開了 Obsidian（自動建立今天的 daily note）——兩邊各自**新建**了同一個路徑的檔案，
沒有共同祖先。ADR 0025 的規則是「路徑相撞：`pathAt` 較早的留下，其他的改名成衝突副本」，結果使用者每天早上都要收一份衝突副本。另外，兩台各勾一個待辦、或一台勾了一台沒動
同一區塊時，`merge3` 常常把相鄰的勾選變化判成同一個衝突區塊。使用者的裁示：

- **裁示 5**：同一天兩邊各自建立同路徑 Markdown＝**改以空檔為共同祖先做三方合併**，合不了退回 callout／副本（取代「較晚的改名成衝突副本」，限文字檔）。
- **裁示 7**：**勾選框衝突自動合併**放 v1：衝突區塊兩邊只差在任務勾選狀態（`- [ ]`／`- [x]`，含 Tasks 外掛勾選時同行附加的 `✅ YYYY-MM-DD`）時自動合併；
  「已勾為準」或「時間較新為準」擇一並說明理由，須確定性。
- 兩者都會改變合併結果：必須確定性、所有裝置同版；以能力宣告控管——**名單上所有成員都宣告支援時才啟用**（比照 ADR 0046），否則退回舊行為。

## 決策

### 1. 開關：名單宣告決定「要不要開」，版本資料決定「這次合併用不用」

- 協調器選項 `mergeRules`（預設 false）與執行中的 `setMergeRules(on)`：開了，這台寫出的版本 id 帶「支援 Markdown 合併規則」的標記。
- 名單能力宣告的鍵 `MERGE_RULES_CAPABILITY`（`'mdMergeRules'`）：應用 `declareCapabilities({ ...CURRENT_DEVICE_CAPABILITIES, [MERGE_RULES_CAPABILITY]: true })`，
  名單 `change` 時 `sync.setMergeRules(membership.allDeclare(MERGE_RULES_CAPABILITY))`——**有任何一台（含舊版）沒宣告就關**。這是裁示的「所有成員都宣告支援才啟用」。
- 但**合併時不看名單**（理由同 ADR 0046 §2：名單同步有延遲，A 以為大家都支援、B 還不知道，兩台會算出不同的合併而分岔）：一次合併用不用新規則，
  只看參與的版本——**所有版本頭都帶標記**（合併版本＝父版本都帶，加入時算好、持久化在 `f:` 的 `mr`，同 `cm`）。所以名單開關只影響「之後的版本帶不帶標記」，
  每台對同一組版本頭算出同一個結果。
- 標記：id 的第 17–24 位是前 16 位的雜湊（`markMergeRulesId`／`isMergeRulesId`／`supportsMergeRules`）。callout 的標記在最後 8 位、涵蓋前 24 位，兩個可以同時帶
  （先標合併規則、再標 callout）；舊版裝置（≤ v0.45）看得懂 callout 的標記（不受影響），看不懂合併規則的標記（照舊規則）。巧合符合的機率 2⁻³²。

### 2. 同路徑各自新建的文字檔：收成一個檔案（裁示 5）

兩個**不同的檔案**（不同 fileId）要用同一個路徑（比對同 `pathKey`），而且兩邊目前的版本都支援合併規則、都是文字檔（`text`，非大檔）、內容不同、都不是空檔
（空檔與同內容照舊：ADR 0048 的空檔收掉、ADR 0035 §G10 的同內容收斂，先判斷）：

- 留下哪一個照 ADR 0025（`pathAt` 較早、平手比 fileId）。**輸的不改名成副本，而是收進留下的那個**：
  - 留下的檔案多一個**沒有父版本**的版本 A：內容＝輸的那一方目前的內容；id ＝ `sha256('fold', 輸的 fileId, 它的版本頭, 留下的 fileId, 路徑)` 加上合併規則的標記（輸的那一方支援 callout 時也帶 callout 的標記）；
    裝置名稱、時間沿用輸的那一方（callout 標示作者用）。留下的檔案因此有兩個版本頭、**沒有共同祖先**，交給一般的合併（§3）。
  - 輸的檔案加一個刪除版本（父版本＝它的版本頭；id 由同樣的輸入決定、帶「被收進別的檔案」的標記）。它的內容已經在 A 裡，所以什麼都沒丟；之後它若在別台被改了，
    「一刪一改保留修改」讓它回來、再收一次（新的 A），一樣收斂。
- 每一台各自做也得到同樣的 A、同樣的刪除版本、同樣的合併版本（id 都由版本資料決定）。
- **磁碟交接**：磁碟上的那一份是輸的（它的版本就是 A 的內容）、留下的還沒落地時，直接記到留下的檔案名下（基準＝A），接著合併結果以前置條件**原地覆寫**——
  不先刪再寫，開著的 daily note 不會消失一下。別台先做了收合、這台先收到刪除版本時：這台認得留下的檔案就以同樣的輸入補做一次 A 再交接；
  已經收到 A 就直接交接；**留下的檔案這台還不認得（訊息亂序）時照常刪掉，它到了再寫**（短暫消失；內容在 A 裡，不遺失）。
- **輸的那一方的內容不在這台**（例如先收到只有版本資訊的補送）：不收、也不改名，兩邊都先等（`pending`，向其他裝置要內容），內容到了再收——
  改名成副本會與別台的結果不同；A 必須帶著內容送出去（別台可能都沒有它的內容了，例如寫它的是清掉了範圍外內容的輕量成員）。
- 不限「同一天」：條件只看版本資料（各自新建、同路徑、文字檔、都支援）。用時間窗判斷「同一天」會引入任意的門檻與時區問題；而兩台各自建立同一個路徑的文字檔，
  不論隔多久，合併成一個（合不了的地方放 callout）都比多一份副本好收拾。

### 3. 「以空檔為共同祖先」：精簡成兩邊共同的行

字面上以空檔當祖先做 `merge3`，兩邊的整份內容都是「同一處的新增」——永遠是一個涵蓋整份檔案的衝突（範本的標題、`## 待辦` 這些兩邊都有的行也算衝突），
callout 會把兩份全文各放一次。所以祖先用**兩邊共同的行**（最長共同子序列，`commonLinesBase`）：等於「以空檔為祖先」再把衝突區塊精簡到真正不同的地方（同 git 的 zealous 衝突精簡）——

- 兩邊都有的行只出現一次；只有一邊有的行直接採用；**同一處兩邊各自新增了不同的行**才算衝突（放 callout，或退回衝突副本）。
- 祖先裡的每一行兩邊都有，所以三方合併**不會刪掉任何一邊的內容**。純函式、確定性（輸入的順序由版本頭的排序決定）。

在 `planMerge` 裡：開了合併規則、兩邊都是文字、**完全找不到共同祖先**時用它（祖先是刪除版本、或內容拿不到時不算，照舊）。這也涵蓋了祖先被修剪光的舊檔案
（ADR 0025 已知限制「找不到共同祖先時退回衝突副本」）：現在合併成一個、合不了的地方 callout——被一邊刪掉的行可能留在結果裡（寧可多、不遺失）。

例（手機、桌機各自從同一個範本建立今天的筆記）：

```
手機：# 2026-10-05 / (空) / ## 待辦 / - [ ] 繳電費 / (空) / ## 紀錄
桌機：# 2026-10-05 / (空) / ## 待辦 / (空) / ## 紀錄 / - 09:00 開會
結果：# 2026-10-05 / (空) / ## 待辦 / - [ ] 繳電費 / (空) / ## 紀錄 / - 09:00 開會      ← 乾淨合併，沒有副本
```

### 4. 任務勾選框衝突自動合併（裁示 7）

`resolveTaskCheckboxConflict`（`./sync`，純函式）接在 `merge3` 的衝突區塊上（`merge3(base, a, b, { resolve })`、`merge3Chunks` 同；callout 合併先試它、解不開的才放進 callout）：

- 衝突區塊兩邊**行數相同**，而且每一行要嘛相同、要嘛是**同一個任務只差在勾選**：去掉 `[ ]`／`[x]`／`[X]` 的狀態與 Tasks 的 ` ✅ YYYY-MM-DD` 之後完全相同
  （項目符號 `-`／`*`／`+`／`1.`／`1)`、縮排、引言裡的任務都認得）。文字、縮排、項目符號有任何不同、行數不同、其他狀態（`[/]`、`[-]`）——**照舊是衝突**。
- 祖先也是同樣行數時逐行三方：只有一邊改的那一行取改的那邊（一台把勾拿掉、另一台沒動那一行 → 拿掉）。
- 兩邊都改了同一行（或沒有逐行對得上的祖先）：**已勾的贏**；都勾了取有完成日期的、日期較早的；其餘（`[x]` 與 `[X]`）取字典序較小的。

**選「已勾為準」而不是「時間較新為準」的理由**：

1. **確定性與順序無關**：「已勾的贏」只看兩行本身，是交換、結合的（等於對勾選做 OR）——三台以上、任何合併順序、任何兩兩合併的組合都得到同一行；
   涵蓋規則下不同裝置先合出的不同合併版本也收斂到同一個內容。
2. **沒有逐行的時間**：版本只有一個 `at`（整份檔案最後一次修改的混合邏輯時鐘），不是「這一行何時被勾」。用版本時間會讓「先勾、後來改了別處」的一方被當成較新，
   把另一台剛勾的取消掉；各裝置的時鐘偏差也會讓「較新」不可靠。
3. **符合任務的語意**：勾選幾乎都是「做完了」，同時有一台把它取消、另一台又動了同一行的情況很少；而取消勾選只有一邊改那一行時，逐行三方本來就會採用（上面第二點）。
   誤判的代價是一個多勾的待辦（使用者看得到、一鍵改回），反過來是一個被默默取消的完成紀錄。
4. 完成日期取較早的：Tasks 記的是「完成的時間」，兩台都勾了時第一次完成的時間較接近事實；也是與順序無關的確定性選擇。

只在合併規則打開時（§1，所有版本頭都支援）使用；文字合併（`merge3`）與 callout 合併都適用。

### 5. 收斂

沿用 ADR 0025、0046 的框架：(a) 標記 `r(v)`：非合併版本看 id、合併版本＝父版本都有，加入時算好持久化，與裝置、時間無關；(b) 合併模式只依賴版本頭集合，
`planMerge(nodes, H, content, { callouts, mergeRules })` 是純函式（空檔祖先與勾選規則都是純函式、確定性）；(c) 收合（§2）的 A、刪除版本只由兩個檔案的版本資料決定，
每台各自做也是同一組版本；不同裝置在不同時間收合（看到的版本頭不同）時產生不同的 A——它們都是留下的檔案裡沒有父版本的版本頭，之後的合併以空檔祖先把它們收在一起（內容相同的直接相同）。

例外（都收斂、都不遺失資料，只是可能多一份副本）：v0.45 以前的裝置照舊規則合併（衝突副本）——涵蓋規則留 id 較小的那個；名單開關延遲（一台還沒關就寫了帶標記的版本，
而另一台已經沒標記）——那一次合併照舊規則。

- `@cinderous/client/sync/vault`：`VaultSyncOptions.mergeRules`、`setMergeRules`、`mergeRules`（getter）、`MERGE_RULES_CAPABILITY`、`markMergeRulesId`、`isMergeRulesId`、`supportsMergeRules`、
  `PlanMergeOptions.mergeRules`；`mergeWithConflictCallouts(..., options)` 多一個選用參數（`resolve`）。

### 7. 相容

- 版本節點沒有新增欄位（能力在 id 裡，舊版原樣儲存、轉送）；`f:` 紀錄多一個選配欄位 `mr`（舊版略過、新版讀不到就補算）。
- 預設（`mergeRules: false`）：這台寫出的版本不帶標記，與 v0.45 位元組相同（測試釘住）；但**沒開的新版裝置照樣會依版本資料**用新規則合併（模式不看本機選項），
  所以同一組版本頭在每台新版裝置上結果一樣。
- 合併規則打開後才產生的新東西（沒有父版本的 A、「被收進別的檔案」的刪除版本）都是一般的版本，舊版照常解析、儲存、轉送；名單開關保證這時名單上沒有舊版。

### 8. 已知限制

1. **三台以上**各自新建同一個路徑、而且收到的順序不同：各台先收合的組合不同，之後的合併偶爾會遇到「衝突區塊緊鄰既有 callout 或切到 callout 的一部分」而退回衝突副本
   （ADR 0046 §5 的安全規則）。所有裝置仍收斂到位元組相同的結果、內容都在（測試以 3 台 × 5 個種子釘住，至少有一部分種子收成單一檔案）。兩台（手機＋桌機）的情境不受影響。
2. 訊息亂序、別台的「被收進別的檔案」的刪除版本先於留下的檔案到達時，這台的那一份會先刪再寫（§2）。
3. 勾選規則不處理行數不同的衝突（例如一台勾了、另一台在同一處多加了一行）：照舊是衝突（callout／副本）。
4. 空檔祖先也用在「祖先被修剪光」的舊檔案：被一邊刪掉的行可能留在合併結果裡（寧可多、不遺失）。
