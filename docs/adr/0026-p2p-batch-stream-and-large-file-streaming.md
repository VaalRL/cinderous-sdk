# 0026. P2P 批次串流與大檔串流寫入：新訊框 0xCB、信用視窗、續傳與原子提交、可持久化佇列；協調器改走 P2P 批次

- Status: Accepted
- Date: 2026-09-29
- 相關：
  - ADR 0021〈後續〉#2（CinderSync G4／Cinder Coffice G3）、#4（CinderSync G6）
  - ADR 0009（`PeerNode`／`PeerChannel`、中繼軌每框 48,000 B、每分鐘 200 框）、0010（`secureChannel`）、0015（`FileTransfer`／`P2PFileQueue`〈還沒做〉兩項）、0023（`./transfer` 子路徑）、0025（協調器、`pending`／`supplyContent`／`readVersionContent`、配額限制）、0027（中繼要接受檔案事件）

## Context

- **G4 首次全量同步／大量變更**：協調器（ADR 0025）每個版本是一則訊息，每台收件裝置一顆 kind 1060。新裝置加入 5,000 個檔案的 Vault，就是每台現有裝置各送 5,000 顆以上；中繼每位收件人只收 4,000 顆（`DEFAULT_FILE_PER_RECIPIENT`，存 7 天），會被拒收。
- **G6 大檔**：`FileTransfer` 交給 App 時整檔 `read()` 進記憶體，預設單檔上限 100 MB；`P2PFileQueue` 不持久化。協調器對超過檔案塊層（≈16.5 MB）的檔案只標「待 P2P」，沒有東西真的去送。
- 限制：平台無關、零 Node；不改雙棘輪、不改任何既有事件與既有 P2P 訊框；主入口的打包不能變大；安全不低於 ADR 0009／0015。

## Decision

### §1 `StreamTransfer`：一條通道上的批次串流（`./transfer`，主入口不帶）

跑在任何 `ByteChannel`（`PeerChannel` 的 P2P 軌或中繼軌、`SecureChannel`）上。一個**工作階段**依序送 N 個檔案；每個檔案有 `id`、`size`、`sha256`（事先知道；大檔用 `hashSource` 分段算）、`meta`（App 的 JSON，≤ 64 KB）。

**線路格式**（新增，與 `FileTransfer` 的 0xCF 完全分開）：

| 位元組 | 內容 |
|---|---|
| 0 | `0xCB` 標記 |
| 1 | 線路版本 `STREAM_WIRE_VERSION = 1`；不認得的版本整則略過 |
| 2 | 方向：0＝送方 → 收方，1＝收方 → 送方 |
| 3–18 | 工作階段 id（16 位元組） |
| 19–22 | 這個方向的序號（u32）；收端依序號重排、去重 |
| 23– | 紀錄：`[類型 u8][長度 u32][內容]`，一則可以有很多筆；不認得的類型略過 |

| 送方紀錄 | 內容 | 收方紀錄 | 內容 |
|---|---|---|---|
| 1 OPEN | `{purpose, count?, bytes?, meta?}` | 16 READY | `{window, inline}` |
| 2 ENTRY | `{i, id, size, sha256, meta}` | 17 REJECT | `{reason}`（整個工作階段） |
| 3 DATA | `[索引 u32][位移 u64][資料]` | 18 HAVE | `{i, have}` 或 `{i, skip}`（大檔） |
| 4 END | `{count, manifest}` | 19 ACK | `{seq}`（累積確認，信用） |
| 5 CANCEL | `{}` | 20 DONE | `{r: [[i, 0 成功｜1 略過｜2 失敗, 原因?], …]}` |
| | | 21 FINISH | `{ok, count, reason?}` |

- **用途（purpose）**：收方以 `handle(purpose, handler)` 掛處理器，同一條通道可以同時有 Vault 同步與一般檔案佇列；沒有人處理的用途整批拒收。
- **小檔併成一則**：送方累積到 `flushBytes`（64 KB）才送一則，3,000 個小檔只有 25 則（實測）；中繼軌上事件數大減。
- **大小檔分流**：`size ≤ inline`（收方在 READY 給，預設 1 MiB）在記憶體組起來；更大的寫進處理器的 `StreamingFileStore`，送方先等 HAVE。
- **信用視窗背壓**：送方「送出但還沒被確認」的位元組不超過收方給的 `window`（預設 4 MiB）；收方**處理完**（寫進儲存、App 的監聽結束）才 ACK。收方寫得慢，送方就停。
- **清單綁定**：END 帶檔案數與 `manifest`＝依序每個 ENTRY 內容的 SHA-256；對不上回 FINISH `ok:false`，送方丟 `StreamIntegrityError`。
- **完成語意**：每個檔案校驗通過、App 的 `onEntry` 成功才回 DONE 成功；送方 `onEntryDone` 逐一收到，中途斷線丟 `StreamInterruptedError`（附已有的結果），其餘下次再送。
- **舊客戶端**：`FileTransfer` 只理 0xCF，看到 0xCB 什麼都不做（有測試）；反過來 `StreamTransfer` 也不理 0xCF。收到比自己新的版本整則略過。
- **加密**：與 ADR 0009／0015 相同——P2P 軌靠 DTLS（指紋經 NIP-59 信令交換）、中繼軌每框 NIP-59；要逐則前向保密就疊在 `secureChannel` 上（有測試：DataChannel 上看不到明文）。通道本身已認證對方公鑰，工作階段綁在通道上。

### §2 大檔串流寫入與續傳（G6）

- `StreamingFileStore` ＝ `PartialFileStore` 加 `readRange(id, offset, length)`，選配 `commit(id, info)`。暫存鍵是**內容的 SHA-256**：同一份內容在任何工作階段、任何重開之後都對得上。
- **續傳**：收方看暫存已有多少（`size`），回 HAVE `{have}`，送方從那裡接著送；已有的部分以 `readRange` **分段重算雜湊**，不整檔讀進記憶體。已有的比宣告的大小還多就清掉重來。
- **校驗後原子提交**：收滿 → 比 SHA-256 → 不符就 `delete`、回報失敗；相符 → App 的 `onEntry`（可以 `readRange` 讀暫存）→ 成功才 `commit`（例如暫存檔改名到目的地；沒實作就 `delete`）。`onEntry` 丟例外＝失敗，**暫存保留**，下次送同一份內容 HAVE 回 `size`，不必重傳。
- **上限**：有儲存時單檔預設 64 GiB（`DEFAULT_MAX_STREAM_ENTRY_BYTES`，可調），不再受記憶體限制；沒有儲存的處理器只收內嵌大小以內的檔案。
- **記憶體恆定**：收方＝亂序緩衝（≤ 視窗＋2 MB）＋一個內嵌小檔；送方＝一段讀取＋未確認的位元組（≤ 視窗）。測試以產生器模擬 16 MB 與 128 MB 的檔案，量測兩端峰值（§測試）。
- `FileTransfer`／`P2PFileQueue` **不動**：線路格式、行為、主入口打包都不變（舊的收方只懂 0xCF）。新程式傳大檔改用 `StreamTransfer`／`P2PStreamQueue`。

### §3 `P2PStreamQueue`：可持久化的「等 P2P 才送」

- 語意同 `P2PFileQueue`：只在 P2P 打通時送（`allowRelay` 才走中繼軌），`flush(peer)` 或對方連上來時觸發；同一個對象排著的檔案一條串流送完。
- 佇列寫進注入的 `TransferQueueStore`（與 `SyncStateStore` 同形狀）；重開後 `restore()` 讀回，送之前以 `open(file)` 重新打開檔案（打不開＝那一筆失敗、移出）。收方的暫存還在就從斷點續傳。
- `enqueue` 的 Promise 在對方處理完（成功或「已經有了」）時完成；`onSettled` 給重開後沒有 Promise 的那些。

### §4 協調器整合：批次模式與大檔直送

設定 `peers: VaultPeerLink` 才啟用；沒給就是 ADR 0025 的行為（既有測試全部照過）。

- **`VaultPeerLink`**：`devices()`、`open(deviceId, {fresh?})`、`onIncoming`。`peerNodeLink({ node, devices, wrap?, relayTrack? })` 用 `PeerNode` 實作：公鑰（通道已認證）對應回 deviceId，名單外的不理；`wrap` 可以疊 `secureChannel`（同一條通道只包一次）。
- **收件對象**：送出佇列的項目多了 `to`（只有這幾台要；對方的摘要或索取引起的補送）與 `got`（已經經 P2P 送到的裝置）。所有對象都 `got` 了才算送出。
- **批次模式**：待送出的版本 ≥ `bulkThreshold`（預設 10，PRD 的 N ≥ 10）時：
  - 對每一台還缺的裝置開一條批次串流，一次送完它缺的版本（版本附小檔內容）。
  - 走中繼（kind 1060）的只以 `relayBulkPerHour`（預設 20 則／小時）限速補送；少於門檻就恢復即時送出。
- **大檔內容直送**（取代「只標待 P2P」）：本機產生大檔版本時，為每台裝置排一筆持久化的直送（`x:`）；對方送來摘要、而它的版本頭裡有我們磁碟上的大檔時也排（收方已經有就回 skip）。
  - 大檔拆成兩個檔案：先送版本（不附內容），再送內容。收方併入版本後，內容已經在手上（例如只是改名）就回 skip，不重傳；版本本身一定送到。
  - 送方以 `VaultAdapter.readRange`（選配）分段讀；收方寫進 `staging`（`StreamingFileStore`；預設記憶體、單檔上限 512 MiB，要更大或跨重開續傳請給持久化的），轉接器有 `writeStream`（選配：寫暫存、比對目前內容雜湊、原子取代）就**直接從暫存串流寫進 Vault**，否則整檔讀出來經 `write`。
  - 大檔的本機雜湊也改成分段讀（有 `readRange` 時），掃描與偵測變更不再整檔進記憶體。
- **收方驗證**（與中繼收到的同一套 `validateVaultMessage`，再加上）：
  - `meta.from` 必須等於通道認證出來的 deviceId（冒名拒收）；`meta.v` 必須是 `VAULT_WIRE_VERSION`；
  - 附內容時大小、雜湊必須與版本一致；是否為大檔由大小決定，旗標矛盾拒收；非大檔不得超過檔案塊層；
  - 路徑規則（絕對路徑、`..`、`.`、空段、控制字元、反斜線）照 ADR 0025。
- 批次串流的用途名稱 `VAULT_STREAM_PURPOSE = 'cinderous/vault/1'`；每個檔案的 `meta` 是 `{ v, from, fileId, node, c }`（`parseVaultEntryMeta`）。中繼上的訊息類型與格式**沒有改**。

### §5 退路（P2P 打不通時）

| 順序 | 路徑 | 條件與限制 |
|---|---|---|
| 1 | WebRTC DataChannel | `PeerNode` 8 秒內打通 |
| 2 | 中繼軌（kind 20079，ephemeral） | 打不通時 `PeerNode` 自動改走；**不存在中繼上、不佔 4,000 顆配額**；每分鐘 200 框（≈160 KB/s）。只送小檔批次，大檔內容等真的 P2P（`relayTrack: false` 可以關掉） |
| 3 | kind 1060 限速補送 | 對方不在線、或兩台從不同時上線：每小時 20 則（7 天 3,360 則，低於 4,000） |

- 連不上、被拒、或一個都沒送成：該裝置指數退避（30 秒起、最長 30 分鐘）。對方送來摘要、主動連上來時立刻重試；背景維護（`tick`）也會照退避重試。
- 對方在既有的通道上拒絕（例如它的協調器重開過、還沒在那條舊通道掛處理器）：下次 `open(…, {fresh: true})`，`peerNodeLink` 關掉舊通道重連，對方會在新通道收到 `onPeer`。
- 對方是舊版（沒有批次）：批次開不起來 → 退避 → 由第 3 層收斂（有測試）。
- 中繼拒收 kind 1060（ADR 0027）時，有 `peers` 就只要有待送出就進批次模式。

### §6 完整性與防濫用

| 威脅 | 防護 |
|---|---|
| 內容被改、假雜湊 | 每檔 SHA-256；不符不交出、暫存刪除 |
| 漏掉或塞入檔案 | 每方向序號＋END 的檔案數與清單雜湊 |
| 越界路徑、冒名 | ADR 0025 的路徑驗證；`from` 綁定通道認證的裝置；名單外的公鑰不理 |
| 無限大宣告 | 單檔上限（有儲存 64 GiB、沒有＝內嵌上限）；超過的不配置、回 skip；檔案數上限 10 萬；`meta` ≤ 64 KB；Vault 另有「非大檔 ≤ 檔案塊層」與大小／雜湊須與版本一致 |
| 記憶體耗盡 | 信用視窗；亂序緩衝超過視窗＋2 MB 就中止；同時最多 8 個收方工作階段；記住的已結束工作階段 1,024 個 |
| 協定錯亂（位移不連續、序號跳號、超過宣告大小） | 整個工作階段中止（REJECT），那個檔案的暫存刪除 |
| 同一份內容兩個工作階段同時寫 | 以內容雜湊互斥，第二個回 skip（失敗、稍後重試） |
| 卡住 | 雙方閒置逾時 60 秒（收方處理大檔時每 20 秒送一則心跳）；收方逾時保留暫存 |

## 測試

- `tests/transfer/stream.test.ts`（23）：3,000 個小檔一條串流；亂序＋重複（兩個方向）；空批次、空檔案；非同步產生器；accept 的 skip／拒收；沒有處理的用途；對方不在（逾時）；大檔寫進儲存、校驗後才 commit；**中途斷線 → 換通道（等同重開）只補剩下的**；收方監聽失敗 → 暫存保留、再送不重傳；大檔 skip；沒有儲存時大檔回失敗、同批小檔照收；`hashSource`；**記憶體恆定（16 MB vs 128 MB）**；**背壓（收方寫得慢）**；惡意對端：假雜湊（小檔與大檔）、超過宣告大小、超大宣告、檔案數超過上限、序號跳號、位移不連續、清單雜湊不符、灌爆信用視窗、太多工作階段；**線路相容**（新版本略過、舊 `FileTransfer` 不回應、互不干擾）；自我審查補的：兩個對端同時送同一份大檔到共用暫存、序號跳太遠。
- `tests/transfer/stream-queue.test.ts`（5，真的 `PeerNode`＋假 WebRTC）：flush 後一條串流送完；只打得通中繼就留著、`allowRelay` 才送；**送到一半斷線、送方重開（restore＋open）→ 收方從斷點續傳**；對方回報暫時的失敗 → 留在佇列、下次成功；重開後檔案不見了 → 失敗、移出。
- `tests/transfer/stream-subpath.test.ts`（3）：子路徑匯出、零 Node、主入口不含批次串流。
- `tests/sync/vault/p2p.test.ts`（13）：**2,000 檔的新裝置加入**（中繼上的版本訊息 20 則，其餘經 P2P）；一次改 300 個檔案；少量變更照舊走中繼；**完全打不通 → 限速補送（任何一小時 ≤ 門檻＋20）最後收斂**；對方是舊版 → 退避、中繼收斂；只打得通中繼軌 → 小檔照走、大檔等 P2P；**大檔直送＋writeStream 分段寫入**；**傳到一半斷線 → 續傳不重傳**；**收方重開後續傳**；**送方重開後照送**；惡意對端（越界路徑、絕對路徑、反斜線、冒名、雜湊／大小不符、大檔旗標矛盾、串流層假雜湊）與合法對照。
- `tests/sync/vault/p2p-peernode.integration.test.ts`（3）：真的 `PeerNode`＋`secureChannel`：40 個檔案經批次送達、DataChannel 上沒有明文；打不通時走 kind 20079；`peerNodeLink` 不理名單外的公鑰。
- `tests/sync/vault/property-p2p.test.ts`：**延伸既有的隨機性質測試**，預設 16 個種子 × 150 個操作（`VAULT_P2P_PROPERTY_SEEDS` 可加大），固定種子可重現：裝置之間有 P2P（離線時通道斷）、**跑到一半加入一台空的新裝置**、偶爾寫**超過檔案塊層的大檔**（奇數種子的轉接器沒有 `readRange`／`writeStream`，走整檔的退路）。檢查同樣的性質（檔案樹逐位元組一致、沒有等待中／內容未到／待送出／待直送、沒有錯誤、寫過的內容都還在），另外確認真的走到大檔與新裝置。發版前另外跑過種子 1–64 與 1000–1039；無 P2P 的 `property.test.ts` 跑過 150 個種子。
- 既有的 `property.test.ts`（40 種子、無 P2P）與協調器的 38 個情境測試照過：沒有 `peers` 時行為不變。

## 實測

（Node 22，Windows，記憶體通道；只作量級參考）

- 3,000 個小檔一條串流：約 50 ms；送方 25 則、收方 7 則訊息。
- 大檔：16 MB 約 220 ms（72 MB/s）、128 MB 約 2 s（65 MB/s，瓶頸是兩端的 SHA-256）。收方緩衝峰值兩者都是 65,553 B，送方未確認峰值兩者都約 1.0 MB——檔案大 8 倍，峰值不變。
- 協調器：2,000 個檔案的 Vault 加入新裝置約 0.2 s（一條 P2P 通道、約 1 MB）。
- 打包（esbuild 壓縮）：主入口 152.7 KB（gzip 55.8 KB）與 `./sync` 80.5 KB **不變**；`./transfer` 13.9 → 34.3 KB（gzip 6.0 → 12.4 KB）；`./sync/vault` 111.0 → 138.4 KB（gzip 41.1 → 50.7 KB）。

## 自我審查

實作完成後另請一位審查者（唯讀）針對資料遺失、完整性、DoS、續傳一致性、死結審一輪；加上延伸的性質測試（種子 17–64 在修正前抓到一個種子收斂失敗）。發現並修正：

1. **（高）共用暫存被兩個工作階段交錯寫**：「同一份內容正在接收」的互斥原本只在單一 `StreamTransfer`（一條通道）裡；協調器的 staging 是所有通道共用的，兩台裝置同時直送同一個大檔時 append 會交錯，而校驗算的是各自收到的位元組，會通過卻寫進壞內容。改成以**儲存**為單位的模組層級互斥（`WeakMap<StreamingFileStore, Set>`），第二個回失敗、稍後再送（有測試）。
2. **（高）收方沒真的併入卻回成功**：協調器已停止、訊息驗證不過時原本 `return`，被當成成功，送方就把佇列項目移除。改成丟例外（回報失敗）；暫停中（沉睡裝置）也不收。
3. **（高）大檔寫入失敗仍回成功、直送被記成已完成**：`#materialize` 失敗會被 `#converge` 吃掉（記進 `#failed`），暫存隨即刪掉，送方又把它記成「這次執行不必再送」。改成：內容沒有真的落地（等父版本、寫入失敗、仍是版本頭卻不在磁碟上）就回失敗、暫存保留；拿掉「已送達就不再排」的記憶（對方已有只多一次 HAVE skip）。
4. **（高）大檔預設暫存在記憶體、上限 64 GiB**：沒給 `staging` 時單檔上限改為 512 MiB（`DEFAULT_MEMORY_STAGING_MAX_BYTES`）。
5. **（中）分段讀的大小與雜湊可能不一致**：分段雜湊的路徑以 stat 的大小當版本大小，檔案在讀的途中被改時兩者對不上，收方永遠校驗不過。現在讀到的長度與 stat 不同就這次不收，等下一次掃描。
6. **（中）亂序緩衝可以被空訊息撐大**：每則訊息至少以標頭大小計入，序號不能比下一個期待的多 1,024 以上（否則中止，有測試）；送方的控制訊息緩衝也加上 4 MB 上限。
7. **（中）送方等來源太久被對方判閒置**：例如協調器正在把大檔寫進磁碟，產生器等 `#run` 超過 60 秒。送方在等下一個檔案時每 20 秒送一則空訊息當心跳。
8. **（中）`P2PStreamQueue` 遇到暫時的失敗就永久移出**：改成留在佇列、計次，連續 3 次或永久性的原因（拒收、太大、沒有儲存、檔案不見了）才移出（有測試）。
9. **（低）** 工作階段結束後不再重設計時器；`cinderous relay start --max-file-mb` 也要白名單或 `--open-file-relay`（與部署同一條規則，ADR 0027）。
10. 開發過程中另外抓到並修正：`MemoryStreamingStore.readRange` 原本每次把整個檔案接起來（O(n²)）；直送的「只有版本」的項目被算成進度，對方一直回失敗時會熱迴圈（記憶體爆掉）——現在只有真的讓工作變少的才算進度；對方協調器重開後在舊通道上沒有處理器（`fresh` 重連）。

審查者確認**沒有死結**：`#run` 佇列內沒有等網路的工作，StreamTransfer 的處理與 App 的監聽不互等。

## 已知限制

- 大檔的**合併**（兩邊都改了同一個大檔、要產生衝突副本）仍要整檔進記憶體（`planMerge` 吃位元組）；只有「套用到磁碟」這一步是串流的。
- 轉接器沒有 `writeStream` 時，收到的大檔整檔讀進記憶體再寫；沒有 `readRange` 時，送大檔整檔讀一次。Obsidian 桌面版可以用 `adapter` 的檔案 API 實作這兩個；行動版視平台能力而定。
- `applyRemote`（外掛自己套用遠端變更）不經手串流寫入的大檔：大檔直接走 `writeStream`（大檔不會在編輯器裡開著）。
- 新裝置加入時，歷史很長的檔案仍依 ADR 0025 以「缺父版本 → 索取」一層一層補（每層一輪批次）；補齊前依 `orphanAfterMs` 的規則處理。
- 多台裝置都有同一份大檔時，可能各自直送一次（收方對已經有的回 skip，只多一次 ENTRY／HAVE 往返；同時送達時以內容雜湊互斥）。
- 批次模式下，對「永遠不上線」的裝置，直送項目排到 30 天後清掉；之後它上線送摘要時會再排。
- **`peers.devices()` 必須是這個 Vault 的全部其他裝置**：佇列項目在 `devices()` 裡每一台都經 P2P 收到後就算送出，不在名單裡、只走中繼的裝置要等下一次摘要交換才補到。
- 持久化的 `staging` 裡，失敗或中斷留下的暫存不會自動清（它們是續傳用的）；外掛可以依修改時間清理很舊的暫存檔。
- 中繼補送與 P2P 批次可能同時送同一個版本（重複但冪等）。
- 信任模型與 ADR 0025 相同：名單內的裝置是可信的；被入侵的裝置能送出合法但惡意的內容（只是不能越出 Vault、不能冒名其他裝置）。

## Consequences

- ＋ 新裝置加入、大量變更不再撞中繼配額；大檔真的會同步，而且記憶體恆定、斷線與重開都能續傳。
- ＋ 不改中繼、不改任何既有事件或訊框；主入口不變大；沒有 `peers` 時行為與 v0.22 相同。
- － 新的線路格式（0xCB 版本 1），日後改格式要升 `STREAM_WIRE_VERSION`。
- － `./transfer` 與 `./sync/vault` 各大約多 20–27 KB（壓縮後 6–10 KB）。
- － 外掛要提供 `PeerNode`、裝置公鑰對照、（建議）持久化的 `staging` 與 `readRange`／`writeStream`，才拿得到全部好處。
