# 0079. 歷史版本公開 `absorbed`：被收進另一個檔案的刪除不是使用者刪除

- 狀態：**已接受（Accepted，2026-10-13）**——CinderSync 自動化實機驗證時找到（使用者 2026-10-13「全都修正」）；實作於 v0.57.1
- 日期：2026-10-13
- 對應：ADR 0059（同路徑新建的合併）、0063（用戶端版本歷史）、G10（路徑相撞、內容相同的收斂）；CinderSync ADR 0070

## Context
兩台裝置各自建了同一篇筆記（同路徑、同內容）時，協調器把其中一個檔案收進另一個（G10 收斂，或 ADR 0059 的合併），被收掉的那個檔案在版本圖上是一個刪除版本。

協調器內部早就在歸檔項目上標了 `absorbed`（`deletedFiles()` 據此不列這種檔案），但 `history(path)` 回傳的 `VaultHistoryEntry` 沒有這個欄位。實機（2026-10-13）CinderSync 的檔案歷史因此顯示「已刪除、0 B」——使用者沒有刪任何東西，內容也還在留下的那個檔案裡，看了會以為資料不見。

## 決策
- `VaultHistoryEntry` 加 `absorbed?: true`：只有被收進另一個檔案的刪除版本才有這個欄位，其他版本沒有（不是 `false`），既有應用的比對不受影響。
- 判斷沿用內部既有的規則（fold 的版本識別碼，或 dedupe 的確定性識別碼），不新增判斷。
- 這種版本照舊是 `deleted: true`：版本圖上確實是刪除，還原與時間點計算不變；只是介面應該說成「已合併」而不是「已刪除」。

## 試過、沒有採用
- **讓這種版本不出現在 `history()`**：歷史要完整反映版本圖，時間點還原也會經過它；隱藏反而讓「這個檔案為什麼不見了」無從查起。
- **把 `deleted` 改成 `false`**：會讓時間點還原與 `deletedFiles()` 的語意不一致。

## Consequences
- ＋ 應用可以把這種版本顯示成「已合併」，不再誤導成資料被刪。
- ＋ 只加選用欄位，相容既有應用。
- 驗證：`tests/sync/vault/history-sync.test.ts`〈被收進另一個檔案的刪除版本（SDK ADR 0079）〉；CinderSync `tests/ui/history-modals.test.ts`〈被收進同路徑另一份的刪除版本〉。
