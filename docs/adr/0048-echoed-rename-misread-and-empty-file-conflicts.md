# 0048. 衝突副本來回震盪：自己套用的改名的回音被誤認成使用者改名；空檔不產生衝突副本（v0.37.1）

- 狀態：**已接受（Accepted）**——2026-10-02，使用者核准修正與空檔規則；實作於 v0.37.1
- 日期：2026-10-02
- 相關：本 repo ADR **0025**（協調器、§4 確定性合併、§6 回環抑制、路徑相撞）、**0035 §G10**（同內容的路徑相撞直接收斂）、
  **0046**（衝突 callout）、0047（排除範圍）；CinderSync 的 Vault 監聽（`vault-watcher.ts`，每個路徑防抖 500 ms、改名帶舊路徑）與
  寫入前備份（`vault-backup.ts`）

## 現象（使用者實機，2026-10-02）

同一台電腦上的兩個 Vault（裝置名稱都是 `stoakc`），配對前就各自擁有同一批檔案（疑似複製資料夾），部分同路徑檔案內容不同、**沒有共同祖先**。
配對後 10 分鐘暖機時段兩邊都在線：

- `歡迎.md` 兩邊只差最後一個字元 → 產生 `歡迎 (衝突-stoakc-20261002-013556).md`。
- **衝突副本來回震盪**：兩邊的寫入前備份（`.trash/cindersync-backup/`）顯示，01:35:56 到 01:37:08 UTC 約 70 秒內，這份副本在 A 被覆寫 14 次、
  B 12 次，內容在兩個版本（223 B／228 B，差一個 `p`）之間交替，每次間隔約 2–3 秒，最後才停下，兩邊最終逐位元組相同。
- `2026-10-02.md`：一邊是 Obsidian 剛建立的 0 位元組每日筆記、另一邊有內容 → 產生一份 0 位元組的衝突副本（沒有意義）。
- 兩邊顯示的衝突數量不同（1 vs 2）：ADR 0025 已知限制（只有做合併的那台收到 `conflict` 事件），外掛改依磁碟計數，本 ADR 不處理。

## 重現（TDD Red）

測試替身 `MemoryVault.watch()`（`tests/sync/vault/harness.ts`）照 CinderSync 的監聽行為產生回音：協調器**自己的**寫入、刪除、改名
一樣觸發事件，每個路徑防抖後通知（改名帶最早的舊路徑、取消舊路徑待送的通知）。兩台各自在配對前就有 `歡迎.md`（差一個字元）、
裝置名稱相同、同時啟動、都在線，計算每台寫入衝突副本的次數（v0.37.0）：

| 網路延遲上限 | 回音防抖 | 每台寫入副本的次數 | 結果 |
|---|---|---|---|
| 0 ms | 500 ms | **約 400 次**（模擬 200 秒仍未停，每 500 ms 一次，兩個內容交替） | 不收斂 |
| 50／300 ms | 500 ms | 1–9 次 | 收斂，但 12 次中 **12 次有一方的內容從 Vault 消失**（外掛的寫入前備份裡還有） |
| 3,000 ms | 500 ms | 1–4 次 | 收斂，6 次中 3 次有一方的內容消失 |

沒有回音時（既有的測試替身）每台只寫一次——所以既有的性質測試從來沒抓到。使用者實機的週期（2–3 秒）＝中繼往返＋500 ms 防抖；
最後停下來、兩個內容都還在，是時序剛好讓兩次回音落在同一個防抖窗裡（加上外掛備份這道安全網），不是協調器保證的。

## 根因

ADR 0025 §6 的回環抑制靠內容雜湊：「套用遠端寫入後索引記下雜湊，外掛隨後通知的變更讀出來相同就什麼都不做（**改名、刪除也一樣：
索引已經是新路徑**）」。括號裡的假設在一種情況下不成立：**改名的舊路徑在同一輪就被另一個檔案佔用**。

路徑相撞（ADR 0025）正是這種情況：留下的檔案 X 要用 `歡迎.md`，輸的 Y 在磁碟上佔著它 → 協調器先 `rename 歡迎.md → 歡迎 (衝突-…).md`（Y），
再 `write 歡迎.md`（X）。500 ms 後外掛送來改名的回音 `notifyLocalChange('歡迎 (衝突-…).md', 'rename', '歡迎.md')`，`#ingestRename`：

1. 用舊路徑查索引 → 查到的是**剛寫進去的 X**（不是被改名的 Y），而且 X 的磁碟路徑正是舊路徑 → 認定「使用者把 X 改名成副本」；
2. 新路徑上有另一個追蹤中的檔案（Y）→ 走「改名蓋掉了另一個檔案」→ **Y 加一個本機刪除版本**；
3. X 加一個本機版本：路徑＝副本、內容＝副本上讀到的（Y 的內容）；接著 `歡迎.md` 上 X 的內容變成一個沒追蹤的檔案 → 新建檔案 Z。

這三個版本送到另一台，另一台的套用又是一次「改名＋寫回原路徑」，它的回音再被同樣誤讀……兩台輪流把兩份內容寫進同一個副本路徑
（裝置名稱相同、`pathAt` 同一秒，副本檔名也相同，所以是**原地覆寫**、內容交替；名稱不同時則是副本的副本的副本）。
Y 的刪除版本與 X 的「修改」並行時，合併規則照設計保留修改、刪掉沒被改的那一方——誤讀造成的「修改」其實帶走了另一方的內容，
所以有時一方的內容就此從 Vault 消失。

衝突副本本身的版本 id **早已是由輸入確定性導出的**（合併副本 `deterministicId('copy', fileId, source, hash)`、相撞改名
`deterministicId('collide', fileId, …heads, newPath)`、G10 `deterministicId('dedupe', fileId, …heads)`）——問題不在副本的確定性，
而在協調器把自己的動作當成了使用者的新動作，每一輪都產生新的、真的不一樣的版本。

互換名字（成環，ADR 0025 §6 的暫存名）有同一個問題：三次改名的回音裡舊路徑都已經被另一個檔案佔用。

## 決策

### 1. 修正：舊路徑被另一個檔案佔用時，改名的回音不是改名（`#ingestRename`）

改名通知 `(from → to)` 中，若 `to` 是索引裡**另一個**檔案正追蹤著的路徑，而且

- 它的內容沒變（讀出的雜湊＝索引記的），**或**
- `from` 上那個檔案根本還在（大小與修改時間相同，或重算雜湊相同），

就不是使用者的改名：兩個路徑各自重新比對（`#ingestPath(from)`、`#ingestPath(to)`），回環抑制照常生效。

| 情況 | v0.37.0 | v0.37.1 |
|---|---|---|
| 自己套用的改名的回音、舊路徑被留下者佔用（路徑相撞、互換名字） | 誤認改名：刪掉被改名的檔案、把它的內容記到留下者名下 | 兩邊各自比對：都沒變，**什麼都不送** |
| 回音到達前使用者改了舊路徑上（留下者）的內容 | 同上，而且使用者的修改被當成新檔案 | 是留下者的一次修改（測試釘住） |
| 回音到達前使用者改了副本 | 同上 | `from` 上的檔案還在 → 是副本的一次修改 |
| 使用者真的把 A 改名蓋掉另一個追蹤中的 B（內容不同、`from` 已不在） | A 改名、B 刪除 | **不變** |
| 外部工具以相同內容蓋掉 | A 改名、B 刪除 | A 刪除、B 不變（內容一樣，只有身分不同） |

（Obsidian 本身不允許改名到已存在的檔案；後兩列只會來自外部工具。）

### 2. 新規則（使用者核准）：空檔不產生衝突副本

空檔（0 位元組）沒有任何內容會遺失，為它產生衝突副本只會留下一個沒有意義的檔案（實機的 `2026-10-02 (衝突-…).md`）。

- **路徑相撞**（`#resolveCollision`）：留下者改成「依 `pathAt`、`fileId` 排序後**第一個非空的**」；其餘空檔的輸家與 G10 同樣處理——
  加一個刪除版本（同一個確定性 id `deterministicId('dedupe', fileId, …heads)`），**不產生副本、不發 `conflict` 事件**。
  磁碟上那份空檔經由刪除版本以前置條件（內容仍是空的）移除，再寫入留下者——不做 G10 的「磁碟交給留下者」，因為內容不同：
  若移交後使用者在空檔裡打字，這次編輯會以留下者的版本為父版本，等於覆蓋留下者的內容。
  全部都是空檔 → 雜湊相同，照 G10 收斂成一份空檔。
- **同一個檔案的並行版本**（`planMerge`／`mergeTwo`）：三方合併合不起來（或缺共同祖先）、其中一方是空檔 → 採用有內容的一方，
  **不產生副本、也不放 callout**（ADR 0046）、不發事件。三方合併合得起來時仍以合併結果為準（例如一方清空、另一方只在別處加行，
  `merge3` 的乾淨結果照舊）。
- **確定性**：只看版本資料（大小）與既有的排序鍵，每台裝置對同一組輸入得到同一個結果；刪除版本的 id 由輸入決定，各台各自處理會得到同一個版本。
- **不遺失**：被收掉的只有 0 位元組的版本。移除空檔之前若使用者剛好打了字，前置條件不符 → 收成本機修改 → 一刪一改保留修改 →
  它不再是空檔，下一次相撞照常產生副本（測試釘住）。
- **取捨**：同一個檔案一台清空、另一台並行修改時，清空會被「撤銷」（留下有內容的一方）。沒有任何內容遺失，使用者可以再清空一次；
  比起留一個空的衝突副本或空白的 callout，這是較不意外的結果。

### 3. 評估但不做：「一方是另一方的前綴」

實機的 `歡迎.md` 兩份只差結尾的一個 `p`，看起來「較長的一方包含較短的一方」，直接採用較長的就不必產生副本。**不做**：

- 沒有共同祖先時，無法分辨「一方在結尾加了字」與「一方把結尾刪了」——後者採用較長的一方等於無聲撤銷使用者的刪除；
- 有共同祖先時，三方合併本來就能處理單純的附加（這個規則只會在三方合併失敗時生效，而那正是兩邊都改了的情況）；
- 對二進位檔（例如被截斷的下載）更危險。

空檔是前綴規則中唯一「不可能誤判」的特例（空檔不含任何使用者內容），所以只做空檔。

## 收斂與不遺失（摘要，沿用 ADR 0025 的框架）

1. **協調器自己的動作不再產生版本**：每一個套用（寫入、刪除、改名）之後索引已經記下結果；回音要嘛在新路徑上看到索引裡的同一個內容，
   要嘛在舊路徑上看到另一個追蹤中、沒變的檔案——修正後兩者都走「各自比對」，雜湊相同、什麼都不做。所以版本圖裡只有使用者的版本與
   協調器以確定性 id 產生的版本（合併、相撞改名、G10／空檔的刪除）。
2. **確定性**：路徑相撞的處理只看各檔案目前的版本（`pathAt`、`fileId`、大小、雜湊）；同一組輸入在每台得到同一個 id。
   不同裝置在不同時間處理（看到的版本頭不同）時產生的版本是並行的版本頭，由 ADR 0025 的確定性合併與涵蓋規則收斂到同一個結果。
3. **有界**：沒有回音產生的新版本，每台的磁碟操作只跟著「新知道的版本」走。配對前就有檔案、N 台同時上線時：每台對每個衝突副本
   **最多寫一次**；原路徑最多寫 N − 1 次（每知道一個更早佔用的檔案就換一次留下者）。由測試與性質測試釘住。
4. **不遺失**：各自比對只會把**磁碟上真的不見**的檔案記成刪除；被收掉的只有內容相同（G10）或 0 位元組（本 ADR）的版本。

## 相容

- 線上格式不變。修正在**收到回音的那台**：仍是 v0.37.0 的裝置自己的回音照樣會被誤讀，所以**每一台都要升到 v0.37.1**。
- 空檔規則與 v0.37.0 混用：舊版以 `pathAt` 決定留下者，可能把有內容的一方改名成副本、而新版把空檔刪掉——結果是有內容的那份在副本路徑上、
  原路徑沒有檔案（不遺失，但不好看）；全部升級後新產生的相撞不再如此。合併的空檔規則在舊版那台合併時不生效（照舊產生空的副本）。

## 未處理

- **G10 的刪除版本比留下者先到**（ADR 0035，既有）：收到「同內容收斂」的刪除版本時還不知道留下者，就先移除磁碟上那一份，留下者到了再寫回
  同一份內容（一次移除＋一次寫入，內容不變；外掛會為移除做一次備份）。要避免得延後移除、等留下者，牽涉「留下者永遠不來」時的清理，另案。
- 衝突數量兩邊不同：ADR 0025 已知限制，CinderSync 改依磁碟計數。
- `#freePath`（副本名稱已被佔用時加 ` 2`）看本機磁碟，不同裝置可能選不同名字——產生的是並行的改名版本，由 rename-rename 規則收斂，不會震盪。

## 給 CinderSync 的影響

- **不需要改外掛程式**：外掛的監聽（協調器自己的寫入也通知、改名帶舊路徑、500 ms 防抖）完全符合 ADR 0025 §6 的契約，錯在 SDK 的假設。
  升級 `@cinderous/client` 到 v0.37.1 即可；每台裝置都要更新。
- 寫入前備份（`.trash/cindersync-backup/`）這次確實是安全網：v0.37.0 下被誤刪的一方內容都還在備份裡。建議保留。
- 已經產生的空衝突副本（例如 `2026-10-02 (衝突-…).md`）不會自動清掉，使用者可以直接刪除。

## Consequences

- ＋ 配對前就有不同內容的同路徑檔案時，衝突副本只產生一次、不再來回覆寫，也不再出現一方內容消失。
- ＋ 協調器自己的改名的回音在所有情況下都是無操作（含互換名字）。
- ＋ 空白的每日筆記之類不再產生空的衝突副本。
- － 一台清空、另一台並行修改時，清空不會保留（見 §2 取捨）。
- － `./sync/vault` +450 B（gzip +146 B）。
