# 0125. 連不上時分辨「邊緣代答」與「網路斷了」

- 狀態：**已接受（Accepted，2026-10-29）**——使用者 2026-10-29 選「做在 SDK 的 RelayPool」（Cinderous 即時通訊的設計缺口第 3 項）
- 日期：2026-10-29
- 對應：SDK ADR 0097（中繼額度用完送 NOTICE＋1013）、0108（1013＝暫時不能用）、0038 P0-C（`onRelayReject`）；Cinderous ADR-0395（客戶端看懂 1013）

## Context

SDK ADR 0108 讓連線池看懂 1013：中繼自己的額度用完時，先接受升級、送 NOTICE，再以 1013 關閉。連線池據此標記「暫時不能用」，5 分鐘後才重連，應用也能說出原因。

但 Cloudflare **Workers 免費方案的每日請求數**（10 萬次，UTC 00:00 重置）用完時，Worker 根本不會執行，邊緣直接回 **Error 1027**（[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)）。這時送不出 NOTICE，也送不出 1013，上面那條路走不到。瀏覽器的 WebSocket 只看得到 1006，跟網路斷了一模一樣。結果是：

- 使用者整天看到「已斷線，重連中…」，以為是自己的網路；
- 連線池照一般退避，每 10 秒重連一次，打一整天。

Cinderous 錨點 2 一天約有 4.6 萬次背景請求（Cinderous ADR-0394），離上限不遠。

## Decision

### 1. 判斷方式：對同一個網址抓兩次 NIP-11

NIP-11 規定中繼的資訊文件要帶 CORS 標頭，SDK 的 Worker 也一定帶。邊緣的錯誤頁是 Cloudflare 回的，不會帶。所以：

| 誰在回答 | 一般 `fetch` | `no-cors` 的 `fetch` | `probeRelayEdge` |
|---|---|---|---|
| 中繼 | 成功 | 成功 | `relay` |
| 邊緣代答（例如 1027） | **失敗** | **成功**（不透明回應） | `edge` |
| 網路斷了 | 失敗 | **失敗** | `unreachable` |

- 不在瀏覽器時（Node 不檢查 CORS），第一次請求就會成功，改看回應有沒有 `Access-Control-Allow-Origin`。
- 每次請求最多等 10 秒（`EDGE_PROBE_TIMEOUT_MS`）。

### 2. 連線池什麼時候探測

- 只在**還沒連上就斷**、而且中繼沒給關閉碼（一般斷線）時才計數，**連續 2 次**才探測（`afterFailures`）。連上過就歸零。
- 同一座**最多 5 分鐘一次**（`minIntervalMs`）。每次花兩個 HTTP 請求，額度用完時這些也是請求。
- 判定 `edge` 就**照 1013 處理**：
  - `onRelayReject`：`source: 'probe'`、`kind: 'unavailable'`、`token: 'edge'`（`EDGE_ANSWERED_TOKEN`）、`reason` 是 `EDGE_ANSWERED_REASON`；
  - 整座標成暫時不能用，用跟 1013 同一個冷卻（`unavailableMs`，預設 5 分鐘）；
  - 已排好的重連延到標記過期。
- 探測回來之前已經連上，或連線池已經關了，結果就不用。

### 3. 預設開或關

- 用預設的 WebSocket、而且有全域 `fetch` 時**預設開啟**。
- 注入了 `createSocket`（測試或自訂傳輸）時**預設關閉**，要明確給 `edgeProbe` 物件才開。自訂傳輸不見得有對應的 HTTP 網址，測試也不該碰真的網路。
- `edgeProbe: false` 關閉。

### 4. 不做的事

- **不把 `edge` 說成「額度用完」**：那只是最可能的原因。Worker 當掉（1101）、公司的攔截代理也是「主機有回應、回答的不是中繼」。原因字串寫「most likely」，應用的文案也要這樣寫。
- **不等到 UTC 00:00 才重連**：判斷可能錯，5 分鐘一次已經把每天幾千次重連降到兩三百次。
- **`edge` 不放進中繼的詞元表**（`RELAY_REJECT_TOKENS`）：那張表是中繼會說的話的契約（每個詞元都要有一句拒收訊息用到）。這是連線池自己的判斷。

## Consequences

- 正面：
  - 每日請求數用完時，應用第一次說得出「中繼主機有回應，但沒有提供服務」，不再跟斷網混在一起。
  - 用完的那段時間，重連從每 10 秒一次降到每 5 分鐘一次。
  - 四款遊戲、兩個外掛、Cinderous 都在 Cloudflare 上連線，升版就有。
- 負面 / 殘餘：
  - **沒看過真正的 1027 回應**。要看到就得把一座錨點的當日額度燒光、讓它停擺一天，所以沒做。驗證用的是模擬：本機三個假目標（帶 CORS 的中繼、回 429 不帶 CORS 的「邊緣」、沒人聽的埠），在 headless Chrome 裡實測過上表的三列，WebSocket 兩種失敗都是 1006。
  - 網路斷了也要多花兩個 HTTP 請求才判定 `unreachable`（每 5 分鐘最多一次）。
  - 不帶 CORS 的第三方中繼會被誤判成 `edge`。NIP-11 規定要帶，實務上影響小；誤判的代價是 5 分鐘才重連一次。
- 驗證：
  - `tests/edge-probe.test.ts` 13 個測試：
    - 網址換算；
    - 五種回應的判定；
    - Node 的 `fetch` 對真的 HTTP 伺服器（帶 CORS／429 不帶／沒人聽）；
    - 連線池的觸發條件、標記與延後重連、頻率上限、探測中途連上、預設開關。
  - 全套 3338 個通過。
  - 破壞測試 8 項，最後全部抓到。第一輪有一項「連上時歸零」沒抓到：查出那行是多餘的（連上過再斷時，斷線處理本來就會歸零），已拿掉，改破壞真正負責歸零的那一行。
