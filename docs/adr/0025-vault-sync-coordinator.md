## Context

`./sync` 提供的是零件：快照、檔案塊、三層分流、行級三方合併、墓碑、水化。兩個 Obsidian 外掛（CinderSync、Cinder Coffice 內建同步）都需要「整個資料夾」層級的編排，而且兩者都不自己實作同步核心：

- 路徑 → 版本的索引；merge3 需要的共同祖先要有人保存；
- 本機變更偵測、送出佇列（離線累積、重連補送、失敗退避、重啟後續傳）；
- 改名要是一個操作（不能變成「刪舊檔＋建新檔」，否則另一台同時對舊檔的修改會遺失或變成重複檔案）；
- 套用遠端變更、回環抑制（自己寫進去的遠端內容不能又被當成本機變更送出）；
- 刪除用墓碑；無法合併時產生衝突副本並回報；**絕不無聲覆蓋或遺失資料**；
- 大檔（超過檔案塊層）這一批只定義狀態與介面，P2P 批次串流是第 3 批（ADR 0021〈後續〉#2）。

外掛跑在 Obsidian 行動版（沒有 Node），每台裝置各有一把身分金鑰（CinderSync ADR 0003），私鑰不交出（ADR 0023）。

## Decision

### §1 新子路徑 `@cinderous/client/sync/vault`，零 Node

- 放在新子路徑而不是 `./sync`：協調器連同 NIP-59 與 SHA-256 打包後約 110KB，放進 `./sync` 會讓只用零件的應用（遊戲、Cinderous）也變大。主入口與 `./sync` 的原始碼都沒有改動，打包大小不變（見〈實測〉）。
- `tests/sync/vault/subpath.test.ts` 以 esbuild 實際打包：模組圖裡沒有任何 Node 內建模組（比照 `./deploy/cloudflare-api` 的守門）、沒有把連線池執行期／部署／中繼拉進來；主入口、`./sync`、`./transfer`、`./protocol` 都不含協調器；`package.json` 宣告了子路徑；打包後的 `dist` 以套件名稱引用得到。

### §2 一律注入

| 介面 | 內容 | 說明 |
|---|---|---|
| `VaultAdapter` | `list`、`read`、`write`、`remove`、`rename`、`stat` | 路徑一律是 Vault 相對路徑、`/` 分隔。`write`／`remove`／`rename` 多一個**前置條件** `expect(current)`：能做到原子「檢查＋寫入」的轉接器（Obsidian `vault.process`）應在同一個操作裡檢查，不符就不寫、回 `false` |
| `applyRemote`（選用） | 自己執行 `write`／`remove`／`rename` | 開啟中的檔案改走編輯器 API、寫入前先備份等，由外掛決定；沒給就經 `VaultAdapter` |
| `SyncStateStore` | `get`、`set`、`delete`、`keys(prefix)`（位元組值） | IndexedDB、檔案、記憶體都可以。協調器內部以 ADR 0024 的手法**每鍵序列化**：同一個鍵的寫入依序完成、讀取等前面的寫入，寫入失敗不卡住後面的寫入 |
| `VaultSyncClock` | `now`、`setTimeout`、`clearTimeout` | 測試用手動時鐘 |
| `VaultSyncTransport` | `send`、`onMessage`、`onStatusChange`、`isOnline` | `NostrVaultTransport`（§5）是預設實作；測試用記憶體假中繼 |
| 身分 | `NostrSigner`（例如 `Identity`） | 只有網路層用得到；協調器本身不碰金鑰 |

### §3 資料模型：每個檔案一個固定的 `fileId`，加一張版本圖

- 檔案的身分是 `fileId`（建立時隨機產生），路徑只是版本的一個屬性。所以**改名是一個版本**，別台同時對舊路徑的修改會套到新路徑上（改名＋修改＝路徑取改名那邊、內容取修改那邊）。
- 每個版本：`id`、`parents`、`path`、`pathAt`（這個路徑從何時開始）、`deleted`、`hash`（SHA-256）、`size`、`text`（可行級合併）、`at`（混合邏輯時鐘）、`device`、`label`、`p2p`。刪除、改名、內容變更、合併都是版本。
- **本機版本的父版本＝目前在磁碟上的版本**（不是「最新收到的版本」）：收到但還沒寫進磁碟的版本（例如大檔內容還沒到），不會被本機編輯誤認為已經看過。
- `text` 由產生版本的裝置判斷（預設：常見文字副檔名、≤ 快照層上限 160KB、合法 UTF-8），記在版本裡，所以每台裝置對「能不能合併」的判斷一致。

### §4 合併語意（確定性）

版本頭超過一個＝有並發修改。合併是**確定性**的：同一組版本頭，每台裝置算出同一個結果、同一個 id（`sha256('merge', 排序後的版本頭, 結果雜湊, 路徑)`）；合併本身也是一個版本、會送出去，兩台各自合併時 id 相同、自然去重。以兩邊的最佳共同祖先 O 為準，逐項三方：

| 情況 | 結果 | 事件 |
|---|---|---|
| 只有一邊改內容 | 取改的那邊 | — |
| 兩邊改成一樣 | 取任一邊 | — |
| 兩邊都改，文字檔且有 O 的內容 | `merge3`；乾淨就用合併結果 | — |
| 兩邊都改，合不起來（同一段改得不同、二進位、找不到 O 的內容） | `(at, device, id)` 較晚的留在主檔；**另一方的完整內容**存成衝突副本，檔名 `conflictCopyName(主檔路徑, 對方裝置名, 對方時間)` | `text`／`binary`（附 `copyPath`） |
| 只有一邊改名 | 取改名 | — |
| 兩邊改成不同名字 | 取較晚的名字，內容不受影響 | `rename-rename`（附 `otherPath`） |
| 一邊刪、另一邊相對 O **內容**沒動（只改名也算沒動） | 刪 | — |
| 一邊刪、另一邊改了內容 | **保留修改**（刪的人沒看過這些內容） | `delete-modify` |
| 兩邊都刪 | 刪 | — |

- 三個以上的版本頭依 `(at, device, id)` 排序後依序兩兩合併；每一步各自找共同祖先。
- **合併版本的涵蓋規則**：幾台裝置在訊息還在路上時，會各自合併手上不同的版本頭組合（`{a,b}`、`{a,c}`），合併版本之間彼此不是祖先，不處理會一直「合併的合併」下去（性質測試在修正前抓到單一檔案 3,356 個版本）。所以：合併版本 X 底下的真正修改（把合併一路攤平後的葉子）若都已是另一個版本頭 Y 的祖先，X 就不算版本頭；兩個合併版本互相涵蓋（同一組修改、不同的合併順序）時留 id 較小的。兩者都保留了全部修改（衝突內容各自在副本裡），選哪一個都不遺失資料，重要的是每台選得一樣。修正後同一種子最多 13 個版本。
- **衝突副本**是一個新的檔案，`fileId = sha256('copy', 主檔 fileId, 被放進副本的那一方, 內容雜湊)`：同一方的內容在不同的合併裡只產生一份副本。副本的路徑只由版本內容決定（不看本機狀態），所以每台一致；真的撞名交給下一條。
- **路徑相撞**（兩個不同的檔案要用同一個路徑，例如兩台各自新增 `Untitled.md`；比較用 NFC＋小寫，大小寫不分的檔案系統也安全）：`pathAt` 較早的留下（平手比 `fileId`），其他的改名成衝突副本名稱。這個改名也是一個版本（id 由內容決定），記 `path-collision`。

### §5 線上格式：沿用 kind 1060 外層，內層新的 rumor kind 4360

- **外層與既有檔案塊完全相同**：kind 1060（`FILE_WRAP_KIND`）、NIP-59 禮物包、`["p", 收件裝置]`、`["expiration", now + 7 天]`。中繼端的配額桶、整類拒收、大小上限（`FILE_EVENT_MAX_BYTES`）都照舊適用，中繼不需要任何改動。
- **內層 rumor kind 4360**（`VAULT_OP_KIND`），內容是訊框 `{ m, i, n, d }`：一則協調器訊息切成 ≤ 48,000 B 的訊框（與 `FILE_CHUNK_BYTES` 相同，外層事件大小與既有檔案塊相同），`d` 是 base64。
- 訊息本體：`[4 bytes 標頭長度][UTF-8 JSON 標頭][內容原始位元組]`，內容不再 base64 一次。三種訊息：
  - `node`：一個版本（內容隨附；刪除與大檔不帶內容）；
  - `digest`：我每個檔案目前的版本頭（分段送）。上線且送出佇列清空後送一次；收到的一方把對方缺的版本頭補送、把自己缺的版本索取回來。這讓離線超過中繼保留期（7 天）的裝置、新加入的裝置也能補齊；
  - `want`：索取某些版本（缺父版本、缺內容時）。
- **與舊客戶端的互動**：Cinderous App 收 1060 時用 `parseFileChunk`，只認內層 kind 43，其他一律回 `null`、略過（有測試：用舊的 `parseFileChunk` 解我們的訊框回 null）。反過來，協調器的傳輸層也略過 kind 43 的檔案塊。雙棘輪與所有既有事件格式都沒有改動。
- **不用快照（kind 30078）**：快照是「加密給自己」、每裝置一顆可取代的事件，而 CinderSync 每台裝置各有一把身分金鑰，別台解不開；而且可取代語意會蓋掉尚未送達的版本。
- **信任**：傳輸層只接受信任名單（預設＝設定的裝置公鑰加上自己）寄來的訊框；協調器收到任何傳輸層交來的訊息都會**再驗一次**（路徑不得是絕對路徑、不得有 `..`／`.`／空段、控制字元、反斜線；id 格式；內容與雜湊、大小相符），自訂的傳輸層不一定經過編解碼。
- 幾台裝置共用同一把身分時，把自己的公鑰也放進 `devices`；自己送出的訊息回到自己時，以 `deviceId` 略過。
- 喚醒補拉：`transport.filters()`（`since` 自動往前退讓 NIP-59 的兩天倒填窗）與 `transport.ingestEvents()` 直接接 `FastHydrator`。

### §6 本機變更偵測與回環抑制

- 外掛收到 Vault 事件時呼叫 `notifyLocalChange(path, kind, oldPath?)`；也可以（或另外）呼叫 `scan()`：列出所有檔案，先比大小與修改時間，有差才讀內容比雜湊（O(n)，以路徑索引）；不見的檔案先與新出現的檔案比對內容，相同＝改名。啟動時預設掃描一次，找出協調器沒在跑時的變更。
- **回環抑制靠內容雜湊**，不靠時間窗：套用遠端寫入後，索引記下寫入的雜湊與檔案狀態；外掛隨後通知的變更讀出來雜湊相同就什麼都不做（改名、刪除也一樣：索引已經是新路徑）。所以外掛不必自己維護「剛寫過的路徑」清單，防抖多久也不影響正確性。
  - **2026-10-02 補註（ADR 0048，v0.37.1）**：「索引已經是新路徑」在**舊路徑同一輪就被另一個檔案佔用**時不成立（路徑相撞：輸的改名成副本、留下的寫回原路徑；互換名字）。v0.37.0 把這種改名的回音誤認成使用者改名，造成衝突副本來回覆寫、有時一方內容消失。現在改名通知的新路徑若是另一個追蹤中、內容沒變的檔案，或舊路徑上的檔案還在，就兩個路徑各自比對。
- **不無聲覆蓋**：每一次寫入、刪除、改名都帶前置條件「磁碟上的內容就是索引記的那一份（或檔案不存在）」。不符（使用者剛好在讀與寫之間改了檔案、或目的地有一個還沒通知的本機檔案）就不寫，先把磁碟上的內容收成本機版本，再重新合併。
- 改名成環（互換名字）時，先把佔住目的地的檔案搬到暫存名 `…​.cinder-swap-xxxxxxxx`（預設忽略），再依序完成。

### §7 送出佇列

- 每個要送的版本是一筆持久化的佇列項目（`q:<序號>`），依序送出、送成功才刪；重啟後從頭續傳。
- **離線累積**：還沒交給傳輸層的本機版本，會被下一次本機編輯直接取代（別台從沒看過它），所以離線改五次只送最後一次。一旦交給傳輸層（可能有一部分裝置已經收到，例如送給第一台成功、第二台失敗），就不再被取代。
- 送出失敗以指數退避重試（預設 1 秒起、最長 5 分鐘），狀態顯示 `error`。

### §8 接收

- 版本的父版本還沒到：先等著（持久化 `w:`），並向其他裝置索取；父版本到了（遠端送來的，或本機自己算出的合併版本）就依序併入。等超過 `orphanAfterMs`（預設一天）就當父版本已遺失、直接併入（找不到共同祖先時合併會退回衝突副本，不遺失資料）。
- 重複、亂序、重送的訊息都是冪等的：版本以 id 去重，合併以內容決定 id。

### §9 持久化的狀態

| 鍵 | 內容 |
|---|---|
| `m` | 混合邏輯時鐘、佇列序號、最後同步時間、衝突清單（最多 200 筆） |
| `f:<fileId>` | 版本圖（最近 64 個版本，逐層從版本頭往回數）、版本頭、磁碟狀態（路徑、雜湊、大小、修改時間、對應的版本）、尚未送出的版本、各裝置已知的版本頭、已修剪的版本 id |
| `b:<fileId>:<雜湊>` | 內容：文字檔保留可能當共同祖先的版本（版本頭、磁碟上的版本、其他裝置已知的版本頭、最近 8 層）；二進位只保留還沒送出、或不在磁碟上的版本頭 |
| `q:<序號>` | 送出佇列 |
| `w:<版本 id>` | 等父版本的遠端版本（含內容） |

### §10 大檔（第 3 批才做 P2P）

- `classifyPayload(size) === 'p2p'` 的版本只送中繼資料（`p2p: true`），不帶內容。收端不動磁碟上的舊版本，狀態列出 `pending`（`via: 'p2p'`）並發 `pending` 事件。
- 第 3 批的接口已經定好：送端 `readVersionContent(fileId, versionId)`（驗過雜湊才回），收端 `supplyContent(fileId, versionId, bytes)`（雜湊不符丟例外）。

### §11 狀態與事件

`status()` 與 `on('status')`：`state`（`idle`／`syncing`／`offline`／`error`／`paused`）、`queue`（待送出數）、`waiting`（等父版本數）、`conflicts`、`pending`、`lastSyncAt`、`pausedReason`、`lastError`。另有 `conflict`、`applied`（已套用的遠端變更）、`pending`、`error` 事件；`index()` 是路徑 → 版本索引，`tombstones()` 是保留期內的刪除。

### §12 墓碑與沉睡裝置

- 刪除是一個版本（即墓碑），因果關係由版本圖決定，**不用** `isDeleted` 的最後寫入者為準：那會讓一邊刪、一邊改時的修改被刪除蓋掉。
- 刪除超過 30 天（`TOMBSTONE_TTL_MS`，以 `gcTombstones` 判斷）且沒有待送項目的檔案，整筆紀錄在背景維護時清掉。
- `isStaleDevice(lastSyncAt)`：啟動時若上次同步超過 30 天，暫停合併與送出（`paused`、`stale-device`），外掛請使用者確認後呼叫 `confirmStaleResume()`。在線（訂閱著）就算在同步，所以一直在線但沒有變更的裝置不會被誤判。

### §13 重用的零件

| 零件 | 用在哪裡 |
|---|---|
| `classifyPayload`、`SNAPSHOT_TIER_MAX_BYTES`、`FILE_TIER_MAX_BYTES` | 大檔判斷、文字合併的大小上限、內容上限 |
| `merge3` | 文字檔的三方合併 |
| `conflictCopyName` | 衝突副本與路徑相撞的新名字 |
| `gcTombstones`、`isStaleDevice`、`STALE_DEVICE_MS`、`FileTombstone` | 墓碑清理、沉睡裝置、`tombstones()` |
| `FILE_WRAP_KIND`、`FILE_CHUNK_BYTES` | 外層 kind 與訊框大小 |
| `sealAndWrap`、`openWrap`、`NostrSigner` | 網路層加解密 |
| `FastHydrator` | 經 `filters()`／`ingestEvents()` 接上 |

沒有用到的：快照（§5）、`DeviceSyncState` 與 OR-Set（檔案需要的是版本圖，不是集合或最後寫入者為準）、`isDeleted`（§12）、推播介面（外掛的事）。

自我審查時發現並補上的：合併的合併無限增生（涵蓋規則）；衝突副本路徑依本機狀態而不一致；父版本是本機算出的合併版本時沒有放行等待中的版本；已被取代的版本仍列為內容未到；「刪除 vs 只改名」讓內容已不存在的檔案被保留；大小寫不同的兩個檔案共存時其中一個沒被追蹤；摘要比佇列先到而重複索取；交給傳輸層後失敗的版本仍可能被取代；`start()` 之前的通知會在空索引上重複建檔；一直穩定不下來的檔案會空轉；在線但沒有變更的裝置會被誤判為沉睡；收到的訊息只在編解碼層驗證；合併要求**每一個**版本頭的內容（只貢獻改名的一方內容可能已不存在，檔案卡住）；反過來，合併結果採用的那一方內容不在手上時仍建立合併版本（產生一個沒有任何裝置有內容的版本）——現在改為只在真的用到時要內容，而結果的內容拿不到就先等。

## 實測

- 打包（esbuild 壓縮）：主入口 152.7KB（gzip 55.8KB）、`./sync` 80.5KB（gzip 31.3KB）——兩者原始碼未變、大小不變；`./sync/vault` 109.7KB（gzip 40.6KB）。
- 規模（`scale.test.ts`，記憶體轉接器）：1,000 個檔案首次掃描 50ms、5,000 個 226ms（線性）；無變更重掃 15ms；兩個變更重掃 12ms（只讀了那兩個檔案）；5,000 個檔案同步到另一台 1.2 秒。

## 已知限制

- 前置條件的原子性取決於轉接器：做不到「檢查＋寫入」原子的轉接器，讀到寫之間仍有很短的競態。Obsidian 的 `vault.process` 可以做到（文字檔）；二進位與刪除、改名沒有原子 API。
- 合併結果依賴共同祖先的內容：祖先被修剪（離線很久、同一檔案改了超過 64 次）時退回衝突副本；各裝置保留的內容不同時，可能一台乾淨合併、另一台產生副本，兩個合併版本以涵蓋規則收斂到同一個，另一個結果留在副本裡——不遺失資料，但可能多一份副本。
- 衝突事件只在自己算出合併的裝置上發；收到別台的合併版本時只會看到副本檔案出現（`applied`）。
- 新裝置加入或久未上線時，其他裝置會各自補送（重複但冪等）；大量檔案時每個檔案一顆事件、每台收件裝置一份，中繼的檔案塊配額（預設每收件人 4,000 顆）可能不夠——批次 P2P 串流是第 3 批（ADR 0021〈後續〉#2）。**已由 [ADR 0026](0026-p2p-batch-stream-and-large-file-streaming.md) 處理（v0.23.0）**：給 `peers` 時，待送出 ≥ 10 個版本就改走 P2P 批次；P2P 打不通時中繼（kind 1060）以每小時 20 則限速補送，在配額之內。另外，中繼沒開 `MAX_FILE_MB` 會整類拒收 1060，見 [ADR 0027](0027-relay-file-events-for-vault-sync.md)。
- 同一版 SDK 才保證合併結果逐位元組相同；版本不同時由涵蓋規則收斂，不會越合越多。
- 資料夾本身不同步（只同步檔案；空資料夾不會出現在別台）；刪除後留下的空資料夾由外掛決定是否清理。
- 協調器不做防抖；外掛照 PRD 在 Vault 事件後防抖（例如 500ms）再通知。

## Consequences

- ＋ 兩個外掛只要實作 `VaultAdapter`、`SyncStateStore`，接上 `NostrVaultTransport`，就有完整的檔案樹同步。
- ＋ 不改中繼、不改任何既有事件格式；舊客戶端看到這些訊息會直接略過。
- ＋ 收斂性與「不遺失資料」由隨機性質測試守著。
- － 新的線上格式（內層 kind 4360）；日後要改必須升 `VAULT_WIRE_VERSION` 並處理新舊並存。
- － 狀態儲存會保留文字檔最近幾個版本的內容（當合併祖先用）。
