# 0106. 中繼弄丟的版本：對方簽收了更後面的序號、這一則一直沒簽收就重送

- 狀態：**已接受（Accepted，2026-10-22）**——使用者 2026-10-22 指示「先修新發現的問題」（手機加入後一直留著桌機已刪的檔）
- 日期：2026-10-22
- 對應：SDK ADR 0068（寄件序號、簽收單）、0074（摘要說沒有、但還在路上的不重送）、0088（新裝置連祖先一起送）；CinderSync TODO〈刪除沒送到加入中的手機〉

## Context

2026-10-22 motorola edge 20 pro（LTE，CinderSync `core-v0.3.7`，SDK v0.73.0）以全新的測試 vault 加入 VaultA：

- 桌機在手機加入前刪了 `ADR0100批次/` 的 75 個檔。手機只收到這些檔的**建立版本**，沒收到刪除版本，一直留著桌機已經刪掉的檔。
- 看兩邊的同步狀態（IndexedDB）：
  - 桌機的佇列裡**沒有**那些刪除版本——當作已經送出、移除了；
  - 桌機記得手機只有建立版本（`rec.peers`），手機那邊也沒有在等父版本的紀錄（`w:`）；
  - 手機只在加入時送過一份摘要，之後一直連著線、沒有本機修改，就不再送摘要；按「立即同步」也不會。
- 中繼的檔案車道是淘汰制（每位收件人有上限，滿了淘汰最快到期的）。加入時桌機往手機的收件匣塞了大量訊息，其中一則（帶刪除版本）送到前不見了；寄件端看到的是成功。

為什麼補不回來：

1. 手機那份摘要（說它沒有刪除版本）反映到桌機的某個寄件序號為止，而刪除版本是在那之後才經中繼送出的——ADR 0074 判定「還在路上」，不重送。這個判斷的有效期是保存期（7 天）。
2. 手機之後沒有再送摘要，所以不會有序號更新的摘要來推翻這個判斷。
3. 簽收單（ADR 0068）其實早就看得出來：手機簽收了桌機更後面的序號，唯獨那一則一直沒簽收。但簽收單只拿來扣帳與記錄「對方已收到」，沒有用來判斷弄丟。

模擬網路重現（`tests/sync/vault/relay-lost.test.ts`：中繼收下一則帶刪除版本的訊息卻弄丟）：新加入的裝置一整天都留著那個檔，寄件端佇列是空的。

## Decision

1. **判定弄丟**：經中繼送給裝置 D 的版本（ADR 0074 記的「誰、哪個版本、哪個序號、什麼時候送」），同時滿足以下條件就當作中繼弄丟了：
   - D 簽收過比它**更後面**的序號；
   - 這一則的序號**不在** D 的簽收區間裡；
   - 送出已超過 `RELAY_LOST_AFTER_MS`（10 分鐘）。收件端處理完 20 秒內就簽收，中繼的投遞順序也只差幾秒，留寬一點；誤判的代價只是多送一次。
2. **處理**：拿掉「還在路上」的紀錄。如果 D 還不知道這個版本（或它的後代），就排進補送（`#resend`，照既有規則：完整成員要的照舊廣播、輕量成員只送給它）。重送的那一則又弄丟時同樣處理——前提是 D 之後又簽收了更後面的序號。
3. **什麼時候看**：每次收到簽收單、每次背景維護（`tick`）。
4. **不判定的情況**：
   - D 從來沒簽收過（例如舊版不簽收、或一直離線）：維持原狀，等它的摘要或上線補拉；
   - D 簽收過、但還沒簽收比這一則更後面的（例如離線中）：照舊等。
5. 只在記憶體：「還在路上」的紀錄本來就只在記憶體（ADR 0074）。寄件端重開後就沒有這個判斷，也沒有「還在路上」的壓制，對方下一份摘要照舊會補送。

`RelayLedger` 新增 `receipts(device)`，傳回那台的簽收區間（唯讀）。

## Consequences

- ＋ 中繼弄丟（收件匣滿了被淘汰、中繼重開、對方當時還不信任這台而沒收）的版本，對方只要還在簽收，十幾分鐘內就補上。不用等對方再送摘要，也不用等 7 天。
- ＋ 不新增訊息類型、不改線上格式；收件端不必升版，只要會簽收（v0.54.0 起）。
- － 對方漏收之後完全不再收到這台的任何訊息（沒有更後面的序號可以簽收）時看不出來，維持原狀：等它的摘要（`resync`、重新連線）。
- － 每次收到簽收單與每次維護都要掃一遍「還在路上」的紀錄（最多 20 萬筆，只在記憶體）。
- 另案（沒有在這裡處理）：
  - 新加入的裝置一開始就被算進加入前的廣播用量。帳上沒有 `to` 的廣播算在每一台頭上，所以這次手機一加入就是 2430／1080 塊，批次只能走直連（→ ADR 0107）；
  - CinderSync 的「立即同步」在已連線時不送摘要，使用者沒辦法手動對帳。
- 測試：`tests/sync/vault/relay-lost.test.ts`
  - 新加入的裝置漏收一則刪除：未滿 10 分鐘照舊等，之後重送一次、檔案刪掉；
  - 沒有弄丟時不重送；
  - 對方離線、還沒簽收更後面的序號時不當作弄丟；
  - 重送的那一則又弄丟時，下一次再補；
  - 舊版（不簽收）維持原狀。
  - 變異測試：拿掉判定，「漏收一則刪除」與「重送的又弄丟」兩項失敗。
  - harness 新增 `FakeHub.drop`：中繼收下卻弄丟的訊息。
