# 0004. 連線池再補五樣：訊框上限、補訂閱游標、立刻重連、活動時間、連線逾時

- Status: Accepted
- Date: 2026-09-27
- 相關：ADR 0003

## Context

《辭職信》原本的連線池還有四個行為 SDK 沒有。要讓它改用 SDK 又不退步，這四樣得補上。
它們對其他應用也有用。

## Decision

- **`maxFrameBytes`**：進站訊框超過上限就整框丟掉，擋惡意中繼塞爆記憶體。
  先比字元數，接近上限才算 UTF-8 位元組，平常幾乎沒有成本。
- **補訂閱游標**：
  - 每條訂閱記住看過最新的 `created_at`，以本機時鐘為上限。
    這樣一則遠未來的事件，不能讓之後補訂閱的 `since` 把整條訂閱靜音。
  - 斷線重連或認證後補送 REQ 時，帶上 `since = max(原本的 since, 游標)`，不必把歷史整份重播。
  - 第一次訂閱照原樣送。
- **`reconnectNow(url)`**：跳過退避、立刻重連；已經開著或正在連就不動。
  給應用的健康探針用，因為探針本身就是定期的。
- **`connectTimeoutMs`**（v0.3.1）：連線太久沒開起來就當作斷線，走一般的退避重連。
  不回應的站原本會永遠卡在 connecting，既不重試，應用也無法判它斷線。
- **`lastActivityAt(url)`**：最近一次從那一座收到任何訊息的時間。有流量的站就不必探，
  因為一次探針是 REQ 加 CLOSE 兩則訊息，會計入中繼的額度。

## Consequences

- ＋ 補訂閱少重播，對長時間掛著的房間與收件匣特別有感。
- － 行為改變：已經看過事件的訂閱，補送的 REQ 會多一個 `since`。
  如果應用依賴「重連後把歷史再送一次」，要自己重新訂閱，不能靠補送。
