# 0131. 重連閘的 DO 那一道主要只計沒認證就斷線的連線

- 狀態：**已接受（Accepted，2026-10-30）**——使用者 2026-10-30：「依序處理」（三項建議的第 3 項：分片那一道只計「沒完成認證就斷線」的連線）
- 日期：2026-10-30
- 對應：ADR 0111（主平面的重連閘）、0130（用戶端被擋之後的退避）；Cinderous ADR-0391、0392

## Context

ADR 0111 的 DO 那一道以 IP 計所有升級：10 分鐘內第 21 次起擋那個 IP 10 分鐘。它要擋的來源（2026-10-20 錨點 2，每 8 秒重連一次）**只連線、不認證**。

但正常的聊天用戶端也會被算進去，而且算的是整個 IP：

- 公司、學校、電信業者的共用 IP 後面，同一個分片上有超過 20 個人時，一次 Wi-Fi 閃斷或早上一起開機，就把整個 IP 擋 10 分鐘；
- 用戶端被擋以後還會整座退避（ADR 0108、0130），影響比 10 分鐘更長。

## Decision

DO 那一道改成兩個計數，仍然只在記憶體裡、仍然以 IP 為鍵、仍然只套主平面：

1. **沒認證就斷線的連線**：用戶端關閉（`webSocketClose`／`webSocketError`）時還沒完成 NIP-42，就記一筆。窗口內滿 `max`（預設 20）條，擋那個 IP `blockMs`（預設 10 分鐘）。
2. **所有升級的總上限**：升級時記一筆，窗口內滿 `maxTotal`（預設 60，`max` 的 3 倍）次也擋。
   - 只算第一種的話，攻擊者拿拋棄式金鑰認證就能繞過。總上限把這種情況壓在原本 3 倍以內。
3. `RECONNECT_GUARD` 多一個選用的第四欄：`次數/窗口秒/封鎖秒[/總上限]`。沒給就是次數的 3 倍；比次數小、或格式不對都退回預設。
4. 被擋的升級照舊在 `acceptWebSocket` 之前回絕、不計數，回絕形狀不變（1013 `rate-limited: reconnects`）。
5. 伺服端自己關掉的連線（超限即關）不經過 `webSocketClose`，不記。

## 理由

- 只看「認證了沒」就能把 ADR 0111 要擋的來源和正常用戶端分開，不用新的協定，也不用用戶端改任何東西。
- 認證過的人只算總上限：60 次＝同一個 IP 後面 60 個人在 10 分鐘內各重連一次，一般公司網路夠用。
- 記在關閉時而不是升級時：升級的當下還不知道會不會認證。斷線時 IP 從連線狀態取（休眠後從 attachment 還原），不多存東西。

## Alternatives Considered

- **完全不計認證過的連線**：最寬，但拋棄式金鑰認證很便宜，等於把這一道拿掉。
- **改用 pubkey 計數**：認證前不知道 pubkey；而且攻擊者也可以每次換一把。
- **只調高原本的 20**：共用 IP 後面的人數沒有上限，調多高都有人撞到；也會讓不認證的來源多打幾倍。

## Consequences

- ＋ 共用 IP 後面的正常使用者不再因為人多被一起擋。
- ＋ 只連不認證的來源照舊在 20 條之後被擋。
- － 認證過的濫用者每個 IP、每個分片 10 分鐘可以升級 60 次（原本 20 次）。Worker 那一道的限速 binding 仍在前面（Cinderous 錨點每分鐘 12 次，Cinderous ADR-0409）。
- － 不認證的來源原本第 21 次升級就被擋；現在要等它第 20 條連線斷掉之後才擋，最多多掛幾條同時開著的連線。
- 行為改變：只設三欄的 `RECONNECT_GUARD` 意思變了（次數改成只計沒認證的），站主不用改設定。

## 測試

- `tests/relay/reconnect-guard.test.ts`：沒認證的滿了就擋、期滿放行；認證過的只算總上限；總上限擋拋棄式金鑰；滑動窗口；不同 IP 各自計數；記憶體上限；四欄格式與壞值退回預設。
- `tests/relay/worker.test.ts`：20 條沒認證就斷線之後，下一次升級在 `acceptWebSocket` 之前回絕、不寫儲存；同一個 IP 認證過的 60 次都放行、第 61 次才擋；`RECONNECT_GUARD` 自訂與 `off`；車道不套。
- 實作前先確認是紅燈（新增的行為測試）。
