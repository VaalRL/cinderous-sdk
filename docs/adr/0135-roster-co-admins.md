# 0135. 組織名冊的共同管理者：任一位可簽，只有擁有者能改管理者名單

- 狀態：**已接受（Accepted，2026-11-12）**——Cinderous 使用者 2026-11-12 選了「任一位可簽，只有擁有者改名單」
- 日期：2026-11-12
- 對應：SDK ADR 0132、0133、0134；Cinderous ADR-0047、ADR-0257 §7.1、ADR-0418

## Context

組織名冊（kind 10038）只認一把金鑰：邀請碼裡的管理者、自架站的 `ROSTER_ADMIN_PUBKEY`。這把金鑰弄丟或那個人不在，名冊就簽不動——不能加人、不能移除離職者、不能改政策。Cinderous ADR-0257 §7.1 把它列為承接企業客戶前要處理的單點風險。

Cinderous 使用者 2026-11-12 從四個做法裡選了：**任一位管理者可以簽名冊，只有擁有者能改管理者名單**。其他選項：誰都能改名單（一把被盜就能踢掉其他人、接管組織）、M-of-N 門檻簽章（要新協定與多人協調，工程大）、只做擁有者換鑰（遺失仍是單點）。

## Decision

1. **`OrgRosterDoc.admins`（可選）**：共同管理者的 pubkey。只有**擁有者簽的名冊**裡的這份名單算數。
   - 清洗：字串、去重、不是擁有者、必須是這份名冊的在世成員（沒有 `supersededBy`），上限 `ROSTER_MAX_ADMINS`＝16。不符的濾掉，不讓整份無效。
   - 沒有共同管理者就省略欄位，舊格式不變。
2. **`verifyOrgRoster(event, trust)`**：`trust` 可以是單一 pubkey（舊用法，只認那一把）或 `RosterTrust { owner, coAdmins }`。
   - 擁有者簽的：`admins` 取自內容。
   - 共同管理者簽的：內容裡的 `admins` 一律忽略、換成 `trust.coAdmins`。
   - 🔴 共同管理者簽的名冊必須讓**每一位**共同管理者都還是在世成員，否則整份無效——共同管理者不能把彼此踢出組織（也就踢不掉彼此在自架站的寫入權）。擁有者不受這條限制。
   - `coAdmins` 由呼叫端記著：取**擁有者最新一份**名冊的 `admins`。這份名單的更新與「成員內容採用哪一份」分開——擁有者的名冊即使比已採用的舊（成員那部分不採用），它列的共同管理者名單照樣生效。
3. **`rosterSigners(owner, coAdmins)`**：擁有者在前，再接共同管理者，供訂閱名冊事件的 `authors`。
4. **自架 Node 站**（ADR 0134 的自動套用與 `cinder_applyroster`）：
   - 收到擁有者或目前共同管理者簽的 kind 10038 就走同一套檢查；`Nip86Admin.rosterSigners()` 回目前可簽的人。
   - 存檔的 `roster` 多兩格：`coAdmins`、`ownerUpdatedAt`（擁有者那份的時間）。讀回時格式不對就整份不用（ADR 0133）。
   - `roster.admin` 仍記擁有者（`ROSTER_ADMIN_PUBKEY`）：換掉名冊金鑰後，連同共同管理者名單一起不再生效。
   - 擁有者較舊的名冊回 `stale:`、成員不動，但共同管理者名單照樣更新並存檔。
   - 共同管理者一定是在世成員，所以本來就在白名單裡；只有擁有者另外加進白名單（ADR 0134 §3，不變）。
5. Worker 沒有名冊套用，不受影響。

## 理由

- 擁有者仍是唯一能改「誰是管理者」的人：一把共同管理者金鑰被盜，損害限於「能改成員與政策」，擁有者發一份新名冊把它移出名單就止血。
- 共同管理者簽的名冊必須保留所有管理者，避免共同管理者之間互相踢人；擁有者是仲裁者。
- 名單的時間與成員的時間分開記，客戶端與自架站對「現在誰是共同管理者」才會得到同一個答案，不受事件到達順序影響。

## Alternatives Considered

- **共同管理者名單放在另一種事件**：多一個 kind、多一條訂閱與存檔，換不到額外保障。不採用。
- **共同管理者簽的名冊若帶不同的 `admins` 就整份拒絕**：讓共同管理者照抄名單才能發，徒增出錯機會。改為忽略。
- **允許共同管理者把其他管理者移出成員**：權限會變成「誰都能踢誰」，等於使用者沒選的那個選項。否決。

## Consequences

- 新 API：`OrgRosterDoc.admins`、`RosterTrust`、`rosterSigners`、`ROSTER_MAX_ADMINS`、`Nip86Admin.rosterSigners()`；`verifyOrgRoster` 第二個參數可為 `RosterTrust`（傳字串的舊用法不變）。
- 存檔格式多兩格（選用），舊存檔照常讀。
- 殘餘風險：
  - 擁有者金鑰遺失：共同管理者仍能維護成員與政策，但不能再改管理者名單。換擁有者金鑰仍要走 Cinderous ADR-0052 的身分輪替與更新 `ROSTER_ADMIN_PUBKEY`。
  - 共同管理者金鑰外洩：在擁有者把它移出名單之前，對方能改成員與政策（不能移除其他管理者）。
  - 共同管理者之間沒有鎖：兩位同時發布，較新的那份勝出，另一份的修改要重做。
