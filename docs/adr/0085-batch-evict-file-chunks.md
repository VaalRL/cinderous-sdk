# 0085. 中繼淘汰檔案塊時整批一起刪：不再切出永遠收不齊的孤兒

- 狀態：**已接受（Accepted，2026-10-14）**——使用者 2026-10-14「客戶端修法和整批淘汰都做，先 SDK 再移植」
- 日期：2026-10-14
- 對應：ADR 0042（保底份額、溢位帶、丟棄計數）、0064（中繼主不可信任）、0081／0084（收件端確認收不齊的訊框）；
  Cinderous ADR-0162（每收件人分桶上限）、ADR-0371（檔案車道、每收件人 1,440 塊）、ADR-0381（檔案車道保底與溢位帶）

## Context
2026-10-14 研究「relay 是否應定期清理永遠收不齊的檔案塊」的結論：

- 中繼**判定不了**「收不齊」：檔案 id、第幾塊、一共幾塊都在密文裡。要判定就得在外層加明文標籤（同步訊息的大小與結構就公開了），
  還會誤刪長期離線收件人手上完整、只是還沒人來拿的資料。不做。
- 收不齊的孤兒**主要是中繼自己切出來的**：每收件人上限（FIFO）、天花板舊路徑、保底份額外、借用列 2 小時到期——四條淘汰路徑都**逐列**刪，
  一則 30 或 164 塊的訊息被刪掉一部分，剩下的永遠收不齊，佔空間到過期、每次補拉都被重新下載（錨點 1 的 130 MiB）。

## Decision
- **批次**＝同一收件人、kind 1060、同一個 `expiration` **標籤值**。同一次送出的所有檔案塊共用同一個值（SDK vault 傳輸層、Cinderous 傳檔都是迴圈外算一次）。
- 四條淘汰路徑只要刪到某一批的任何一列，就把那批其餘的列一起刪，一起計入丟棄計數（`dropped`）：
  每收件人上限（FIFO）、天花板舊路徑（`legacy`）、天花板回收（`reclaim`：借用列）與保底份額外（`excess`）、借用列到期（`prune`）。
- **借用到期**：借用的那幾塊 2 小時到期時，同一批正常存放的也一起刪（使用者裁示選較簡單的這一級；「寫入時整批決定借不借」不做）。
- SQLite 版新增欄位 `batch`（`expiration` 標籤的原始值——借用列的 `expiration` 欄會被改成 2 小時，不能拿它當批次）與部分索引
  `idx_offline_batch(recipient, batch, bytes, created_at) WHERE batch IS NOT NULL`：只有檔案塊進索引；查批次、找同批的列都只讀索引
  （`batch` 排在 json 後面，讀大表就要走完檔案塊的溢位頁）。記憶體版直接讀事件的標籤。兩個實作逐字對齊。
- 相容：可為 NULL 的欄位＋部分索引。舊版程式（Cinderous main、SDK v0.59 以前）的 INSERT 不帶它＝NULL＝**不參與整批淘汰**；回滾照常讀寫。
  升級前就存在的列同樣是 NULL，照舊逐列淘汰。
- 不改保存期（檔案塊照舊 7 天）。

## Alternatives Considered
- **定期清理「N 小時沒有新塊又不齊」的批**：判定不了不齊，而且會刪掉離線收件人完整的資料（見 Context）。
- **縮短檔案車道保存期**：孤兒少佔幾天，但長期離線的裝置收不到；整批淘汰＋收件端確認之後孤兒不該再累積，先不動。
- **寄件端放棄時送 NIP-09 刪除**：只解「送到一半」那一種；刪除事件會把一串外層 id 連在一起（多洩漏），而且外層作者是一次性金鑰，寄件端得保留每顆的私鑰。
- **寫入時整批決定借不借**（一批要嘛全借、要嘛全不借）：較正確，但要在寫入時看同批前面的列落在哪；借用到期時整批刪已經不會留下孤兒，先不做。

## Consequences
- ＋ 中繼不再切出新的孤兒：刪一批就騰出整批空間、少刪別人；收件端不再為收不齊的訊框反覆下載。
- ＋ 不加任何元資料、不需要客戶端更新：所有產生檔案塊的程式本來就共用 `expiration`。
- － **同一秒送給同一人的另一則**（`expiration` 剛好相同）可能被一起刪——它本來也在被淘汰的那個時間點附近；收件端由摘要／索取重送。
- － 整批刪可能讓那位收件人掉到保底以下（份額外淘汰原本會停在保底）：被一起刪的那些本來就收不齊。
- － **既有的元資料面**（不是本 ADR 新增的）：中繼本來就能從「同一個 `expiration`」把同一批歸在一起、推出每批大小。已記進 ADR 0064 的已知限制。
  若將來要消除它（例如每塊的 `expiration` 加幾秒隨機抖動），整批淘汰就做不到，兩者要取捨。
- 移植：Cinderous relay 的兩個 store 要做同樣的改動（建構子長出同樣兩行 DDL，`tests/relay/schema-compat.test.ts` 的 `SDK_0085_ADDITIONS` 逐字）；部署前照例取得同意。
- 驗證：`tests/relay/batch-evict.test.ts`（記憶體版、SQLite 版各 5 項：FIFO、天花板舊路徑、保底份額外、借用到期、不受影響的列）；
  `tests/relay/schema-compat.test.ts`（從零建出的 schema＝Cinderous main＋ADR 0042＋ADR 0085 的遷移，逐字；舊版寫下的列 `batch` 為 NULL、不參與整批淘汰）。
