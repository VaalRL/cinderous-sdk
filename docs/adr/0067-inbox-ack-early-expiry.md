# 0067. 收件確認後提早過期：收件人處理完，中繼把那些包降為「現在＋寬限」到期

- 狀態：**已接受（Accepted，2026-10-11）**。使用者 2026-10-11 問「當所有該同步的設備都已經同步過後，讓 relay 上的資料降級、更快速過期，是否有效益」；看過測量後裁示：「寫提早過期的 ADR」。同日裁示寬限：「保留時間應該比照未註冊的應用程式」。其餘各題同日裁示：「都照建議」。
- 日期：2026-10-11
- 對應：
  - ADR **0025** §5（協調器的 Nostr 網路層：kind 1060、每台裝置各包一份）、**0028**（摘要補送）、**0029**（補拉與塊數預算 `relayLimits`）、**0035**（補訂閱往前退讓兩天）、**0038**（容量訊號）、**0042**（每收件人配額、丟棄計數）、**0045**（補拉不完整不推進起點）。
  - ADR **0064**（中繼不可信任）、**0066**（中繼推得出群組與上線狀態；本 ADR 不改變它）。
  - CinderSync ADR 0018（每小時一輪、平常不連線）。

## Context

### 現況

- 同步訊息以 kind 1060 禮物包送到中繼，每台收件裝置各一份（外層 `#p` 只有一位收件人），帶 `expiration`，**7 天**（`DEFAULT_VAULT_TTL_SECONDS`）。
- 收件人每次補拉的起點都**往前退 2 天**（`TIMESTAMP_JITTER_SECONDS`），因為 NIP-59 的 `created_at` 會隨機往前填，中繼無法以「收到的時間」過濾。
- 中繼不知道收件人處理過沒有。NIP-09 刪不掉（外層是一次性金鑰簽的，收件人不是作者）；NIP-62 vanish 會連這台自己的快照一起清掉，範圍太大。

### 測量（2026-10-11）

方法：SDK 測試 harness 跑 3 台裝置 14 天，同步方式同 CinderSync（每小時一輪、平常不連線、`digestPolicy: 'on-change'` 一天最多一份）。協調器送出的每一則訊息再經**真正的** `NostrVaultTransport` 包成 kind 1060（真實大小、`created_at` 倒填、`expiration`），用簡化的中繼模型重放。工作量：桌機上班 10 輪 × 改 3 篇，筆電晚上 4 輪 × 2 篇，手機一天 3 次寫日記＋每天 2 張 1.5 MB 照片；每篇存 5 次。

| 指標（一般使用，14 天） | 基準：放滿 7 天 | 處理完＋寬限 2 小時 | 處理完＋寬限 1 小時 | 處理完立刻過期 |
|---|---|---|---|---|
| 中繼佔用：平均／峰值 | 243.6／368.7 MB | **11.1／49.1 MB** | 9.2／49.0 MB | 7.3／47.7 MB |
| 每台每天補拉下載（平均） | 約 105 MB | **約 24 MB** | 約 14.5 MB | 同左 |
| 下載中重複（已處理過）的比例 | 86% | **40%** | 0% | 0% |
| 每收件人列數峰值（桌機／筆電／手機） | 1,735／2,234／830 | **301／396／131** | 301／396／128 | 301／396／125 |

「手機出遊 5 天不開」的情境：佔用平均 101 → 6.4 MB（寬限 2 小時）；手機自己的列留到它回來。

寬限 2 小時的重複比例是 40%，不是 0%：每小時一輪，確認過的包在寬限內還會被下一輪的補拉（往前退 2 天）再抓一次。寬限 1 小時剛好落在輪與輪之間所以是 0%，但實際的輪不會準點，1 小時也會有一些重複。

解讀：

1. **重複下載**：每小時一輪 × 每輪重抓 2 天份，86% 的下載是已處理過的包（手機的流量、電量，也是 Durable Object 的讀取額度）。
2. **配額**：CinderSync 部署的中繼 `maxFileMb` = 17 ⇒ 每收件人約 872 塊，送出端預算再打 0.75 折。放滿 7 天時一般用量（主要是照片）的需求就超過配額：實際會變成送出端節流（同步延後）或中繼淘汰最舊、還沒領的包。處理完就過期，峰值降到 400 以下。
3. **寬限的長短對佔用影響很小**（2 小時、1 小時、立刻過期的平均佔用都在 7–11 MB），差在重複下載。

限制：工作量是假設的，絕對數字隨照片數與存檔次數變；中繼模型沒算配額淘汰、送出端節流與多座中繼。比例（重複 86%、佔用降一個數量級）在兩個情境都穩定。

### 效益不包括的

- **惡意站主**：收到的當下就能複製，提早過期擋不住。
- **中繼資料**（ADR 0066）：中繼本來就從 AUTH 知道誰上線；確認不新增、也不減少可推知的資訊。
- 對隱私的幫助只在「誠實的中繼日後出事」（被入侵、被要求交出、使用者的 Cloudflare 帳號被盜）時，可取得的密文從 7 天份縮成約兩小時份。

## Decision

### 1. 收件確認事件（Cinderous 中繼擴充）

- 新的**瞬時** kind（暫定 **25190**，實作時再確認不和現有 kind 衝突），收件人自己的金鑰簽：
  - `content`：處理完的外層事件 id（hex），以逗號分隔；一則最多 500 個，超過分多則。
  - 不帶 `p` 標籤、不帶其他資訊。
- 中繼把它當**控制訊息**：不存、不轉發給任何訂閱。只在以下條件都成立時處理：
  1. 這條連線已經 NIP-42 AUTH；
  2. 確認事件的 `pubkey` ＝ AUTH 的 pubkey，簽章有效；
  3. 只動 `offline_msgs` 裡 `recipient` ＝ 這個 pubkey、`id` 在清單中的列。
- 處理：`expiration = min(expiration, now + 寬限)`。**寬限比照未註冊應用的保存期**：直接用 `PUBLIC_LANE_RETENTION_SECONDS`（2 小時，Cinderous ADR-0367 §決策 1），不另設常數（SSOT）；站方保存上限比它短時取站方上限（ADR-0160：站方上限恆為權威）。不另開設定項。回 `OK true`（說明為空字串：不新增客戶端要認的詞元）；格式不對回 `OK false "invalid: malformed: …"`、簽章者不是 AUTH 身分回 `OK false "restricted: self-only: …"`、沒 AUTH 回 `auth-required` 並重發挑戰。
- 別人不能讓你的包提早過期：條件 2、3 保證只能動自己收件匣裡的列。

### 2. 中繼宣告與相容

- NIP-11 新增 `cinder_inbox_ack: { kind: 25190, grace_sec: 7200 }`（實際值）。客戶端只對宣告了的中繼送確認。
- 公開中繼、舊版 Cinderous 中繼：不宣告就不送，照舊放到它的期限。舊版客戶端不送確認，照舊放 7 天。兩邊都不會出錯，只是拿不到好處。
- Cloudflare（`SqlMessageStore`）與 Node（`MessageStore`）兩種儲存都要實作。

### 3. 客戶端什麼時候送

- **處理完才確認，不是收到就確認**：
  - 一則協調器訊息的所有訊框都收齊、交給協調器，而且協調器把結果**寫進狀態儲存**之後，那些訊框的外層 id 才算處理完。
  - 寄件人不在信任名單、解不開、訊框沒收齊的，**不確認**，留給保存期限（可能是還沒同步到名單的新裝置，太早清掉會掉資料）。
- 批次送：每輪補拉推進起點時，或累積滿 500 個、或每 5 分鐘，對每座有宣告的中繼送一次。送不出去就留到下次。
- 多座中繼：每座各送；中繼對不在自己這裡的 id 直接忽略。

### 4. 出錯時的補救

- 確認送出後本機狀態卻沒保存住（當掉、從備份還原）：寬限內重開還補拉得到；超過寬限就靠既有的摘要補送（ADR 0028，CinderSync 一天至少一份），較慢但不會永遠缺。

### 5. 送出端的預算：另見 ADR 0068，分開出版

送出端的塊數預算（`relayLimits`）假設「每一塊都在中繼上放滿保存期」，看不到收件人確認了沒有。使用者 2026-10-11 裁示採用 D 方案（收件人以加密簽收單回報、送出端按收件人記帳），寫在 [ADR 0068](0068-per-recipient-relay-budget-with-encrypted-receipts.md)，**與本 ADR 分開出版**：本 ADR 不改送出端預算；ADR 0068 只改客戶端、不需要本 ADR 的中繼擴充。

## 實作計畫（TDD）

1. 中繼：確認事件的解析與驗證（AUTH、簽章、pubkey、id 格式、數量上限）→ 兩種儲存的降級 → 不存不轉發 → NIP-11 宣告（寬限取 `PUBLIC_LANE_RETENTION_SECONDS` 與站方保存上限的較小者）。
2. 客戶端：`NostrVaultTransport` 記錄每則訊息由哪些外層 id 組成 → 協調器回報「已保存」→ 批次確認 → 只對有宣告的中繼送。
3. 整合測試：真正的 `RelayCore`＋兩台裝置：處理完的包在寬限後消失、沒處理完（當掉、未信任寄件人）的留著、確認不到別人的列、舊客戶端與不宣告的中繼行為不變。
4. 把 2026-10-11 的測量腳本改成可重跑的基準測試（不進 CI 預設）。
5. CinderSync：升級 SDK，並在 `onLimits` 接上 `setInboxAckRelays`（見〈實作紀錄〉）；README 寫明中繼上的包處理完約兩小時後清掉。

## 實作紀錄（2026-10-11，TDD）

中繼：

- `protocol/inbox-ack.ts`：`INBOX_ACK_KIND`（25190，SDK 與 Cinderous 都沒有用過這個號碼；IoT 用 25170–25173）、`INBOX_ACK_MAX_IDS`、`buildInboxAck`、`inboxAckIdsOf`（任何一段不是 64 位小寫 hex 或超過 500 個 ⇒ 整則不處理）。
- `OfflineStore.ackInbox(recipient, ids, expiresAt, now)`（選用）：兩種儲存都只提早、不延後；**寄給多位收件人的事件不動**——記憶體版的到期時間是每顆事件一份，降了會連累其他收件人；SQL 版以「庫裡有沒有同 id、別的收件人的列」判斷，走主鍵、不讀 json（檔案塊的 json 在溢位頁上）。
- `RelayCore` 的 `inboxAckGraceSec`：與 NIP-62 同一個位置（速率限制之後），不存、不扇出。沒設＝那個 kind 照一般瞬時事件轉發（舊行為）。
- 寬限由 `inboxAckGraceFor(storeOptions)` 算（`PUBLIC_LANE_RETENTION_SECONDS` 與這顆 DO 保存上限的較小者），Worker、Node 宿主與 NIP-11 共用同一個函式。
- NIP-11 `cinder_inbox_ack: { kind, grace_sec }`；唯讀寬限期的路徑、Node 版 `REQUIRE_AUTH=0`（不發挑戰，沒有人證明得了「自己的收件匣」）不宣告也不處理。
- 拒收句子沿用既有詞元（`self-only`、`malformed`），契約測試多兩列。

客戶端：

- `VaultSyncTransport.onMessage` 的監聽者回傳型別改成 `unknown`（原本 `void`，`(m) => list.push(m)` 這種寫法照樣通過型別檢查）：回傳 **Promise** 才算表態，完成＝處理完而且已保存，reject＝沒有。至少一個監聽者表態、而且全部完成才確認；應答器這類不回傳的旁聽者不擋。
- 協調器的 `#onMessage` 回傳那個 Promise：這次工作結束時寫回狀態（`#persist`）失敗就 reject。原本「不必等」的背景寫入（等父版本的 `w:`、待推送清單 `x:`、佇列 `q:`）改經 `#bg` 追蹤，`#persist` 會等它們落地，失敗就算這一輪沒保存好（以前失敗是未處理的 rejection）。自己的、格式不對的、沉睡暫停中擱著的訊息不表態。
- `NostrVaultTransport`：重組時記下每個訊框的外層 id（含重複的訊框）；選項 `inboxAck`（預設開）、`inboxAckRelays`、`inboxAckBatch`（滿幾個就送，1–500、預設 500；測試用它避免真的加解密 500 則），方法 `setInboxAckRelays`、`flushInboxAcks`。滿 500 個、5 分鐘、補拉完成、`stop()` 時送；送不出去留著（最多 5,000 個，超過丟最舊的，那些只是放滿保存期）。走同一身分的事件預算（`publishPaced`）。
- `RelayPool.publish` 新增 `relays` 選項：只送給那幾座（確認只送給宣告了的中繼）；給了就不走耐久度路徑。
- `fetchRelayFilePolicy` 讀出 `inboxAck`；`inboxAckRelays(policies)` 挑出宣告了的那幾座；`watchRelayFileLimits` 的 `onLimits` 多第三個參數 `policies`。
- **CinderSync 要接一行**（不是「升級 SDK 即可」）：在 `watchRelayFileLimits` 的 `onLimits` 裡 `transport.setInboxAckRelays(inboxAckRelays(policies))`。

端對端（實作計畫第 3 項，`tests/sync/vault/inbox-ack.e2e.test.ts`）：真的 Node 中繼（SQLite）、三台裝置各用真的 `RelayPool`（NIP-42）、傳輸層與協調器，支援與否從真的 NIP-11 讀。a 寄給 b、b 處理完的包在中繼的 SQLite 裡到期時間變成「現在＋7200 秒」；不在 b 信任名單的 mallory 寄來的仍是 7 天；不送確認的舊客戶端照舊 7 天。

基準測試（實作計畫第 4 項，2026-10-12）：`npm run measure:inbox-ack`（`vitest.measure.config.ts` 只收 `tests/bench/*.measure.ts`，`npm test` 不跑）。可用環境變數 `DAYS`、`GRACES`（分鐘，逗號分隔）、`SCENARIOS`、`MEASURE_OUT` 調整。中繼重放模型抽到 `tests/bench/relay-replay.ts`，它自己的測試（`relay-replay.test.ts`）在 CI 裡跑。重跑結果與〈測量〉一節的表逐位相同（約 2 分鐘）。

CinderSync（第 5 項）：已接線，CinderSync ADR 0049（f562990）。錨點跑 Cinderous 自己的中繼、不是 SDK 中繼，使用者 2026-10-12 裁示等 Cinderous PR #9（SDK 公開後）再生效，不另外移植。

## Consequences

- 好處：中繼佔用約降 95%、重複下載 86% → 40%（以 2026-10-11 的模擬，寬限 2 小時；寬限 1 小時那欄的 0% 是整點輪次的巧合）；一般用量不再撞到每收件人配額；誠實中繼日後出事時可取得的密文大幅減少。
- 代價：新增 Cinderous 專屬的中繼擴充（不是標準 NIP）；客戶端要把「已保存」接回傳輸層，時機錯了會在寬限後掉訊息（靠摘要補回）。
- 不變：ADR 0066 的中繼資料外洩；公開中繼上的行為。
- 另案：測量時看到同一個版本被送了不只一次（一般使用 388 個版本，最多 4 次；手機出遊情境最多 11 次），原因未查，可能是 harness 的連線模型或協調器的重送，另外調查。
