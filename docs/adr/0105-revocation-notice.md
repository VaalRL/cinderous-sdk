# 0105. 撤銷通知：撤銷的那台另外送被撤銷的裝置一份精簡名單

- 狀態：**已接受（Accepted，2026-10-22）**——使用者 2026-10-22 同意「撤銷時另外送一則通知給被撤銷的那台」
- 日期：2026-10-22
- 對應：SDK ADR 0028（名單、撤銷永遠贏、撤銷後輪換）、0045（送不出去的名單變動）、0082（名單與 Vault 傳輸共用訂閱）；CinderSync ADR 0099（`sync-state.json` 的 `member`）

## Context

2026-10-22 用 Pixel 8a（CinderSync，SDK v0.72.0）實測「被撤銷的裝置要多久才知道自己被移除」：

| 條件 | 結果 |
|---|---|
| 撤銷時離線，約 1 小時後才打開 | 從收件匣補到撤銷**之前**的名單更新，撤銷那一份沒有寄給它；狀態 `running`、自認是成員 |
| 在線時被撤銷 | 3 分鐘後仍是 `running`、自認是成員 |
| 撤銷後在手機新增筆記並立即同步 | 顯示「即時同步中」、佇列送完、沒有任何錯誤；桌機**沒有收到** |

原因：ADR 0028 的設計是「被撤銷的裝置收不到之後的名單與新金鑰」——`announce()` 只送給目前有效的成員。被撤銷的裝置只有收到一份「名單裡有它自己的撤銷紀錄」的名單，`merge` 才會發 `selfRevoked`，但這份名單永遠不會寄給它。結果是使用者一直以為在同步，寫的內容卻沒有人收（其他成員的協調器早就不收它的訊息），也沒有任何提示。

## Decision

1. **撤銷的那台另外送一份精簡名單給被撤銷的裝置**（`buildRevocationNotice`）：
   - `devices: []`：不告訴它現在有哪些成員；
   - `revoked`：**只有它自己的那一筆**撤銷紀錄（撤銷者簽章，照舊驗證）；
   - `keys`：扣掉撤銷時輪換出來的新金鑰——它本來就有的舊金鑰。名單格式至少要有一把金鑰，扣完沒有就不送；
   - 不帶能力、備援、輕量成員、改名宣告。
2. **用一般名單的格式送**（內層 kind 4361、外層照 `outerKind`、帶 `expiration`）。被撤銷的裝置走既有的 `merge`：寄件人在它的名單上是成員、撤銷紀錄的簽章正確 → 自己不再是成員 → `selfRevoked: true`。所以**被撤銷的裝置不必升版**，只要撤銷的那台是新版。
3. **在 `NostrRosterSync` 收到 `reason: 'revoke'` 的變動時，當下就包好**——那時的「目前金鑰」正是撤銷時輪換出來的新金鑰，扣掉它。從別台合併得知的撤銷（`reason: 'merge'`）不送，撤銷的那台送過了。
4. **盡力而為**：與名單同一份事件預算（`publishPaced`）、同一個耐久度要求；送不到只經 `onError` 回報，不記成 ADR 0045 的「有未送出的名單變動」（那是給還是成員的裝置的）。
5. 撤銷時離線的裝置：通知留在中繼的收件匣（`expiration` 預設 7 天，另受中繼的保存期限制），它上線補拉時一樣收到。

## Consequences

- ＋ 在線或之後才上線（在中繼保存期內）的被撤銷裝置都會進入 `selfRevoked`，CinderSync 會停止同步、提示使用者、狀態變成 `removed`（`sync-state.json` 的 `member: false`）。
- ＋ 不洩漏撤銷之後的任何東西：沒有新金鑰、沒有成員清單、沒有其他人的宣告。它知道的只有「誰、什麼時候撤銷了它」，這原本就在它看得到的範圍內。
- ＋ 舊版的被撤銷裝置也收得懂。
- － 被撤銷的裝置若不認得撤銷者（撤銷者是它離線之後才加入的），`merge` 會因寄件人不是成員而不收。補拉時它會先收到撤銷者加入的那份名單（加入時它還是成員），事件順序不保證時可能漏掉；這種情況維持原狀（不知道自己被撤銷）。
- － 離線超過中繼保存期才上線的裝置收不到通知，維持原狀。
- － 每撤銷一台多發一顆事件。
- 測試：`tests/pairing/revocation-notice.test.ts`（在線、離線後補拉、通知內容、`buildRevocationNotice` 的邊界、合併得知的不重送）；`tests/pairing/roster.test.ts` 原本「撤銷後沒有任何事件寄給被撤銷的」改成「只寄一份通知、仍拿不到新金鑰」。
