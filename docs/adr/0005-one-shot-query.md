# 0005. 一次性查詢 `query`：等每一座都回 EOSE

- Status: Accepted
- Date: 2026-09-27
- 加註（2026-10-01，ADR 0045）：`query` 在一座都沒開、或查到一半全部斷線時也回陣列，分不出「查完了、沒有」；v0.36 新增 `queryResult`（`answered`＝回完的座數、每座狀態），依結果推進游標的程式碼改用它。`query` 的回傳不變。

## Context

`subscribe` 是常駐訂閱，`onEose` 只在第一座回 EOSE 時叫一次。這對「打開畫面時載入一份清單」
不夠：如果第二座站上才有的事件晚一步才到，清單就少了幾筆。
《元素使》的讀法全是這種一次性查詢（牌組清單、留言板、私訊收件匣），它原本的連線客戶端就有 `list`。

## Decision

`query(filters, timeoutMs)`：

- 對每一座開著的站送同一個 REQ。
- 每一座都回 EOSE、被 `CLOSED` 或斷線之後才回。
- 逾時就帶著已經收到的結果回，不會因為一座站卡住就整個失敗。
- 結果以 id 去重、先驗簽，依 `created_at` 由新到舊排序；結束時對每一座送 CLOSE。
- 如果還沒有任何一座開起來，就在同一個逾時內等第一座開起來；一直沒開就回空陣列。
- 被 `CLOSED` 時，理由經 `onRelayProblem` 回報。
- （v0.4.1）被 `auth-required` 擋下、而且有身分時，等 NIP-42 認證成功後對那一座重送，和常駐訂閱、發布同一套；認證失敗就不再等那一座。
  私訊收件匣（`#p` 自己）就是這個情況：連上的同時查詢就出去了，認證還沒完成。

## Consequences

- ＋ 不必自己組「subscribe＋計時器＋手動 close」。
- － 回空陣列有兩種可能：真的沒資料，或者一座都連不上。
  要分辨時看 `status()`，或用 `onStatusChange` 確認至少有一座開過。
