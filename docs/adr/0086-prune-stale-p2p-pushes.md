# 0086. 待直送的大檔內容不在了就馬上剔除：不讓應用為已刪除的檔案一直等 P2P

- 狀態：**已接受（Accepted，2026-10-15）**——使用者 2026-10-15「兩個需要我決定的：依你建議方式修復」
- 日期：2026-10-15
- 對應：ADR 0053（P2P 直送、`pushes`）；CinderSync ADR 0021（立即同步等對方上線）、TODO〈P2P〉2026-10-15 桌機實機驗證

## Context
協調器替每台不在線、要直連才收得到的裝置記一筆「待直送」（`#pushes`，持久化在 `x:`）。內容已經不在磁碟上的（檔案刪了、被新版本取代）
原本只在**真的要送給那台時**（`#p2pWork` 讀不到內容）、或那台過期（`STALE_DEVICE_MS`）才剔除。

2026-10-15 實機：桌機 A 傳了 40 MB／60 MB 的測試檔給 B，手機一直沒上線；把兩個檔刪掉之後，`status().pushes` 仍是 3～4。
CinderSync 依 `pushes > 0` 判定「還有大檔要直傳」，於是每次按立即同步都多等 3 分鐘對方上線、狀態列的待傳數也偏高。資料不受影響。

## Decision
- 新增 `#prunePushes()`：檔案紀錄或版本不在、版本是刪除、或磁碟上的內容雜湊已經不是那個版本（`rec.disk?.hash !== node.hash`），就 `#dropPush`
  （連同 `x:` 的持久化）。與 `#p2pWork` 讀不到內容時的判定相同（`#diskSource`）。
- 在 `status()` 算 `pushes` 之前、以及 `#pump()` 決定要不要排 P2P 之前呼叫——應用與協調器看到的都是剔除後的數字。
- 新版本自己會另外排一筆（照舊）。

## Alternatives Considered
- **在每個本機修改／刪除的處理路徑裡剔除**：路徑很多（本機修改、刪除、改名、遠端合併改寫磁碟、排除），容易漏；集中在讀取數字的地方一處就好。
- **讓應用自己判斷**：應用看不到 `#pushes` 的內容，做不到。

## Consequences
- ＋ 刪除或取代待直送的大檔後，`pushes` 立刻正確；應用不再為它等 P2P。
- － `status()` 會順手刪掉幾筆持久化的 `x:`（背景寫入）；每次走一遍 `#pushes`（上限 `MAX_PUSHES`），成本小。
- 驗證：`tests/sync/vault/p2p.test.ts`〈待直送的大檔在對方上線前就刪掉或被新版取代〉（刪掉 → 剔除；被新版取代 → 只剩新版那一筆、`x:` 也只剩一筆）。
