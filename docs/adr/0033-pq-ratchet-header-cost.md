## Context

v0.27 以前的後量子雙棘輪（ADR 0010 §2）每次 DH 步進都附一把新的 ML-KEM-768 公鑰，並對「對方最近一把公鑰」封裝一份密文，兩邊在 KDF_RK 立即混入。因為接收端可能先收到同一條鏈的**任何**一則，所以**每一則**都得帶這兩個欄位：

| 欄位 | 位元組 |
|---|---|
| 版本、DH 公鑰、PN、N | 41 |
| 旗標 | 1 |
| ML-KEM-768 公鑰 | 1,184 |
| ML-KEM-768 密文 | 1,088 |
| **合計（每一則）** | **2,314** |

星狀會話（ADR 0030 §6）實測一則 20 B 的按鍵更新：成員→Host 2,395 B、Host→每位成員 2,434 B；經中繼一則 8,702 B 的事件。8 位成員時一次不合併的按鍵，Host 上行約 19.5 KB。應用層批次（50 筆合一則 3,767 B）只能緩解。

## Decision

### §1 核心想法：KEM 輪次與 DH 步進脫鉤，延後混入

- **一輪 KEM**＝「一方公布一把 ML-KEM 公鑰 → 另一方封裝 → 公布者在自己下一次 DH 步進時混入」。每一方各自的公鑰編號 0、1、2…，輪次就用公鑰的編號。
- **不是每一步都做**：封裝方手上有對方還沒用過的公鑰、上一輪已經被混入、而且自上一輪以來自己送滿 `pqRekeyInterval` 則（預設 50）才封裝（§3）。
- **延後混入**（與 v1 最大的不同）：密文所在那條鏈的金鑰**不依賴**這份密文。解封裝方在自己**下一次 DH 步進的傳送半步**才把共享秘密串進 KDF_RK，並在那條鏈每則 header 寫 `mix`＝輪次編號；封裝方收到那條鏈時，在接收半步用同一份秘密。
  - ⇒ 帶密文的那一則遺失或晚到，**只會延後後量子的自癒，不會讓任何一則解不開**。這是可以只附一次的關鍵。
  - 傳送半步放在「MAC 驗過、KEM 欄位收下」之後：步進那一則自己帶的密文，這一步就能混入（雙向輪流時一輪只要一個來回）。
- **例外：Alice 的第一條鏈**綁定握手時 Bob hello 裡的 ML-KEM 公鑰（輪次 0），**立即混入**，與 v1 相同；這條鏈每一則都帶那份密文，Bob 的第一個接收步進沒看到就拒絕。⇒ 從第一則起，所有鏈金鑰都含後量子秘密（§7）。在 `secureChannel` 裡這條鏈只有「開始」一則控制訊息。

### §2 訊息格式（header 版本 3；大端序）

| 位移 | 長度 | 欄位 | 說明 |
|---|---|---|---|
| 0 | 1 | 版本 | `3`＝後量子 v2。`1`＝古典（與 v0.27 相同，不變）。`2`＝v0.27 的後量子格式，**已不支援** |
| 1 | 32 | DH 公鑰 | secp256k1 x-only（同 v1） |
| 33 | 4 | PN | 上一條傳送鏈的長度（同 v1） |
| 37 | 4 | N | 序號（同 v1） |
| 41 | 1 | 旗標 | bit0＝帶公鑰、bit1＝帶密文；其他位元必須是 0（否則視為壞 header） |
| 42 | 4 | ackPk | 我收到的**對方**公鑰最大編號；`0xFFFFFFFF`＝還沒有 |
| 46 | 4 | mix | 這條鏈混入的**我方**輪次編號；`0xFFFFFFFF`＝沒有 |
| 50 | 4＋1,184 | 公鑰（選用） | 我方目前的公鑰編號＋ML-KEM-768 公鑰 |
| 50 或 1,238 | 4＋1,088 | 密文（選用） | 輪次編號（＝對方公鑰編號）＋ML-KEM-768 密文 |

- 整個 header 仍是 AEAD 的附加資料（AD＝會話 AD ‖ header），任何一個位元被改都在 MAC 失敗。
- `EncryptedEnvelope.kemAlgorithm` 為 `'pq-double-ratchet-v2'`（型別聯集保留 v1 值以免外部程式編譯失敗，但不再產生）。
- `ratchetHeaderLength(bytes)` 依旗標算長度，`secureChannel` 用它切「header ‖ 密文」。

### §3 狀態機

每一方的後量子狀態（全部有上限：同時最多一把自己的私鑰、一把對方未用的公鑰、一個等混入的外送輪次、一個等混入的內收輪次）：

| 狀態 | 意義 |
|---|---|
| `kem`／`kemId` | 我目前的 ML-KEM 金鑰對與編號；被對方封裝、我解封裝後立刻換下一把（舊私鑰與種子在解密成功後清零） |
| `peerAck` | 對方回報收到的我方公鑰最大編號；`< kemId` 時，每條新傳送鏈的第一則附上公鑰 |
| `peerKemId`／`peerKemPk` | 我收到的對方公鑰最大編號，與還沒封裝過的那一把（封裝後丟掉，一把只用一次） |
| `out`（`outId`、`outCt`、`outSs`） | 我封裝出去、等對方混入；每條新傳送鏈附一次密文，直到對方某條鏈的 `mix` 等於 `outId` |
| `in`（`inId`、`inSs`） | 對方封裝給我、等我下一次傳送半步混入 |
| `sendMix` | 目前這條傳送鏈混入的我方輪次，寫進每則 header |
| `sinceRound` | 自上一次封裝以來我送了幾則 |
| `initCt` | Alice 第一條鏈的握手密文（每則都帶，第一次步進後丟掉） |
| `outStall`／`pkStall` | 看門狗計數（§6） |

轉移：

1. **加密**：若（沒有 `initCt`、沒有 `out`、手上有 `peerKemPk`、`sinceRound ≥ interval`）→ 封裝，進入 `out`，`sinceRound = 0`。然後依上表決定附不附公鑰／密文（每條鏈各最多一次），`sinceRound += 1`。整段在第一個 `await` 之前做完（並發不重用金鑰）。
2. **解密**（交易式：任何一步失敗整批還原）：
   - 新鏈 → 接收半步：`mix ≠ 無` 就必須等於 `outId`（否則拒絕），用 `outSs` 推導接收鏈、清掉 `out`；`mix = 無` 而 `out` 還在 → `outStall += 1`；`ackPk < kemId` → `pkStall += 1`。Bob 的第一條接收鏈改走 §1 的例外。
   - 驗 MAC、解開。
   - **吸收 KEM 欄位**（只在 MAC 驗過之後）：`ackPk` 取最大；公鑰編號只能是 `peerKemId + 1`（相同或更小＝重帶，略過；跳號＝協定錯誤）；密文編號等於 `kemId` → 解封裝、進入 `in`、換下一把公鑰（更小＝重帶或晚到，略過；更大，或 `in` 已經有東西＝協定錯誤）。
   - 新鏈 → 傳送半步：新 DH 金鑰對，`in` 有東西就混入並記在 `sendMix`。
   - 跳過的金鑰（亂序、遺失）與 v1 相同；用跳過的金鑰解開的舊鏈訊息，KEM 欄位照樣吸收，但不會觸發任何混入。

### §4 取捨與量化

**header 大小**（`tests/crypto/double-ratchet-pq.test.ts` 的量測）：

| 情境 | v0.27 | v0.28 |
|---|---|---|
| 連續打字（同一條鏈） | 2,314 B | **50 B** |
| DH 步進的第一則（沒有輪次） | 2,314 B | **50 B** |
| 輪次開始（附密文） | 2,314 B | 1,142 B |
| 換了新公鑰（附公鑰） | 2,314 B | 1,238 B |
| 握手後 Alice 第一則（握手密文＋公鑰） | 2,314 B | 2,330 B |
| 雙向輪流 600 則、間隔 50，平均每則 | 2,314 B | **94 B**（理論 50＋2×2,280÷100 ≈ 96） |
| 單向 500 則、對方不回 | 每則 2,314 B | 1 則 1,142 B，其餘 50 B |
| 古典（對照） | 41 B | 41 B（不變） |

**星狀會話**（`tests/star/integration.test.ts`，真的 `secureChannel`＋`StarHost`／`StarMember`；位元組是 PeerChannel 上的一則訊息）：

| 情境 | v0.27 PQ | v0.28 PQ | 古典 |
|---|---|---|---|
| 成員送一則 20 B 更新 | 2,395 B | **131 B** | 122 B |
| Host 轉送一則 20 B 更新（每位成員） | 2,434 B | **170 B** | 161 B |
| 同一批次視窗 50 則 | 3,767 B | **1,503 B** | 1,494 B |
| 經中繼一則 20 B（kind 20079 事件） | 8,702 B | **2,214 B** | 2,214 B |
| 經中繼 50 則合併 | 14,162 B | **5,970 B** | 5,970 B |

中繼軌的事件在 NIP-44 填補後與古典落在同一級距，完全相同。8 位成員時一次不合併的按鍵，Host 上行從約 19.5 KB 降到約 1.4 KB。

**頻寬 vs 遺失容忍度**：每一輪每個方向的固定成本是一份密文＋一把公鑰＝2,280 B。每條傳送鏈只附**一次**（c＝1）：

- 延後混入讓「附的那一則掉了」的代價只是**多等一步**（下一條鏈重帶），不是解不開。遺失率 p 時，每一輪平均多 p／(1−p) 個來回（20% 遺失 ≈ 0.25 個來回），每多一次重帶多 1,092 或 1,188 B。
- 若每條鏈附 c 次：失敗率降到 p^c，但只有「一條鏈有 c 則以上」（單向打字）才有差；雙向輪流時每條鏈常常只有一則，多附也沒用，卻每輪多 (c−1)×2,280 B。P2P 軌是可靠有序的，c＝1 永遠夠。⇒ 取 c＝1。
- 單向打字時，輪次開在鏈的中間，對方那時已經開好自己的傳送鏈，要等下一步才混入 ⇒ 封裝方換鏈時多重帶一次密文（1,092 B）。這是可接受的一次性成本。
- **`pqRekeyInterval`**（預設 50，1～10,000）：越小，狀態外洩後量子攻擊者能跟的訊息越少（§7），頻寬越大。1＝每一步都有輪次在跑（接近 v1 的自癒頻率），攤提仍遠低於 v1，因為只有公鑰或密文、而且只附一次。50 取自 iMessage PQ3（約每 50 則）。

### §5 協定版本與舊版對端

- `secureChannel` 的 hello（JSON）多一個 `pqf: [2]`：支援的後量子線路格式清單。v0.27 的解析器只看 `v`／`dh`／`kem`，會略過它。
- 要後量子，而對方的 hello 有 ML-KEM 公鑰卻沒有共同的 `pqf`（v0.27 以前）⇒ **明確拒絕**：丟 `UnsupportedRatchetVersionError`（`peerFormats` 帶對方宣告的清單），訊息請雙方升級到 0.28.0。**不退回舊格式，也不退回古典。** 對方（舊版）這邊會逾時。
- 兩則 hello 都雜湊進握手秘密：中間人拿掉 `pqf` ⇒ 這邊明確拒絕；改掉 `pqf` 的內容 ⇒ 雙方算出不同的秘密、金鑰確認失敗。中間人無法把雙方降到舊格式。
- **古典模式不受影響**：header 與 v0.27 逐位元相同，hello 沒有 `pqf` 也接受 ⇒ 新舊版本的古典會話照樣互通（有測試：手刻的 v0.27 對端）。
- **舊的後量子解碼器直接移除，不保留過渡期**，理由：
  1. 沒有任何已發布的使用者（上表）；兩個預定使用者（未發布外掛）會一起升級 SDK。
  2. 保留等於同時維護兩套後量子狀態機，審查面加倍；而舊格式「每則都帶 KEM」的混入時機與新格式不同，無法共用程式碼。
  3. 雙棘輪只用在即時通道（ADR 0010 §2），沒有離線佇列或長期保存的密文需要舊解碼器。
  - `fromState` 照樣還原 v0.27 匯出的**古典**會話（v:1）；v0.27 的**後量子**會話狀態明確拒絕（請重新握手）。匯出格式升到 v:2。
- `ICryptoSession`、`secureChannel` 的簽章不變；新增選用參數 `pqRekeyInterval`（`RatchetInit` 與 `SecureChannelOptions`），新增匯出 `DEFAULT_PQ_REKEY_INTERVAL`、`UnsupportedRatchetVersionError`、`RatchetProtocolError`（§10 #5）。`chooseEngine`／`crypto_engines`（ADR 0014）不變：它決定用不用雙棘輪，線路格式版本在通道內的 hello 協商。

### §6 威脅模型與降級防護

攻擊者能力：

- **被動、將來有量子電腦**（今天側錄、將來解密）：主要對象。
- **主動網路攻擊者**：中繼軌的中繼業者、P2P 路徑上的人。能丟、延遲、重排、重放任何一框；若外層（NIP-59／DTLS）失守，也能竄改棘輪的位元組——雙棘輪必須自己擋得住。
- **一時的狀態外洩**（裝置被入侵一段時間後清除）：談 FS 與 PCS。
- 已認證的對方不是攻擊者（它本來就看得到明文）。

| 攻擊 | 結果 |
|---|---|
| 拿掉 KEM 欄位（清旗標、截短） | header 是 AD ⇒ MAC 失敗、狀態不變 |
| 版本改成 1（古典）或 2（舊版） | 後量子會話只收版本 3 ⇒ 拒絕（舊版有專用錯誤訊息） |
| 改 `mix`、`ackPk`、公鑰或密文編號 | MAC 失敗；`mix` 還同時改變鏈金鑰的推導 |
| 拿掉 Alice 第一條鏈的握手密文 | Bob 的第一個接收步進直接拒絕，不會變成只有古典的起點 |
| 重放帶密文／公鑰的訊息 | 與 v1 相同的重放檢查（同鏈序號、跳過金鑰用過即刪、退役鏈）；同一輪的密文就算合法重帶，也只解封裝一次 |
| **選擇性丟包**：專丟帶密文或公鑰的訊息，其他照送 | v1 不存在這個問題（每則都帶）。v2 用**看門狗**：對方已經步進超過 16 次（`PQ_STALL_LIMIT`），我封出去的輪次還沒被混入、或我的公鑰還沒被回報收到 ⇒ 丟 `SecurityDowngradeError`、銷毀會話；`secureChannel` 關閉通道並經 `onListenerError` 回報（握手中則握手失敗）。**不靜默退回純古典**（ADR-0365） |
| 在協商時拿掉或改掉 `pqf` | §5：明確拒絕或握手失敗 |
| 改匯出的狀態（`pq:false`、刪欄位、不一致的編號） | `fromState` 逐欄驗型別、長度與彼此的一致性，拒絕 |

- 看門狗只數**對方的步進**，而計數在解密的交易裡：偽造的訊息過不了 MAC、計數跟著還原，所以中間人只能靠「丟掉合法的訊息」觸發它——那本來就等於阻斷服務（把所有訊息都丟掉也一樣）。
- 正常遺失下的誤判：需要連續 17 次對方步進都沒拿到重帶的那一則。20% 遺失約 1.3×10⁻¹²，50% 約 7.6×10⁻⁶（每一輪）。有測試：20% 隨機遺失＋亂序、雙向約 1,200 則，零誤判、輪次持續完成。
- 對照 SPQR：SPQR 用抹除碼讓「丟掉任意幾則」擋不住重建（容忍）；我們選擇「偵測後關閉」（fail closed），實作簡單得多，代價是攻擊者可以讓會話斷線、重新握手——它本來就能讓會話斷線。

### §7 安全性質（與 v0.27 相比）

- **後量子保密（今天側錄、將來解密）：範圍不變，每一則都涵蓋。** 所有鏈金鑰都由根金鑰推導，而根金鑰是 HKDF 鏈：Alice 第一條鏈在第一步就混入輪次 0 的 ML-KEM 秘密（封給 Bob 握手時的公鑰，私鑰從沒離開 Bob），之後每一把根金鑰、鏈金鑰、訊息金鑰都由它延續而來。量子攻擊者能解出所有 ECDH，但解不出這份 ML-KEM 秘密，所以推不出任何一把訊息金鑰。**同一條鏈後續訊息的後量子保護來自鏈金鑰的延續**（HMAC 鏈，起點是含 KEM 秘密的根金鑰）——v1 也是如此：v1 每一步再混入的 KEM 秘密，對「沒有狀態外洩」的攻擊者不增加保密，只增加下述的自癒。
- **握手本身**仍只有古典部分（ADR 0010 已知限制，不變）：擋不住「握手當下就有量子電腦的主動攻擊者」。
- **前向保密（FS）：不變。** 訊息金鑰用過即刪、鏈金鑰與根金鑰單向、舊 DH 私鑰清零，機制與 v1 相同。狀態裡等混入的 `outSs`／`inSs`、還沒用的 ML-KEM 私鑰外洩，只影響**之後**要混入的秘密（屬於 PCS），推不回過去的訊息。
- **古典事後自癒（PCS，對古典攻擊者）：不變**，每一步都有新的 DH。
- **後量子事後自癒（對「狀態外洩後、又有量子電腦」的攻擊者）：變慢，這是本 ADR 唯一明確的削弱。**
  - v1：外洩結束後的下一步就混入攻擊者不知道的 KEM 秘密（約一個來回）。
  - v2：攻擊者拿到外洩當下的全部狀態（含我目前的 ML-KEM 私鑰、等混入的 `outSs`／`inSs`），之後能用量子電腦跟著 DH 步進，直到「外洩結束後才開始的一輪」被混入。外洩當下已經在進行的輪次（以及對方之後封給我**外洩時那把**公鑰的一輪）攻擊者都知道，救不了；要等下一輪。⇒ 最壞約某一方再送 **2 × `pqRekeyInterval`**（預設約 100 則）加幾個來回（安全審查 #1 實測）。若攻擊者同時做選擇性丟包，每一輪還能在看門狗門檻內再拖 16 步。`pqRekeyInterval: 1` 可把它壓回接近 v1。
  - 狀態外洩時，也同時外洩當時的訊息金鑰與鏈金鑰；這段期間的損失與 v1 相同。
- **中繼資料**：`ackPk`、`mix`、輪次編號與「這則有沒有帶 KEM」（看大小就知道）都是明文，會洩漏輪次的節奏；外層仍有 NIP-59（中繼軌）或 DTLS（P2P）。
- **資源**：每一輪每方最多一次封裝、一次解封裝、一次金鑰生成；已認證的對方最快也只能每一步推進一輪（密文編號必須等於我目前的公鑰、`in` 必須是空的），所以 ML-KEM 運算量不會超過 v1（v1 每一步都各做一次）。記憶體有固定上限（§3）。

### §8 與 Signal SPQR（Triple Ratchet）、Apple PQ3 的比較

| | SPQR（Signal，2025） | PQ3（Apple，2024） | 本 ADR |
|---|---|---|---|
| KEM 何時做 | 持續：ML-KEM Braid，一個 epoch 一輪 | 定期：約每 50 則、至少每 7 天 | 定期：每方每送 `pqRekeyInterval`（預設 50）則 |
| 線路上怎麼送 | 抹除碼切成小塊，**每則都帶一塊**（大小均勻）；Braid 把公鑰拆成 64 B 種子＋其餘，讓封裝與傳公鑰平行 | 輪到時那一則帶完整的公鑰＋密文（「多 2 KB 以上」） | 輪到時帶完整的公鑰或密文，每條鏈一次，直到被確認 |
| 金鑰怎麼結合 | 兩條獨立的棘輪，每則訊息金鑰＝KDF(雙棘輪金鑰, SPQR 金鑰) | HKDF-Extract 依序串進會話金鑰 | 串進雙棘輪的根金鑰 KDF（與 v1 相同） |
| 選擇性丟包 | 抹除碼：收到任意足夠的塊就能重建（容忍） | —（公開文件未詳述） | 看門狗偵測後關閉（fail closed） |
| 降級 | 只在第一次收到對方訊息時允許降級 | — | 不允許：握手時就協商，沒有共同版本就拒絕 |
| 驗證 | ProVerif、F*、hax 形式驗證並接 CI | 形式分析（Tamarin 等） | 內部審查＋攻擊測試，**未經外部審計、未形式驗證** |

**為何不採用 SPQR 的做法**：

- 複雜度：Braid 的狀態機（header／ek／ct1／ct2 四種訊息）、抹除碼、epoch 管理、第二條棘輪，對一個沒有外部審計的 SDK 來說審查面太大。本 ADR 的差異只在「何時附、何時混入」，混入點仍是 v1 已審查過的 KDF_RK。
- 我們的傳輸不需要均勻的小訊息：P2P 軌一框 16 KB、中繼軌 48 KB 且有 NIP-44 填補；偶爾一則 1–2 KB 沒有問題。SPQR 切塊是為了讓每則訊息的大小固定、不在行動網路上造成可見延遲。
- 選擇性丟包：SPQR 靠抹除碼容忍；我們偵測後關閉，行為可預期、程式短。
- SPQR 的「兩條獨立棘輪、每則訊息金鑰兩邊結合」在一條棘輪的實作有缺陷時仍有保護（縱深防禦）；本 ADR 沒有這一層，列為未來選項（若日後做外部審計或形式驗證，一併評估）。

**與 PQ3 最接近**：定期、完整大小、偶爾出現的 KEM 負載；差別是我們延後到對方下一步才混入、每條鏈只附一次、有看門狗；沒有時間上限（雙棘輪只用在即時通道，通道一斷會話就結束，ADR 0010 §2）。

### §9 測試（TDD）

- `tests/crypto/double-ratchet-pq.test.ts`（26）：header 格式與大小（第一則 2,330、Bob 第一則 1,238、之後 50）、`ratchetHeaderLength`、參數驗證；輪次狀態機（送滿間隔才封裝、附一次、對方下一步混入、混入後不再重帶）、雙向輪流、間隔 1；**遺失與亂序**（Alice 第一條鏈的第一則遺失、帶密文的那一則遺失、**DH 步進的第一則遺失**、密文比對方步進晚到、20% 隨機遺失＋亂序約 1,200 則）；**長時間單向**（500 則只帶一次密文，對方回應後完成輪次）；**重放與降級**（重放帶密文的訊息與握手第一則、拿掉 KEM 欄位、改版本、竄改 `mix`／`ackPk`／密文編號、第一條鏈拿掉握手密文、**選擇性丟密文**、**選擇性丟公鑰**）；**並發**（間隔 1 下同時加密 50 則、同時解密跨步進的亂序一批＋重放）；匯出還原（輪次進行到一半、Alice 第一條鏈、嚴格驗證、v0.27 古典狀態）；量測。

### §10 安全審查（2026-09-29，內部、唯讀審查者）

審查範圍：`src/crypto/double-ratchet.ts`（逐行）、`secure-channel.ts`、`types.ts` 與新測試。審查者在暫存目錄寫了攻擊與模糊測試（4 組設定 × 12 個種子、20–50% 遺失、亂序 20–100 則、交錯、隨機匯出再還原，約 19,500 則成功解密：**0 次非預期錯誤、0 次看門狗誤判、明文全對**），跑完即刪，未留在 repo。**沒有 Critical／High。**

| # | 嚴重度 | 發現 | 處理 |
|---|---|---|---|
| 1 | Medium（設計取捨） | 後量子事後自癒比 v1 慢：外洩當下進行中的輪次攻擊者已知，最壞約 2 × `pqRekeyInterval` 則＋幾個來回；選擇性丟包者每輪還能在看門狗門檻內再拖 16 步（實測：兩方向各連丟 16 則帶密文的才放 1 則，800 則只完成 32 輪、不觸發；連丟 17 則就觸發） | 接受為設計取捨；§7 與 README 寫明上限，不宣稱「與 v1 相同的每步自癒」。要更快可設 `pqRekeyInterval` 小一點。App 層「疑似外洩時立刻開一輪」列為後續 |
| 2 | Low | 對方的 ML-KEM 公鑰只驗長度：已認證但有 bug／惡意的對方送一把係數超出範圍的公鑰，我方收下後每次開輪次都丟例外，會話永遠送不出去、通道也不關 | 收下時做 FIPS 203 的封裝金鑰檢查（每個 12 位元係數 < 3329），不合格丟 `RatchetProtocolError`、銷毀會話；`fromState` 的 `peerKemPk` 同樣檢查。測試（以 `vi.mock` 產生壞公鑰） |

| 10 | Info | 已認證的對方可以用假的 DH 步進逼我們每步做一次解封裝＋金鑰生成 | 接受：每個我方輪次最多一次，記憶體有上限（§7〈資源〉） |

審查者確認沒有問題的：每一把訊息金鑰都經根金鑰依賴 ML-KEM 秘密（Alice 第一條鏈直接混入輪次 0、Bob 第一次接收步進強制要有它、之後所有鏈都從含它的根金鑰推導、Bob 的 KEM 公鑰經 hello 雜湊綁定）；找不到任何讓後量子會話產生或接受純古典鏈金鑰的路徑；版本只收 3（古典只收 1、2 明確拒絕）、保留旗標與長度與 `NONE` 編號都有檢查；header 整個在 AD 裡、跨會話拼接不過；除了 Bob 第一則的隱式拒絕路徑，解封裝都在 MAC 之後；MAC 前的所有狀態變化失敗時整批還原；並發（`encrypt` 在第一個 `await` 前完成讀改寫）；看門狗計數只在 MAC 驗過的混入／回報時歸零，16 步以內的丟包或重排不觸發，中間人無法只憑驗得過的訊息一擊關閉；FS 與 v1 相同；協商（沒有 `pqf`→明確拒絕、竄改→握手失敗、古典與 v0.27 互通、v0.27 後量子狀態拒絕）；編號到頂丟例外、不繞回。

## Consequences

- ＋ PQ 模式每則 header 從 2,314 B 降到 50 B（只比古典多 9 B）；輪次攤提後雙向輪流平均 94 B。星狀會話一則按鍵 2,395 → 131 B，經中繼 8,702 → 2,214 B（與古典相同）。
- ＋ 帶 KEM 的訊息遺失不再影響任何一則能不能解（延後混入）。
- ＋ 後量子保密的範圍與前向保密不變；選擇性丟包被偵測、明確失敗。
- － 後量子事後自癒從「下一步」變成「最壞約 2 × `pqRekeyInterval` 則＋幾個來回」（可調；§7、§10 #1）。
- － 與 v0.27 的後量子會話不相容（明確拒絕，古典照常互通）；v0.27 匯出的後量子狀態不能還原。
- － 主動攻擊者可以藉由選擇性丟包讓會話被關閉（它本來就能阻斷服務）。
- － 仍未經外部審計與形式驗證；沒有 SPQR 的第二條獨立棘輪。
- － 主入口打包大小 156,329 → 163,033 B（+6.7 KB，+4.3%；gzip 57,162 → 59,473 B，+2.3 KB），`./star` 113,983 → 120,585 B。主要是新的狀態欄位（屬性名不會被壓縮）、輪次邏輯、`fromState` 的逐欄驗證與中文錯誤訊息。
- 試算器（`./estimator`，ADR 0002）仍照 PRD 的公式以每則 2,272 B 計後量子雙棘輪，現在偏保守；是否改成攤提值另案決定（會改動 PRD 範例的對照數字）。
