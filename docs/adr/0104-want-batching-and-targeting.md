# 0104. 索取（want）合併成幾則再送，只問答得出來的裝置

- 狀態：**已接受（Accepted，2026-10-22）**——使用者 2026-10-22 選定「A、B、C 一起做」
- 日期：2026-10-22
- 對應：SDK ADR 0058（帶 `fetch` 的索取）、0088（新檔案連祖先一起要，`deep`）；CinderSync ADR 0098（應答端也要拿 TURN）

## Context

2026-10-22 在 motorola edge 20 pro（Android 13、LTE）以新的測試 vault（MotoTest4）加入既有的同步群組，加入過程中在手機上寫的筆記，60 秒內都沒有送到桌機。

查下來是協調器自己的 `want` 把同一身分的事件預算（每分鐘 100 則、先進先出，直連信令與 vault 同步共用）吃光了：
- `#want()` 每遇到一個缺父版本、或缺內容的版本，就**立刻、各送一則**；
- 每一則都**廣播給名單上每一台**，包含早就離線、不會回答的舊測試機；
- 實機 40 秒送出 363 則 `want`，約 7 個收件人，總共約 2,500 個事件，要排 20 多分鐘。手機自己的 `node` 與直連信令都排在後面。

等這批送完之後，手機改的內容 1.7 秒就經中繼到了桌機——傳輸本身沒問題，是排隊。

## Decision

1. **合併**：`#want` 照舊先做節流（同一個版本 `wantIntervalMs` 內只要一次），然後放進收集區，`WANT_BATCH_MS`（100 ms）後一起送。
   - 依「要不要內容（`fetch`）／要不要祖先（`deep`）／收件人」分組，每組每則最多 1000 項，同一個版本只出現一次。
   - 收集中算在 `#auxSending` 裡：`sent()` 不會在索取送出之前就回報送完。
   - 送出時已經離線、暫停或停止：整批丟掉，並清掉節流紀錄，之後可以馬上再要。`stop()` 也一樣。
2. **只問答得出來的裝置**（`VaultSendOptions.to`）：
   - 收到的版本缺父版本 → 只問**送這個版本來的那台**，它一定有。
   - 摘要裡看到不認得的版本頭 → 只問**送摘要來的那台**。
   - 缺內容（`#markPending`）→ 只問 `rec.peers` 裡**已知有這個版本或它的後代**的裝置；一台都不知道才廣播。
   - 使用者等著的讀取（`fetch`）照舊廣播。
   - 定期維護時的重新索取（等太久的父版本、還沒到的內容）**照舊廣播**，當作退路：問的那台剛好離線了，下一輪維護會問所有裝置。
3. 協定沒有改：舊版裝置照樣看得懂、照樣回答。

## Consequences

- ＋ 新裝置加入時，40 個檔、每個 3 版的測試案例裡，新裝置的索取從 80 則降到 4 則以內，而且只送給在線、送版本來的那台。
- ＋ 不在線的舊裝置不再收到用不到的索取，收件人變少，中繼的事件數也跟著少。
- － 每個索取多等 100 ms 才送出。使用者等著的讀取也一樣，但相較於中繼的來回時間可以忽略。
- － 問的那台剛好在送出後離線：要等下一輪維護（預設 5 分鐘的節流過了之後）改成廣播才問得到別台。
- 要讓 CinderSync 與 Coffice 拿到，要升 SDK 版本。新舊版本混著用也能互通，只是舊版的那一台還是會廣播。
